# 配额与计费机制

本页解释系统**怎么算、怎么扣**每一笔用量。阅读前提：先看[核心概念](concepts.md)里的「方案 / 额度池 / 配额倍率」。

## 一个请求进来，经过哪些检查

请求（以协议默认入口 `/v1` 或 `/v1/responses` 进来）按顺序通过以下关卡，任何一道不过就返回错误：

| 顺序 | 检查 | 超限行为 |
|---|---|---|
| 1 | 入口识别、虚拟 Key 有效性 | 404 / 403 |
| 2 | 组成员直连限制（开启「限制直连」后，组内方案禁止 `/后缀` 直连） | 403 |
| 3 | IP 限流（**120 次/分钟/IP**，硬编码，60 秒滚动窗口） | 429，Retry-After: 60 |
| 4 | 用户归属校验（Key 是否分配给该方案） | 403 |
| 5 | 每用户频率（`rateLimitPerMinute`，默认 **60 次/分钟**，滚动窗口） | 429，Retry-After: 60 |
| 6 | 每用户并发（`maxConcurrentPerUser`，默认 **5**） | 429，Retry-After: 1 |
| 7 | **逐候选方案**依次检查：模型白名单 → 熔断器 → **配额** | 见下 |

第 7 步是核心：系统按生效方案组的顺序逐个方案尝试，每个候选都要过三道门，任何一道不过就**跳到下一个候选**（failover），最后一个候选也不过才把错误返回给你。

> ⚠️ **配额是逐方案检查的**：同一个用户的配额会在每个候选方案上各判一次——因为不同方案的倍率、额度池可能不同。429 文案里显示的是「实际会记账的那个模型」的倍率，不是方案默认。

## 额度池：配额的唯一载体

**配额存在「额度池」上，不直接存在方案或用户身上**（方案级每日限额是旧版设计，已迁移进池）。运行时判定：

```text
baseLimit = 用户在该池设置的个人配额（>0 时）
          否则 = 池级每日配额
limit     = baseLimit + 当日临时加量(bonus)
used      = 当日计权用量(weighted_tokens 求和) − 当日重置基线
允许请求 ⇔ used < limit
```

- 两者都没设（≤0）→ **不限制**，签到/加量等临时操作会提示「无需加量」
- 同一池内多个方案**共享**同一份额度：从方案 A 用掉的，从方案 B 的入口看也一样少
- 一个用户可以访问多个池（多个方案分属不同池时），各池独立计账、独立签到/加量

## weighted_tokens：配额货币的完整公式

每次响应完成后记账，公式：

```text
rate = 当前倍率（峰谷判定 + 模型单独定价，见下节）

# Anthropic 协议
billableInput = input_tokens
weighted      = round((billableInput + output_tokens) × rate)

# OpenAI Responses 协议（缓存命中折叠在 input 里，先剥离）
includedCache = cache_read（仅当 0 < cache_read ≤ input_tokens 时剥离）
billableInput = input_tokens − includedCache + round(includedCache × cacheReadQuotaRate)
weighted      = round((billableInput + output_tokens) × rate)
```

各 token 类型的处理：

| 类型 | 计入配额基数？ | 说明 |
|---|---|---|
| input_tokens | ✅ 全额 | Anthropic 上游的 input **天然不含**缓存命中（缓存读单独上报） |
| output_tokens | ✅ 全额 | |
| **cache_creation（缓存写入）** | ❌ **不计入** | 只落库存档、进报表，不参与计权 |
| cache_read（Anthropic） | ❌ **不计入** | 上游单独报字段，配额基数本身就是缓存外口径 |
| cache_read（Responses/OpenAI） | 默认剥离不计 | 上游把命中折在 input 里，先剥离（镜像 Anthropic 口径）；`cacheReadQuotaRate` 决定剥离后按多少比例计回 |

`cacheReadQuotaRate`（仅 Responses 协议方案有意义）：**默认 0 = 缓存命中完全免费**；0~1 部分计入；1 = 全额计费（旧口径）。守卫：仅当 `0 < cache_read ≤ input_tokens` 时才剥离——上游返回的缓存读大于 input（说明已排除过缓存）时视为口径已对齐，不再处理。

### 数字示例

**Anthropic 方案**，低谷倍率 ×0.5，某次响应：input 10,000 / output 4,000 / 缓存写 50,000 / 缓存读 80,000：

```text
weighted = round((10000 + 4000) × 0.5) = 7000
```

本次扣配额 **7000**——缓存写、缓存读都不进公式；但报表和图表显示全部真实 token。

**Responses（Codex）方案**，倍率 ×1.0，`cacheReadQuotaRate = 0.1`，某次响应：input 100,000（其中缓存命中 90,000 折叠在内）/ output 2,000：

```text
billableInput = 100000 − 90000 + round(90000 × 0.1) = 19000
weighted      = round((19000 + 2000) × 1.0) = 21000
```

若 `cacheReadQuotaRate` 为默认 0，则 weighted = 12,000——这就是 Codex 重放式对话（每轮重发全对话、缓存命中率极高）在默认配置下几乎不扣配额的原因。

> ⚠️ **记账时刻是响应完成时刻**：跨峰谷边界的长请求按「结束时刻」的倍率定价。倍率**写时冻结、永不追溯**——事后改倍率只影响之后的请求，历史不重算。

## 峰谷倍率怎么选

```text
inPeak  = 当前时刻(北京时间)落在方案的 peakHours 内
rate    = 有该模型的单独定价 → inPeak ? 定价.peak : 定价.offPeak
        否则                 → inPeak ? 方案峰倍率 : 方案谷倍率
```

- **模型单独定价按「真实上游模型名」匹配**（不是别名），精确匹配优先，其次大小写不敏感比对
- 高峰时段支持跨午夜（如 22:00–02:00：`分钟 ≥ 22:00` 或 `分钟 < 02:00` 命中）
- **peakHours 不配置 = 全天按低谷倍率**（设置页会警告）
- 倍率范围 [0, 10]，两位小数；**锚定约定：×1.0 = 高峰时段一个 token 按方案默认价**
- 配额倍率工作区/价目表里的「×N 后转入低谷」提示，取的是**下一个会翻转峰谷状态**的时刻

## 临时加量 / 重置 / 撤销：到底改了什么

三个操作都写在「当日操作表」里，键 =（池, 用户, 北京日期）——**日期一变旧行查不到，自然失效**，无需回滚任务：

| 操作 | 精确语义 |
|---|---|
| **加量** | **设置/覆盖**当日 bonus 值（不是累加！再加 1 万是「改成 1 万」不是「+1 万」）。生效：`limit = baseLimit + bonus` |
| **重置** | 记录当日已用计权量为**基线**，此后 `used = 当日用量 − 基线`，即配额回满。统计行不删，报表照常显示真实用量 |
| **撤销** | 删除当日该用户的全部手工痕迹（加量和基线一起清），回到系统自然状态 |

**累加的例外**：签到奖励和「加量申请发放」是**累加**到 bonus 上的（`bonus = 原bonus + 奖励`），与手工加量共存。

> ⚠️ 手工加量作用于**整个池**：给方案 A 加量，同池的方案 B 也一起生效（否则用户换条路由照样被挡）。

## 签到与加量申请的精确规则

**每日签到**：

```text
amount = min + floor(random() × (max − min + 1))   # [min, max] 均匀整数
```

- 默认区间 [10,000, 100,000]；随机数**只抽一次**，用户可访问的**每个池各加同一份**（不是每池独立抽）
- 每天一次（北京日期键）；连续天数（streak）纯展示，无奖励加成；未签时从昨天起算（「今天还能保住的连续」）

**加量申请**：

- 提交：每北京日 1 次；**提交不占每周次数**——只有管理员处理过（通过/拒绝）的申请才计数
- 每周上限默认 **3**（可配 0–1000），周窗口 = 本周一 00:00（北京时间）
- 池不限量时拒绝申请（「无需申请加量」）
- 管理员「发放加量」= 发当日临时加量（累加）并自动标记已处理

## 自动配额调整（AUTO）完整算法

> ⚠️ 三个隐藏约束，配置前必须知道：
> 1. 只评估**默认方案所属的额度池**，其他池不受影响
> 2. 只评估**设置了个人配额**的用户（只吃池公共配额的用户永远不会被自动上调）
> 3. **没有定时器**——每天第一次有请求进来时惰性评估一次（每北京日一次）

参数（设置页 → 全局配置 → 自动配额调整）：

| UI 名称 | 字段 | 默认 | 范围 |
|---|---|---|---|
| 启用自动调整 | `autoQuotaAdjust.enabled` | 关 | — |
| 评估周期（天） | `evaluationPeriodDays` | 5 | 3–30 |
| 命中阈值 | `hitThreshold` | 0.9 | 0.5–1 |
| 触发命中率 | `triggerRate` | 0.9 | 0.3–1 |
| 增长率 | `increaseFactor` | 1.15（+15%） | +5%~+100% |
| 安全系数 | `safetyFactor` | 1.3 | 100%–200% |
| 单次最大增幅 | `maxIncreaseFactor` | 2.0 | ≥1.1 |
| 配额上限 | `maxAutoQuota` | 10,000,000 | ≥0 |
| 冷却天数 | `cooldownDays` | 3 | ≥1 |

算法（对池内每个用户）：

```text
dates    = 昨天往前 P 个北京日期（不含今天）
dayUsage[d] = 该用户当日按池全部成员方案聚合的计权用量(weighted_tokens)

命中日   = dayUsage[d] > 0 且 dayUsage[d] ≥ userQuota × hitThreshold 的天数
命中率   = 命中日数 ÷ P          ← 分母是周期总天数！
命中率 < triggerRate → 不调整

avgDaily = 总用量 ÷ 有用量的天数   ← 这里的分母才是有用量天数
methodA  = userQuota × increaseFactor        # 稳健路线：现有额度 × 增长率
methodB  = avgDaily × safetyFactor           # 激进路线：真实日均 × 安全系数
newQuota = min( max(methodA, methodB),
               userQuota × maxIncreaseFactor,
               maxAutoQuota )
newQuota ≤ userQuota → 放弃
生效: 永久改写该用户在池内的 dailyTokenLimit（直到下次调整）
```

### 数字示例

个人配额 1,000,000，默认参数（P=5, hit=0.9, trigger=0.9, growth=1.15, safety=1.3, maxInc=2.0）：

- 近 5 天计权用量：900k、950k、880k、920k、0（周三没来）
- 命中日 = 4 天（≥900k）；命中率 = 4÷5 = 0.8 < 0.9 → **不调整**（尽管几乎天天顶满，因为没用的那天也占分母）
- 若命中率达标：methodA = 1,000,000×1.15 = 1,150,000；methodB = (900k+950k+880k+920k)÷4 ×1.3 = 1,191,750 → 取大者 1,191,750，未超 2,000,000 上限 → 新配额 **1,191,750**

> ⚠️ 评估一律用**计权**列：若用真实 token，×0.5 的低谷折扣会被复利放大。调整写 `quota_adjust_history`（只留最近 100 条）+ 系统审计，与临时加量互不干扰。

## 超限 429 长什么样

所有候选都因配额失败时，返回 429：

```json
{
  "error": "今日配额已用尽：7400/8000（计权）…",
  "type": "quota_exceeded",
  "quota": {
    "used": 7400, "limit": 8000, "remaining": 0,
    "source": "个人配额", "rawUsed": 14800, "discounted": 7400, "rate": 0.5
  },
  "usageUrl": "http://服务器地址/usage/你的虚拟Key"
}
```

（`rawUsed` 与 `used` 的差额是倍率/缓存抵扣的展示口径，按当日真实与计权比例折算。）

响应头 `Retry-After` = 距**下一个北京时间零点**的秒数。错误消息逐行包含：

1. 计权用量与限额（池共享时注明「额度池『xx』，N 个方案共用」）
2. 真实 token 与抵扣差额（`实际 token 14800，已抵扣 7400`）
3. 当前时段倍率（`高峰 ×1.5` / 模型单独定价标注 / `· 20:00 后转入低谷 ×0.5`）
4. 固定尾行：`额度将于北京时间次日凌晨重置。查看用量详情: {usageUrl}`

每日零点重置不是定时清零，而是**日期键不再匹配**——今天的用量行存的是今天的北京日期，零点后查的是新日期，自然从零开始。
