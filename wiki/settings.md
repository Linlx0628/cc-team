# 设置页：方案与全局配置

地址 `/settings`（需登录）。布局：左侧栏（协议切换、方案卡片、方案组编辑器、导航按钮）+ 右侧表单区（当前所选方案的配置）。

## 左侧栏

- **协议双标签**：Anthropic（Claude Code · /v1）与 OpenAI（Codex · /v1/responses）各自维护一套方案列表，「＋ 新建」在当前协议下建方案
- **方案卡片**：每个方案一张卡，点击后右侧显示其表单；卡片上显示该方案的用户数（只统计已分配真实 Key 的用户）
- **默认方案组 / OpenAI 方案组编辑器**：有序名单即 failover 优先级。「＋加入」弹层挑方案加入组，可上下排序；第一位是**组头**。**「限制直连」**勾选后，基础组与全部调度组的方案都不允许带 `/后缀` 直连
- **调度接管提示**：当方案组调度规则生效期间，组编辑器会变成只读提示（显示生效中的组名与来源），规则结束后自动恢复编辑
- **侧栏导航按钮**：额度池、数据管理、操作日志、加量申请（待处理时显示角标）、方案组调度
- **底部按钮**：用户管理、通知管理、上游额度（都是右侧二级视图，不再是弹窗）

### 方案卡片上的「测试」按钮

- **在哪**：每张方案卡片底部那排按钮里的「**测试**」（和复制、复制代码、重命名同一排）
- **怎么用**：点一下即可，按钮会变成「测试中…」并禁用，出结果后自动恢复；**页面不重载**，结果用一个提示告诉你
- **它会做什么**：直接拿该方案里已经配置的**真实 Key**，向上游发一次极小的真实请求（内容就是一句 `hi`），用上游的回应判断这套方案能不能通
- **怎么算成功**：上游返回 **HTTP 2xx** 就算成功。成功提示里会带上状态码、往返耗时、这次实际发给上游的模型名，外加抽到的回复原文（如 `hi`），例如 `方案「GLM」测试成功：HTTP 200 · 1234 ms · 模型 glm-4-flash，回复「hi」`
- **测哪个模型**：自动挑最便宜的那个 —— 优先别名里带 `haiku` 的，其次带 `sonnet` 的，再其次任意一个别名，都没有就用「允许模型」的第一个；**连一个模型线索都没有时按协议兜底**（Anthropic 用 `claude-3-5-haiku-20241022`，Responses 用 `gpt-4o-mini`），这样刚建好还没配别名也能测。全过程不需要你选
- **请求长什么样**：Anthropic 协议发 `POST {上游}/v1/messages`，头是 `x-api-key` + `anthropic-version: 2023-06-01`，体是 `{"model":"<上面挑的那个>","max_tokens":16,"messages":[{"role":"user","content":"hi"}]}`；Responses 协议发 `POST {上游}{方案的 responsesPath 或 /v1/responses}`，头是 `Authorization: Bearer`，体是 `{"model":"…","input":"hi","max_output_tokens":16}`。上游地址已带 `/v1` 时不会再重复拼一段
- **失败怎么提示**：弹窗给出具体原因 —— 还没填上游地址 / 还没有可用的成员密钥 / 上游返回的状态码与错误正文（如 `401 invalid api key`）/ 20 秒超时 / 网络不通。照提示改配置再测一次即可
- **会留痕**：**每点一次测试，就在「操作日志」里新增一条「方案测试」记录**（动作标识 `profile.test`）。成功、失败都记，内容包括状态码、耗时、模型名与错误文案；**真实 Key 不会出现在日志里**
- **时间口径**：记录时间与页面其它地方一致，都是**北京时间（UTC+8）**
- **多协议都适用**：Anthropic（Claude Code）方案打 `/v1/messages`，OpenAI（Codex）方案按该方案配置的 Responses 出站端点打（默认 `/v1/responses`，火山 Coding Plan 这类用 `/responses` 的也照它自己的配置来）

> ⚠️ 测试发的是**真实请求**（会产生极少量 token 消耗，属于方案自身的计费）。「测试成功」只说明地址、Key、模型、协议这几项能对上，**不代表**额度、限流、图片识别等其它配置也正常。

## 方案表单（右侧）

### 上游代理

- **上游地址**：真正的服务商接入点
- **熔断状态徽章**：正常 / 探测中 / 熔断中（熔断时显示距下次探测的秒数）

### 模型别名（必填）

结构化编辑器，一行一条别名：

- **别名**：暴露给成员的模型名（如 `jx-opus`）
- **实际模型**：上游真实模型
- **每别名上下文长度**
- 快捷按钮一键添加 `jx-fable` / `jx-opus` / `jx-haiku` / `jx-sonnet`
- **高峰期模型别名覆盖**：进入高峰时段时，对外别名自动切换到配置的高峰版

**允许模型**由别名自动汇总生成，不可手填。成员侧的 Codex 模型目录、配置页模型清单都来自这里。

### 图片识别辅助

多模态勾选 + 辅助模型指定：方案本身不识图时，可指定一个有视觉能力的辅助模型代为处理图片（vision 桥接）。

### 计费类型 / 额度池

- **计费类型**：决定配额怎么算
- **额度池**：同一上游套餐的方案选同一个池，共享额度判定（见[核心概念](concepts.md#额度池)）。侧栏「额度池」入口可看池列表

### 配额倍率与高峰时段

- **峰 / 谷方案默认倍率** + 按模型的 `modelQuotaRates`（模型级优先）
- **cacheReadQuotaRate**：缓存读取的计权系数
- **高峰时段**：每日重复的时间段（北京时间），峰时用峰倍率并触发别名覆盖

### 全局配置（所有方案共享）

**超时 & 重试 / 流量控制**（参数细节与重试算法见[代理与调度机制](mechanism-proxy.md#超时与重试)）：

| UI 名称 | 默认值 | 范围 | 行为 |
|---|---|---|---|
| JSON 请求超时 | 3 分钟 | 10s–10min | 非流式上游超时 |
| 流式请求超时 | 10 分钟 | 1–30min | 流式 socket 兜底 |
| 最大重试次数 | 3 | 0–10 | 非流式同上游重试（流式**没有**重试） |
| 重试基础延迟 | 1000ms | 100ms–30s | 指数退避基数 |
| 可重试状态码 | 429,502,503,504 | — | 命中才重试 |
| 每用户最大并发 | 5 | 1–50 | 超限 429，1 秒后重试 |
| 每用户每分钟请求 | 60 | 1–600 | 滚动窗口，超限 429 |
| 熔断失败阈值 | 5 | 1–50 | 连续失败即熔断 |
| 熔断冷却时间 | 30 秒 | 1s–5min | 探测失败后 ×2 退避，封顶 5 分钟 |

> ⚠️ 三个参数**没有 UI 输入框**，需手改 `config.json` 并重启：`proxy.streamIdleTimeout`（流式空闲超时，默认 120s）、`proxy.stickySessionTtlSeconds`（粘性会话 TTL，默认 300s，0 关闭）、`proxy.rateLimitFallbackSeconds`（限流兜底窗口，默认 120s）。

- **自动配额调整**：持续用满时自动上调额度池配额。参数与完整算法（含三个隐藏约束）见[配额与计费机制](mechanism-quota.md#自动配额调整-auto完整算法)
- **签到与加量申请**：开关与参数（签到奖励默认区间 [1 万, 10 万] token；申请每周处理上限默认 3）。规则见[用户与配额管理](users.md#签到与奖励)
- **产出与成本设置**：等值成本用的参考牌价表（USD/1M tokens，支持峰谷分时价；**改价后历史立即按新价重算**）。计算细节见[指标口径参考](metrics-reference.md#等值成本计算)
- **旧数据导入**、**统计数据清理**
- **通知设置**：飞书 / 钉钉 / 企业微信 / Server酱 / Bark，可发测试通知。触发事件与冷却语义见[后台自动化](automation.md#通知推送)。产出告警推送到这里配置的渠道，**同时发一份给触发告警的成员本人**（按其「我的用量」页自助配置的渠道）
  - **邮件（SMTP 直发）**：SMTP 服务器 / 端口 / 账号 / 密码（或授权码）/ 发件人 / 发件人显示名（可选，收件人看到的「发件人」名字）。**账号 = SMTP 认证用户名，填完整邮箱地址**（国内邮箱一律用「授权码」而非网页登录密码；填错会报 `526/535 Authentication failure`）。**密码明文回显**，方便核对；清空后保存 = 保留原值（不会误删）。**465 是隐式 TLS（默认勾选）**；用 587 请取消「隐式 TLS」走 STARTTLS。内网自签名证书可勾「跳过证书校验」（默认关——开启等于不校验对方身份，只在确实必要时用）
  - 邮件用于把**代码评审发现的问题发给提交人**（见[代码评审](code-review.md#评出问题后通知谁)）；成员自己配的「收件邮箱」也走这套 SMTP
  - **两种邮件版式**：代码评审邮件用「终端代码风」长文档版式（按文件分组、`-`/`+` 建议对照，见[代码评审](code-review.md)）；**普通通知**（网关告警/恢复、产出告警）用**通知卡**版式 —— 顶部按级别着色（故障红 / 提醒琥珀 / 恢复绿）、`【类型】` 作徽标、首行作标题、其余行作细节，底部一行等宽时间（北京时间），因此邮件列表里一眼能分清是"出故障了"还是"恢复了"。两者都是 table 布局 + 内联样式、零外部资源；客户端不支持 HTML 时自动降级为原来的纯文本
- **危险操作**：清空全部数据（操作前系统会自动备份到 `backups/`；审计日志不受清空影响）

## 方案导出 / 导入（跨环境搬迁）

- **导出**：方案可导出为一段可粘贴 JSON（含别名、峰谷、倍率、上下文窗口、多模态、图片桥）
- **不含的字段**（敏感或环境相关，导出前心里有数）：用户分配、额度池、真实 Key、URL 后缀
- **导入**：在另一环境的新建方案弹窗（侧栏「＋ 新建」）里粘贴这段 JSON 即可重建方案；**只新建、不覆盖**已有方案

典型用法：测试环境调好一套方案 → 导出 JSON → 生产环境粘贴导入。

## 保存后会发生什么

设置页的每一处保存都分两类，**看到的反馈不一样**：

| 你点了什么 | 保存后 |
|---|---|
| 用户管理的「**保存全部**」、某行的「**删除**」、额度池卡片的「**保存**」、额度池「**重命名**」 | **就地生效，页面不重载**：当前视图（用户管理 / 额度池）保持打开，右侧底部立即弹出「已保存 / 已删除 / 已重命名」提示，表格与卡片当场更新 |
| 新建 / 删除额度池、方案的新建 / 导入 / 删除 / 重命名 / 复制 / 设为默认、方案组保存、调度规则保存、清空数据 | **整页重载**：这些会改动服务端渲染出来的整块结构（侧栏列表、下拉选项），重载后自动**回到你原来所在的视图**并弹出提示 |

> ⚠️ 只改数字/名字的保存之所以不再重载，是因为页面里显示的这些值本来就是浏览器当前状态的真实来源，服务端落库后本地同步即可。它**不会**改变任何落库口径：接口、校验、`config.json` 的写入路径完全没变。
> ⚠️ 保存失败仍然是原来的 `alert` 弹窗（例如用户名重复、额度池名已存在），不会静默吞掉。

## 用户管理

见[用户与配额管理](users.md)。入口在侧栏底部按钮，点击后右侧**整页视图**显示（不再是弹窗），全局用户与方案真实 Key 分配都在这一页编辑，「保存全部」一次性提交。

## 通知管理（站内信）

入口：设置页底部「**通知管理**」按钮（右侧二级视图）。创建 Markdown 格式的站内信，发布到成员「我的用量」页。每条通知由**类型**与**接收对象**两个维度决定成员怎么看到它：

| 类型 | 成员侧表现 |
|---|---|
| **通知**（默认） | 只出现在成员页右上角的**消息铃铛**里，不打断使用 |
| **公告** | 除了进铃铛（带「公告」角标），成员**每次打开「我的用量」页**都会**全屏弹出**，直到这条公告被标记已读 |

### 生命周期：草稿 → 发布 → 撤回/删除

| 状态 | 成员能看到吗 | 可做的操作 |
|---|---|---|
| 草稿 | 不能 | 编辑（含改类型）、发布、删除 |
| 已发布 | 能（通知进铃铛；公告额外弹屏） | 查看、撤回、删除 |

- **新建/编辑**：填标题（≤100 字）与 Markdown 正文（≤20000 字），选**类型**与**接收对象**，类型下拉下方实时显示该类型的行为说明，右侧实时预览成员看到的渲染效果。保存后是**草稿**，必须点「**发布**」才会推送
- **接收对象**：「全员」或「指定成员」（多选）。定向名单发布后不可改——要改名单先撤回再编辑
- **撤回**：通知立即从成员侧消失（铃铛里消失，公告也不再弹），回到草稿。**已读记录保留**：重新发布后读过的人不会重新变未读——想让所有人重新看到，复制内容新建一条更符合直觉
- **删除**：通知与已读记录一起删，不可恢复
- 所有操作（创建/编辑/发布/撤回/删除）记入审计日志的「管理操作」分类，创建与发布的日志文案里带类型（公告/通知）

### 公告的「已读」语义

公告**没有过期时间**，全屏弹屏只认「已读」。成员侧标记已读的三种途径（写的是同一份已读记录，任一途径生效后这条公告就不再弹）：

1. 弹屏上点「**我已阅读，不再弹出**」
2. 铃铛列表里**展开**这条公告（和通知一样「看过才算」）
3. 铃铛里点「**全部已读**」

成员点「暂时关闭」（或按 `Esc`）只关闭当次、**不标已读**，下次进页仍会弹——这是刻意设计，适合「必须让每个人确认」的停机公告、制度变更等场景。想让公告彻底不弹又不想等成员自己点，只能**撤回或删除**它。

多条未读公告同时存在时，按发布时间**从旧到新**逐条弹出（弹屏右上角显示「第 x / y 条」）。

### 成员侧（铃铛）

成员在「我的用量」页顶部右侧看到**消息通知铃铛**（所有标签页共用）：

- 有未读时显示红色角标（数字，超过 99 显示 `99+`），每 60 秒自动刷新。未读数**包含未读公告**
- **鼠标放上去**弹出未读消息列表（最近 8 条），点「查看全部」进完整列表
- **点击铃铛**打开消息列表弹窗：未读条目高亮，点条目展开渲染后的 Markdown 正文，**展开即标记该条已读**；「全部已读」一键清零
- 公告条目标题前带「**公告**」小角标，与普通通知区分；已读的公告仍留在列表里可随时翻看
- 定向通知只有被选中的成员在铃铛里看到；全员通知所有人可见

## 上游额度（左栏底部入口）

入口：设置页左栏**最底部**「**上游额度**」按钮（右侧二级视图）。这里配置的是「去问各平台官方接口要额度/余额」的行为，**不动代理与本地配额**：

- **顶部固定操作条**：`总开关`（默认开启）、`保存全部`、`刷新全部`、`去面板看 →`。改动需点「保存全部」才落盘
- **每个平台一行**：勾选框（启用）、平台名、`实验` 标（接口未文档化）、**这一行右侧直接显示最近读到的数字**（纯余额平台如 `¥1,234.56`；既有套餐窗口又有余额的平台如 `每周 98% · ¥380.00`，**最紧的窗口排前面**，需要关注时标红/标黄）与状态徽章（`正常 / 额度告警 / 查询失败 / 未配置 / 已关闭 / 仅控制台`）——不用展开就能看出哪些平台已经通了
- **点行展开**才看到凭据设置：**凭据来源**（自动复用方案里已有的密钥 / 指定方案与成员 / 手动填 Key；云平台则是 AccessKey ID + Secret；中转网关 Sub2API / NewAPI 是「**方案**（带出站点地址）」这一格，其中 **Sub2API 的方案是必选项**（地址与成员 Key 都从方案来，没有「凭据来源」），NewAPI 要填控制台的**系统访问令牌**与数字用户 ID）、平台专属字段（如智谱的组织与项目 ID、火山的区域、NewAPI 的每单位额度）；行内的「**查询一次**」当场发一次请求，结果（读到几项、具体数字）直接显示在这一行里
- **中转站（Sub2API / NewAPI）不是一行，而是一段**：段头右上角「**＋ 添加站点**」可以加任意多个站点（同时用好几家中转），每个站点一张卡；卡上有「删除这个站点」，改动同样要点「保存全部」才生效。**Sub2API 的卡上只有「方案 + 成员」**——没有「凭据来源」、也没有单独的显示名，地址与 Key 都从方案来（**一个方案 = 一个站点**，卡片标题就是方案名，换方案标题跟着变）；**NewAPI 的卡上还有显示名与系统访问令牌**。新加的站点要先点「保存全部」，再点「查询一次」（没保存的站点查询会提示先保存）
- **`高级：缓存 / 自动刷新 / 超时 / 告警阈值`**（页面顶部）与每个平台行里的 **`高级：接入点覆盖 / 显示名`** 默认折叠，不占版面
- 成员下拉**只列真的配了密钥且没停用的成员**（空 Key 的成员查不了）；「保存全部」后会清掉被改动平台的缓存。页面先渲配置、再补最近读数；读取失败时会显示具体原因与「重试」按钮，不会留一片空白
- 凭据明文存储与回显（与 SMTP 密码同一套处理）

完整的平台清单、每家接口的官方性与凭据要求、缓存/告警的精确算法与数字示例见[上游额度 / 账户余额](upstream-quota.md)；面板上的展示见[管理面板：工作区](dashboard-workspaces.md#2-上游额度)。

## 代码评审（左栏菜单）

「设置页 → 左栏菜单 → 代码评审」（与额度池/数据管理等并列的二级视图）：

**启用与引擎**（第一张卡片）：

| 字段 | 默认 | 说明 |
|---|---|---|
| 启用代码评审 | 关 | 总开关;关闭时任何触发都返回 409 |
| 评审用哪个方案 | 无 | **下拉选择已有方案** —— 不需要填任何 API 信息:评审就是经本网关发往该方案,端点与协议由服务端按方案推导并强制回环,管理员改不了 |
| 评审模型 | 方案第一个可用模型 | 下拉 = 所选方案的别名 + 允许模型 |
| 评审账号 | 未创建 | 一键创建 `jx-review-…` 专用账号(超级用户),运行期向所选方案**借用已有的真实 Key** —— 不用再填真实 Key;用量记在「代码评审」名下便于对账。方案一把真实 Key 都没有时会明确提示 |
| 引擎状态行 | — | OCR 版本 · git 版本(需 ≥2.41) · 工作区占用 · 队列;「重新检测引擎」随时刷新 |

**统一评审标准**（第二张卡片，**只读**）：显示这一版的**版本号**（编译产物 sha256 前 12 位，如 `v4246b9e1a629`）与完整指纹、段数/大小/命中规则数，下面可逐段展开看正文，并列出「哪个 glob 命中哪一段」的**命中顺序表**。标准正文内置在代码 `lib/review-standard/` 里，**界面不提供编辑** —— 改标准走代码评审与发版（可评审、可回滚），改完重启服务再点卡片上的「重新载入」即可刷新。这一版的版本号会出现在每条运行记录、导出报告与通知邮件里，用于归因「两次意见数不同是不是换了标准」。⚠️ 标准坏掉时（段文件被清空、兜底规则不在最后一条）这张卡会**标红并摊开具体错误**，且这期间发起的评审**直接失败并写明原因**，不会退回「没有标准」凑合评。完整口径见[统一评审标准](code-review.md#统一评审标准)。

**业务背景**（第三张卡片）：标准管「怎么评」，业务背景管「这段代码在我们这儿是干什么的」—— 两块多行输入，**每块最多 20000 字**，输入框下方实时显示「已填 N / 20000 字」：

| 级别 | 在哪填 | 写什么 |
|---|---|---|
| 全局 | 这张卡片的「全局业务背景」 | 所有仓库共用的团队级约定（资金通道、状态机规则、幂等键取法……） |
| 本仓库 | 仓库白名单 →「编辑」→「本仓库业务背景」 | 这个仓库特有的东西（它负责哪些业务、哪些模块是资金/权限关键路径） |

两者按「**全局 + 本仓库**」的顺序拼接成一份 Markdown 后一起交给引擎（不走命令行参数，落成文件注入）；留空即不注入。**别把它写成第二份编码规范** —— 通用规范归标准管，这里只写代码里读不出来的业务规则。

**仓库白名单**（第四张卡片）：**填入只是登记,首次触发评审时才拉取**。来源 remote=线上仓库(需凭据时填 Token/私钥),local=服务器本地绝对路径(无需凭据,评审的是已 commit 的内容)。表格列出 名称/来源(remote·local)/地址/分支/凭据(已配置 ****末4位)/定时/在线触发/**成员**;「＋添加仓库」展开表单编辑,定时可选关闭/固定间隔(1~168 小时)/每天定点(北京时间 HH:MM)+「只在星期几」(1=周一…7=周日,逗号分隔,留空=每天)。编辑器里还有「**本仓库业务背景**」(多行,上限同全局 20000 字)与「**冷启动回溯提交数**」(留空 = 跟随全局那 10;大仓库可填小一点,主分支合并多就填 ≥2)。**凭据明文回显**在编辑器的输入框里(可直接核对/修改;清空保存 = 保留原值)。编辑器里的「**测试连接**」按当前填的值直接验(不必先保存),表格行里的「测试」结果以浮层提示。**分支是一个可输入 + 可点选的下拉**:直接手输任意分支名,或点「**拉取分支**」把远端分支列出来点选(点 ▼ 或聚焦输入框展开、输入即过滤、Esc 收起)。行里的「**复制**」把同一条配置克隆成新条目(name 加「副本」,push 自动评审默认关以免与原条目双触发)—— 同仓库多分支监控就复制几份再各改分支。同一张编辑器里还有「**负责这个仓库的成员**」勾选表 —— 列在里面的人才能触发这个仓库,并在自己的「我的用量」页看到它的评审结果。

**高级参数**（默认折叠）：单任务并发(4)/单任务超时(30 分)/**探索深度(high)/单次 token 预算(800 万)/自动续评轮数(2,0=关闭,钳位 0~10)/单请求超时(0=不下发,秒)**/全局并发任务(2)/记录保留天数(90)/每仓库保留运行数(50)/单仓库磁盘上限(2048MB)/**当日 token 预算(5000 万,0=不限,所有仓库合计)**/**冷启动回溯提交数(10,钳位 1~500)**/结果推送(每次/仅失败/不推送)/排除路径/OCR 可执行文件(留空=PATH)/是否保存意见里的代码片段(默认保存)。判定逻辑与边界见[代码评审](code-review.md)的「预算与守卫」。

⚠️ **单次预算撞顶的后果是「部分完成」,不是「失败」**:已经评出来的意见照常保留(引擎退出码仍是 0),网关随即**自动续评**——用**同一个引擎会话**只补没评到的部分(已评的复用、不重复付费),最多续「**自动续评轮数**」轮(默认 `2`,填 `0` 关闭)。续评也补不完时(撞轮数上限 / 当日预算已尽 / 这一轮没有任何新增进展)才把「部分完成」留给运行列表与详情,标出「只评了 10/39」并写明原因;残留的文件**不会在下次评审里自动补**(游标照常推进),补救办法是**调高单次预算或续评轮数 + 用「按范围补评」重评没评到的那段** —— 详见[单次预算撞顶:部分完成](code-review.md#单次预算撞顶部分完成)。

> ⚠️ **升级提醒**：本次把「单次 token 预算」的**代码默认值**从 200 万改成了 800 万、「当日 token 预算」从 `0`(不限)改成了 5000 万。并新增「**自动续评轮数**」(默认 `2`)、「**单请求超时(秒)**」(默认 `0` = 不下发)。默认值只对**新建**的配置生效 —— **已经部署过的环境，`config.json` 里存的仍是旧值，不会被自动改写**，需要在设置页手动改这两个输入框再保存（改不改都不影响功能，只影响会不会被预算掐断）。⚠️ 但**新增键在老配置上会立刻按默认值生效**：`自动续评轮数` 缺省就是 `2`，即老环境一旦撞顶也会自动续评（这正是修复「大提交评不完」的本意）；不想要它就把输入框填 `0` 再保存。5000 万是**安全网不是配额规划**：粗算 ≈ 单次预算 × 一天真正会跑的仓库数，仓库多或 diff 大时按实际调小。

「**单请求超时(秒)**」下发给引擎的 `OCR_LLM_TIMEOUT`，管的是**单次 LLM 请求**（引擎默认 300 秒），和「单任务超时(分钟)」不是一回事：后者管整个任务的分钟预算。大 diff 时整组以 `LLM request timeout` 失败、而任务总时长还远没到时，调这个才有用（留空或 `0` = 不下发，行为与从前一致）。

「**探索深度**」= 引擎的 `--effort`：`high`（默认）允许更多轮次的读文件/检索，支撑标准要求的「沿调用链取证」；`low`/`medium` 更快更省，但取证轮次变少、更容易只凭直觉提意见。**这是「只出确证缺陷」的代价来源**，详见[统一评审标准](code-review.md#统一评审标准)。

「**冷启动回溯提交数**」的含义:一条分支**第一次**评审(或上次评到的提交已被 force push 改写)时,从分支末端往前回溯多少**步**作为评审起点。它是步数不是提交个数 —— 填 `1` 等于只看最新那一个提交,填 `2` 才会把最新那个合并提交**带进来**的内容算在内,所以主分支合并别的分支时想一起评必须 ≥2。默认 `10`;**可按仓库**在仓库编辑器里单独覆盖(该处留空 = 跟随全局)。值越大,冷启动那一次的评审量越大;仓库大就调小。完整口径(含 `to~N` 走第一父链的说明与数字示例)见[评审范围](code-review.md#评审范围增量口径)。

**成员与可见范围**（第五张卡片）：说明性卡片。**授权是按仓库给的** —— 去仓库的「编辑」里勾选成员,列在里面的人 = 能触发这个仓库 + 能在「我的用量」页看到它的评审结果;不在名单里的人既触发不了也看不到。超级用户(含评审账号)不受成员名单限制。成员从外部触发还要求该仓库打开「允许通过 API / MCP 触发」(每 Key 60 秒一次)。

**Webhook 自动评审**（第六张卡片）：回调地址(只读,复制到托管平台)、密钥(「生成」一键随机;留空 = 不修改,空 = 功能关闭)、防抖秒数(同一仓库窗口内多次 push 只评一次,默认 300,0 = 不防抖)。GitLab/Gitee 把密钥填进平台的 Token/密码框,GitHub 填进 Secret。同时要到每个仓库的「编辑」里勾「push 到该仓库时自动评审」才会真的触发。配置细节见[代码评审](code-review.md#webhook-自动评审push-即评审)。

**维护**（第七张卡片）：工作区占用 + 「立即清理」(按保留设置删历史,不动游标)、「清空评审数据」与「连工作区一起删」(需管理员密码,自动先备份 config 与数据库)。

「引擎」卡片上的「运行自检」逐项体检(引擎/方案/真实 Key/模型/端点/账号/工作区/每个仓库),不修改任何配置。

保存走独立接口 `/api/code-review/*`,不进通用设置表单。安全边界与完整手册见[代码评审](code-review.md)。
