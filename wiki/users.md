# 用户与配额管理

入口：设置页底部「**用户管理**」按钮。

## 虚拟 Key（用户）

用户管理视图分两层：**全局用户** + **每方案分配**。

### 全局用户

- **虚拟 Key**：形如 `jx-xxxx` 的成员凭证，创建后发给成员
- **名称**：成员在报表里显示的名字
- **失效时间**：到期的 Key 自动失效（适合临时外部协作者）
- **禁用**：一键停用，请求立即被拒

### 每方案分配

在具体方案下给用户分配：

- **真实 Key**：该成员在这个方案上游使用的凭证（如上游服务的 API Key），用于上游侧的用量归属；未分配真实 Key 的用户不计入方案卡片的用户数
- **个人配额**：该成员在此方案的每日额度
- **禁用**：单独禁用某成员对某方案的使用

### 只给成员配部分方案

成员**不必**在每个方案下都配真实 Key——只配他该用的那几个就行，没配的方案对他自动不可用，网关会**自动跳过**：

| 场景 | 行为 |
|---|---|
| 走默认入口（`/v1`、`/v1/responses`），组内部分方案没配他的 Key | 自动跳过没配的方案，落到他有 Key 的方案上，无需任何额外配置 |
| 默认入口的组头（第一顺位方案）没配他的 Key，但组内其他方案配了 | 同样放行——组头不是门槛，组里「有没有他能用的方案」才是 |
| 组里一个他能用的方案都没有 | 请求被拒（403）：`当前入口的方案组里没有你可用的方案，请联系管理员为你的 Key 分配至少一个组内方案` |
| 组内他能用的方案暂时全被限流/熔断 | 429：`当前方案组里暂时没有你可用的方案（你被授权的成员都被限流或熔断），请稍后重试` |
| Codex 启动时的模型探测（`/v1/models`） | 与请求同一口径：按组找第一个他能用的方案出模型目录；全组不可用时明确提示「方案组里没有你可用的方案」，而不是笼统的密钥错误 |
| 成员用 `/方案后缀` 直连某个没配 Key 的方案 | 403——后缀直连就是指定方案，没有「跳过」可言 |

> ⚠️ 网关**绝不会**把成员的虚拟 Key（`jx-` 开头）转发给上游。成员看到上游口吻的「API 密钥无效」，只可能是他直连了一个没配 Key 的方案后缀（网关本会直接拒绝），或该方案下配的真实 Key 在上游侧已失效；走默认入口不会出现「虚拟 Key 被拒」这种报错。

配额模型：**配额存在额度池上**——个人与池级限额、临时加量都按池生效（详见[配额与计费机制](mechanism-quota.md#额度池配额的唯一载体)）。限额 ≤0（个人与池都没设）= 不限制。

## 临时额度：三个操作到底改了什么

用户管理里的「**临时额度**」按钮，三个动作的精确语义（都写在「当日操作」里，键为池 + 用户 + 北京日期，**次日日期一变自动失效**）：

| 动作 | 精确语义 |
|---|---|
| 临时加量 | **设置/覆盖**当日加量值（不是累加！已加 1 万再加 5 千 = 变成 5 千）。生效后限额 = 基础限额 + 加量值。作用于**整个池**（同池其他方案一起生效） |
| 重置今日用量 | 记录当日已用计权量为**基线**，此后按「当日用量 − 基线」判定，配额回满。统计行不删，报表照常显示真实用量 |
| 撤销今日手工操作 | 删除当日该用户的全部手工痕迹（加量与基线一起清），回到系统自然状态 |

> ⚠️ **累加的例外**：签到奖励和加量申请发放是**累加**到当日加量上的，与手工加量共存。

成员侧会在「我的用量」页的配额提示条里看到临时加量标记。

## 签到与奖励

- 开关与参数在设置页「全局配置」的「签到与加量申请」区：默认奖励区间 **[10,000, 100,000]** token，随机数在闭区间内均匀抽取
- 成员每日在「我的用量」页签到，随机获得一笔 token 额度；**随机数只抽一次，用户可访问的每个额度池各加同一份**（不是每池独立抽）
- 连续天数（streak）纯展示、无奖励加成；未签时显示「今天还能保住的连续」
- 签到是**成员自助**的，替代一部分手工加量的沟通成本

## 加量申请（审批流）

1. 成员在「我的用量」页点「申请加量」，选**额度池**、填写理由（必填，≤200 字）提交；**提交不占每周次数**——只有管理员处理过的申请才计数
2. 规则：每北京日限提交 1 次（固定）；每周处理上限默认 **3**（可配 0–1000），周窗口 = 本周一 00:00（北京时间）；池不限量时拒绝申请
3. 管理员在设置页侧栏「**加量申请**」（有待处理时显示角标）里查看申请历史，通过 / 拒绝并可附备注（≤200 字）；提交时会即时推送到已配置的通知渠道
4. 「发放加量」= 给指定池发当日临时加量（**累加**式）并自动标记已处理；结果回写申请历史，成员侧可见

## 点数预算（按人周期，可选）

管理员在设置页侧栏「**点数预算**」里逐人开启。开启后，这个成员不再按「额度池的每日个人配额」判定，而是按自己的**周期点数预算**判定：

- **1 点 = 10,000 计费计权 token**；预算填整数点（0 ~ 10,000,000）。点数使用独立价目：方案点数倍率 × 用户系数 × 方案系数，和额度池倍率互不影响
- **周期**：每日 / 每周（周一 00:00 起）/ 每月（自然月 1 日 00:00 起），全部按北京时间
- **中途启用**可填生效日期，只从那天起算，之前的历史用量不扣
- **预算为 0 且启用 = 该成员所有请求被拒**；要暂停点数、回到旧配额，应把「启用」关掉，而不是填 0
- 点数模式下该成员在池里的**个人日配额被忽略**；池级日限额仍作为团队护栏
- 该成员的「签到」「申请加量」会返回「点数模式下请改预算」的提示；管理员直接在「点数预算」里调预算即可
- 成员在「我的用量 → 概览 → 请求方案」里按 **Anthropic / OpenAI** 分组选择；每组第一个「默认自动」按方案组调度走；成员也可手动指定首选，手动选择会覆盖自动调度组（不要求该方案当前在组内）；选中后请求只走该方案，不可用时直接报错并标红，不会自动切换。管理员可在「点数预算」页顶部关闭「允许成员自选方案」
- 只有方案表单里勾选「**支持点数计费**」的方案才会出现在成员的可选列表里；取消勾选后该方案不会被点数成员用到（不能自动路由、不能直连、不能设首选）
- 管理员可在「点数预算」表格里给每人设**用户计费系数**（0.10~10.00，默认 1.00）；它只乘点数，不乘额度池。方案侧的系数/点数倍率在方案表单里配

完整的周期公式、429 形态与边界见[配额与计费机制](mechanism-quota.md#点数预算模式可选)。

## 操作日志

设置页侧栏「操作日志」记录 admin / system / checkin / request 四类日志（含管理员改动、自动配额调整、签到、申请），保留最近 3000 条，出问题回溯用。
