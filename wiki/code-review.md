# 代码评审

系统把登记过的仓库拉到服务器本地,用 [open-code-review](https://open-codereview.ai)(阿里开源的 OCR CLI)做**行级代码评审**,结果进管理面板「代码评审」工作区,并可推送通知。评审消耗走本网关的**评审专用 Key** —— 也就是计入用量与配额,和日常使用同一套账。

> ⚠️ **这是本系统唯一会执行外部命令的功能**(`git` 与 `ocr`),因此**默认关闭**,只有管理员能配置,成员无法提交任意仓库地址。

## 前置依赖(装在哪台机器上)

| 依赖 | 要求 | 安装 |
|---|---|---|
| `git` | ≥ 2.41 | `apt install git` / `apk add git` |
| `@alibaba-group/open-code-review`(`ocr`) | 能跑 `ocr version` | `npm i -g @alibaba-group/open-code-review` |
| `openssh-client` | 仅 SSH 拉私有仓库时需要 | `apk add openssh-client` |

网关**不会自动安装** OCR:未检测到时会显示「未安装」与安装命令,由管理员自行处理。设置页左栏「代码评审」的「引擎」卡片顶部会显示探测结果(OCR 版本与 git 版本),下面的「运行自检」会连方案、账号、工作区、每个仓库一起体检。

## 三步启用(不需要填任何 API 信息)

系统本身就是 AI API 网关,评审只是「另一个经网关的调用方」—— 所以只需要选方案,不用配 Key/端点/协议:

1. **选方案**:设置页 → 左栏「代码评审」→「评审用哪个方案」下拉选一个已有方案(端点与协议由系统按该方案自动推导)
2. **一键创建评审账号**:点「创建评审账号」即可。系统生成 `jx-review-…` 专用账号并设为超级用户,运行期向所选方案**借用已有的真实 Key**(不需要你填);用量记在「代码评审」名下,便于对账
3. **加仓库白名单**:「＋添加仓库」填名称、来源(`remote` 填 `https://`/`ssh://`/`git@` 地址,`local` 填服务器上已有仓库的绝对路径)、分支(**可点「拉取分支」从仓库列出来选**);可选凭据/定时/在线触发
4. **给仓库指定成员**:在同一个编辑器里勾「负责这个仓库的成员」—— 列在里面的人才能触发它、并在自己的「我的用量」页看到它的结果

引擎参数(并发、超时、token 预算等)收在「高级参数」折叠区,默认值一般不用动。

**评审端点会钉住你选的方案**:系统按该方案推导出 `http://127.0.0.1:<端口>/<方案后缀>/v1` —— 带后缀才能确保评审**就跑在这个方案上**。不带后缀的 `/v1` 会被当成「默认入口」交给**方案组**去 failover,结果评审可能跑在你没选的方案上(实测踩过:设置里选「阶跃星辰」,实际跑在「火山引擎」→「DeepSeek」),而真实 Key 也是从胜出方案借的 —— 用量会记错人。自检里有「方案已钉住」与「模型可用」两项专门盯这件事:方案没有独立后缀、或所选模型不属于该方案时都会报红。

## Webhook 自动评审(push 即评审)

GitLab / GitHub / Gitee 有人 **push** 时,平台主动回调网关,自动入队评审 —— 秒级,不用等定时扫描。

**配置步骤**(设置页 → 左栏「代码评审」→「Webhook 自动评审」卡片):

1. 点「生成」得到一个密钥并保存。密钥会**明文回填**在输入框里,旁边的「复制」按钮一键复制(换新密钥再点一次「生成」并保存即可 —— 保存后记得同步更新托管平台里填的值,否则签名校验会失败)
2. 把卡片上显示的**回调地址**(`http(s)://<网关>/api/code-review/webhook`)与密钥填进托管平台:
   - **GitLab**:项目 → Settings → Webhooks → URL 填回调地址、Secret Token 填密钥、勾 Push events
   - **Gitee**:项目 → 管理 → WebHooks → URL 填回调地址、密码填密钥、勾 Push
   - **GitHub**:项目 → Settings → Webhooks → Payload URL 填回调地址、Secret 填密钥(平台会自动做 HMAC 签名)、勾 push
3. 在目标仓库的「编辑」里勾「**push 到该仓库时自动评审**」(默认关,一个仓库一个开关)

**触发条件(缺一不触发,均返回 2xx 但忽略)**:功能已启用 + 仓库在白名单且勾了 push 自动评审 + 推送的是该仓库配置的那条分支 + 不是删分支/打 tag。防抖窗口内(默认 300 秒,可配 0~3600)同一仓库只评一次;评审进行中来的 push 会与进行中的任务**合并**(评完那次就包含它)。当日 token 预算照常拦截。

💡 **同时监控多个分支**:把同一仓库 URL 在白名单里配**多条**,每条选一个分支、各勾各的「push 自动评审」—— 推哪个分支只触发配了那个分支的条目,互不干扰(手动触发则不用这么配,面板的分支下拉可以对任意分支按次评审)。表格行的「**复制**」按钮可以把一条配置克隆成新条目(凭据不复制、push 自动评审默认关),改个分支就能用。

**手动补发**:自动通知只在评审完成时发一次。管理面板评审详情(评出过意见的运行)里有「**发送给负责人**」按钮 —— 按同一套邮箱定向规则把这条的报告邮件再发一次,并在状态行提示实际发给了谁。适合负责人换邮箱后重发、或漏收时补发。

**安全模型**:全局一个密钥(验证回调确实来自你配过的平台 —— GitLab/Gitee 是静态 Token 头,GitHub 是 HMAC-SHA256 签名,比对都走常数时间比较)× URL 白名单(决定哪个仓库可被触发;地址按 host+path 归一化匹配,`git@` SSH 写法与 https 回调能互认,**端口不参与**比对 —— SSH 写法表达不了 https 端口)。密钥不匹配只记日志不写审计(该端点无登录可达,防刷)。

触发记录里「触发方式」显示为**推送**,并把**推送人**(平台载荷里的姓名与邮箱)记入运行;评出问题时按[邮箱定向规则](#评出问题后通知谁)通知(见下节)。

## 触发方式一览(含 Webhook)

| 方式 | 怎么用 | 说明 |
|---|---|---|
| 手动 | 管理面板 → 代码评审 → 选**仓库**与**分支** → 开始评审 | 分支可当场从列表里选(见下);同仓库已有任务在跑时返回同一个 runId(去重) |
| 定时 | 设置页给仓库配「固定间隔 / 每天定时」 | 每 60 秒扫描一次;按**北京时间**判定;到点且该仓库无进行中任务才入队 |
| Webhook | 平台 push 回调 `/api/code-review/webhook` | 全局密钥 + 仓库勾了「push 自动评审」+ 分支匹配;详见上一节 |
| CI | `curl -X POST /api/code-review/trigger` + 虚拟 Key | 该 Key 必须在**这个仓库的成员名单**里,且仓库开了「允许在线触发」 |
| MCP | agent 调用 `code_review_trigger` / `code_review_list` | 同上;不在任何仓库名单里的 Key,工具列表里**看不到**这两个工具 |

**「谁能触发哪个仓库」是按仓库给的**:每个仓库有自己的成员名单(设置页里点该仓库的「编辑」勾选)。不是每个人负责同一个仓库,所以没有「一次授权、全仓库通行」的全局名单。不带仓库名触发时,只会触发**该成员名下的**那些仓库。

## 定时评审怎么算到期

每 60 秒扫一遍所有**启用**的仓库,按**北京时间**判定(时区固定 UTC+8,不跟随服务器本地时区):

```text
关闭          : 永不自动触发
固定间隔      : 上次运行距今 ≥ 间隔小时数 → 触发(从未跑过 = 立即触发)
每天定时 + 星期: 若填了星期,今天不在其中 → 不触发
                现在时刻 < 设定时刻              → 不触发
                今天已经跑过(手动也算)          → 不触发
                否则 → 触发
```

| 参数 | 默认 | 取值范围 | 说明 |
|---|---|---|---|
| 定时评审 | 关闭 | 关闭 / 固定间隔 / 每天定时 | 每仓库独立设置 |
| 间隔(小时) | 6 | 1 ~ 168 | 只看「距上次运行」,不挑时段 |
| 每天时刻 | `03:00` | `HH:MM` | 北京时间;格式非法时按 `03:00` 处理 |
| 只在星期几 | 空 | `1`~`7`(1=周一)逗号分隔 | 留空 = 每天;仅「每天定时」生效 |

⚠️ 注意:

- **「上次运行」包含手动与 API 触发** —— 手动跑过一次,当天的定时就不会再跑;间隔模式也会因此顺延
- **失败也会写「上次运行」**,不会每 60 秒重试失败任务;要看失败原因请用「结果推送」或运行列表
- **同一仓库永远串行**:排队中或运行中的仓库会被跳过,等它结束后的下一次扫描再判
- 清空评审数据会连游标与「上次运行」一起抹掉 → 定时仓库会立刻重新到期(相当于重新开始)
- **改了仓库的默认分支 = 换了一条线**:新分支没有游标,下一次评它就是**冷启动回溯**(最近 N 个提交)。定时的到期判定看的是「这个仓库**所有分支**里最近一次运行」(避免按次评完分支又被定时器马上重跑一轮),所以改分支不会让定时器立刻触发 —— 但换分支后第一次评审的量会明显变大

## 评出问题后通知谁

评审**发现了意见**时(0 条意见不打扰人),先做一步**邮箱定向**:

1. 拿这条提交的**推送人邮箱**(webhook 载荷带来,最贴近「该负责的人」)去匹配系统成员在「我的用量 → 通知设置」里填的**收件邮箱**(精确匹配、不区分大小写);
2. 推送人没匹配上,再拿**提交作者邮箱**(`git log -1 --format=%ae`)试一次;
3. **匹配到成员** → 只通知这**一个人**,走他自己配的渠道(飞书/钉钉/企微/Server酱/Bark/邮箱),**不再发给仓库全员**;
4. **两都没匹配上** → 回退老行为,两条去向并存:

| 去向 | 发给谁 | 需要什么 |
|---|---|---|
| **提交人 / 推送人** | 两者的邮箱直发(同一邮箱只发一封)—— 哪怕不是网关成员 | 管理员在「通知设置」里配好 SMTP |
| **仓库成员** | 该仓库成员名单里的人,走**他们各自**在「我的用量 → 通知设置」里配的渠道(飞书/钉钉/企微/Server酱/Bark/邮箱) | 成员自己配渠道;邮箱还需管理员配 SMTP |

**邮件正文 = 完整评审报告**(与管理面板「导出报告」同一份 HTML,含概要、被评文件清单、按文件分组的全部意见与建议改法);邮件客户端不渲染 HTML 时自动降级为纯文本摘要(前 5 条意见)。报告超过 **1.5MB** 时也降级纯文本并记一条日志 —— 超大附件会被 SMTP 拒收。飞书/钉钉等 IM 渠道仍发纯文本摘要。

**输出语言默认中文**：评审意见正文与推理过程都用简体中文。OCR 引擎自身默认 English，网关每次运行前会把 `language` 写进它的隔离配置（拼成 `Always respond in Simplified Chinese.` 注入全部系统提示）。想换语言：`config.json` 的 `codeReview.language` 填语言名（如 `"English"`、`"日本語"`）——**该项无界面控件，只能在 config.json 手改**，且保存设置不会把它重置（属保留字段白名单）。只影响新评审，历史记录不变。

**版式(终端代码风)**:深色抬头(`[代码评审] 仓库 #id · N findings` + 分支/区间/时间),元信息用等宽字体逐行对齐(status/files/tools/author/model/tokens/elapsed),行号写成 `@@ L42-58 @@`,改前/改后直接在同一个块里排成 `-` / `+` 两色(与 git diff 同观感),模型的推理过程收在「推理过程」折叠里。同一份 HTML 既是邮件正文也是「导出报告」,所以两边观感一致;全部用 table 布局 + 内联样式,不引用任何外部资源(图片/外链字体/外链样式),Gmail / Outlook / 阿里企业邮箱都能正确渲染。**普通通知(网关告警/恢复、产出告警)的邮件不用这套版式**,见下。

两个开关(高级参数里,默认都开):`notifyCommitAuthor` 控制是否发提交人,`notifyMembers` 控制是否发仓库成员。**两个都关时,定向命中也不发**。它们与「结果推送」(`notifyOn`)是**两回事**:`notifyOn` 管的是**管理员自己**那几个渠道(飞书/钉钉/…),按「每次/仅失败/不推送」推系统事件。

⚠️ 边界情况:

- **匹配到的成员账号已停用 / 删除,或他自己关了「启用我的评审通知」** → 视同**没匹配到**,回退第 4 条的全员路径。备选方案「匹配即静默」(他关了通知就谁都不发)未被采用 —— 评审问题不该因为一个人关通知就没人收。
- 被评提交的作者取自**评审时那次 git log**;如果仓库是浅克隆或作者信息缺失,取不到就只试推送人邮箱,不会因此让评审失败。
- **没填邮箱的成员匹配不到** —— 所以评审功能启用后,成员进「我的用量」页会被要求先填邮箱(见[我的用量页](my-usage.md)的「评审邮箱门」)。

## 单条意见「不用处理」

评审出的问题不一定都要改。每一条意见下面都有「**不用处理**」按钮 —— 点它**必须填写理由**（≤500 字），提交后这条意见变成「不处理」态：

- **在哪点**：成员在「我的用量 → 代码评审 → 详情」；管理员在管理面板「代码评审 → 运行详情」。两边共享同一份状态，谁点都生效。
- **理由必填**：理由为空会直接拒绝（接口层也挡一道）。这条记录的价值全在理由里 —— 后来的人看到「为什么当时没改」比看到「有人点了忽略」有用得多。
- **记名留痕**：成员点击记本人名字，管理员代为标记记「管理员」（管理端是共享口令，要追来源 IP 看审计日志）；带处置时间。
- **可撤销**：再点「撤销」恢复为待处理，理由等记录一并清空。
- **与「已解决」是两回事**：不处理是**按单条意见**的处置（这条不需要改）；[已解决](#已解决状态)是**按整次运行**的收尾开关。两者独立 —— 一条运行里可以有几条「不处理」，同时整体还挂着「未解决」，等处理完再点已解决。
- **显示位置**：评审列表显示「N 条意见 · M 条不处理」；导出的报告/邮件里，被标记的意见下方会带一行「已标记不处理：<理由> — <谁> <时间>」（报告是导出时现渲染的，反映当下状态）。

## 已解决状态

每次评审(一条运行记录)有一个**已解决**开关,**按整条记录生效** —— 一次 push 评出的所有问题算一个整体:

- **谁能点**:成员在「我的用量 → 代码评审」的记录详情里点「标记已解决」;管理员在管理面板「代码评审」的运行详情里也能点(还能代成员撤销)。两边是**同一个状态**,谁点都生效。
- **什么时候能点**:运行已结束(完成/失败/超时等终结态)且**评出过意见**;0 条意见的记录没有这个概念。
- **不点就一直挂着未解决**:「我的用量」侧栏「代码评审」菜单的角标显示你名下**未解决**的运行数,点已解决减一,全部处理完归零。角标**不会**因为打开分区而清零(那是旧的「未读」口径,已废弃;打开分区只影响 MCP 查询的 `unseenOnly`)。
- **撤销**:再点一次「撤销已解决」恢复未解决,角标重新 +1。
- **谁点的、什么时候点的**:解决人**记名留痕** —— 列表与详情里已解决记录后面会显示「已解决 张嘉欣 10-01 14:30」。成员点击记的是**成员名**(按点击当时的名字快照,成员日后改名不回改历史);管理员代为标记记「管理员」(管理端是共享口令,没有逐人身份;要追到具体来源 IP 可查审计日志)。撤销后这条留痕一并清空。
- **同一仓库又来新 push** → 产生一条**新的**未解决运行,角标重新出现;旧的已解决记录不受影响。
- **可见性扩展**:被邮箱定向通知到的人(哪怕不是该仓库成员),也能在自己的「代码评审」页看到这条运行、点已解决 —— 看到、通知、解决对同一个人闭环。

## 统一评审标准

**所有仓库、所有分支、所有文件类型共用同一份标准。** 标准正文内置在代码里(`lib/review-standard/`)、随版本发布,设置页**只读**展示(左栏「代码评审」→「统一评审标准」卡片,**默认折叠**,版本号就在标题行,点标题展开看详情),每条运行记录、导出报告与通知邮件里都带**这次用的是哪一版**。

### 标准由哪几段组成

| 段 | 管哪些文件 |
|---|---|
| **通用** | **所有**送审文件 —— 每份文件拿到的正文都以它开头 |
| 后端 Java / JVM | `*.java`、`*.kt`、`*.kts`、`pom.xml`、`*Mapper.xml` / `*Dao.xml` |
| 前端 | `*.ts` `*.tsx` `*.js` `*.jsx` `*.mjs` `*.cjs` `*.vue` |
| Go | `*.go` |
| Python | `*.py` `*.pyi` `*.ipynb` |
| 兜底 | 上面都没命中的(SQL / 配置 / 脚本 / 其他) |

**一个文件实际拿到的正文 = 通用段 + 它那一类的技术栈段**(编译时拼成一份自包含文本)。之所以要拼:引擎的规则是**首个匹配的 glob 生效、命中即不再叠加**,不拼的话通用段就管不到 Java/Vue 这些文件。设置页的标准卡片里可以逐段展开看正文。

### 哪条规则命中(`--rule` 的匹配顺序)

```text
1. **/pom.xml                        → 后端 Java / JVM 段
2. **/*{mapper,dao}*.xml             → 后端 Java / JVM 段
3. **/*.{java,kt,kts}                → 后端 Java / JVM 段
4. **/*.{ts,tsx,js,jsx,mjs,cjs,vue}  → 前端段
5. **/*.go                           → Go 段
6. **/*.{py,pyi,ipynb}               → Python 段
7. **/*                             → 兜底段   ← 必须是最后一条
```

- **首条匹配即生效**,后面的规则不再看。所以具体类型必须排在前面,`**/*` 兜底必须**是最后一条** —— 顺序错一条就会静默把整类文件送进错的标准里,因此加载时有**硬校验**:兜底不在最后一条、段文件缺失或为空,评审会**直接失败并写明原因**,不会退回「没有标准」凑合评
- 举几个例子:`src/main/java/com/x/Foo.java` → Java 段;`src/main/resources/mapper/UserMapper.xml` → Java 段;`front/src/App.vue` → 前端段;`db/schema.sql`、`conf/app.yml`、`Dockerfile` → 兜底段
- ⚠️ **`.vue` 只有我们这一份标准覆盖**:OCR 引擎自带的清单里根本没有 `.vue` 的条目(实测 `ocr rules check` 只认 `**/*.{ts,tsx,js,jsx,mjs,cjs}`),所以 Vue 文件的检查口径全部来自我们的前端段
- 匹配关系是 glob(支持 `{a,b}` 花括号展开),`**/` 表示任意层级目录;大写后缀同样命中(实测 `Foo.JAVA`、`App.VUE` 都进对应段)

### 和引擎自带检查清单的关系

每条规则都带 `merge_system_rule: true`:OCR **自带的**分语言检查清单(它自己那套 `rule_docs/<语言>.md`)会与我们的标准**同时生效**,而不是被我们覆盖掉。理由很实在 —— 引擎清单会随版本更新,照抄一份到我们这里必然漏抄,合并则两边都留。

实测合并后的文本顺序是:**引擎自带清单 → 我们的通用段 → 该技术栈段**(用 `ocr rules check --rule <标准文件> <路径>` 可以自己验,需要在一个 git 仓库里跑)。冲突时以我们为准:通用段里明确写了两条 —— ①引擎预扫描给出的「焦点项」只有在属于下面七类确证缺陷时才允许报;②引擎清单里若有风格/命名类条目,一律忽略。

### 只出「确证缺陷」:七类 + 禁止清单

允许输出的问题**只有**七类,不在这七类里的一律不报:

| # | 类别 | 典型 |
|---|---|---|
| 1 | 逻辑错误 | 分支写反、边界/越界、短路顺序不符原意、条件恒真恒假、`switch` 漏 `break`、不可达代码 |
| 2 | 空值与异常路径 | 未判空就解引用、异常被吞掉导致失败静默、异常路径下资源未释放 |
| 3 | 并发与幂等 | 先检查后使用、多步操作缺原子性、非线程安全容器被并发写、重复提交未去重 |
| 4 | 资金与数据一致性 | 金额/券/积分/库存/余额算错、事务边界不对、该回滚没回滚、状态机非法跳转 |
| 5 | 安全 | 越权、注入(SQL/命令/模板)、密钥明文、敏感信息进日志或响应 |
| 6 | 资源泄漏 | 连接/文件/流/定时器/事件监听/订阅未关闭或未解绑 |
| 7 | 明确性能缺陷 | 循环内查库或发请求、N+1、无界查询或无界循环 |

**明确不提的**(引擎清单里若也列了同样条目,以标准为准忽略):拼写、命名、格式、缩进、注释措辞、日志文案;已注释掉的代码块、声明未使用的变量、未使用的 import;「建议抽取方法 / 换设计模式 / 加单元测试 / 加日志 / 加注释」;「这样写更优雅/更简洁/可读性更好」;语言惯用法差异、依赖升级建议;`.md` 文档的措辞排版。

**每条意见必须给齐四件证据,缺一条就不许提:**

| 要件 | 要求 |
|---|---|
| 位置 | 具体文件与行号,且落在**本次改动新增/修改**的行上 |
| 触发条件 | 什么输入、什么时序、什么数据状态会出问题(别人能照着复现) |
| 具体后果 | 资损 / 数据错乱 / 越权 / 崩溃 / 泄漏 —— **写不出后果的不是缺陷** |
| 证据 | 实际读到的上下游代码位置(`文件:行号`),证明不是在猜 |

一句话口径:**推不出「触发条件 + 后果」的,就是还没查清 —— 不提。宁可漏报,不可误报。**

### 业务语义:必须沿调用链取证

代码承载业务,一个方法往往被很多地方共用。改动只要落在**金额、退款、优惠券、余额、库存、状态流转、幂等键、权限判定、租户隔离**这些路径上,标准要求:

```text
1. 先用 code_search 找到上游调用方、用 file_read 读到下游实现
   → 确认「谁调用它、它又调用了谁」
2. 意见里写清对整条链路的影响
   → 上游传入的值域是否变了 / 下游依赖的约定是否被破坏 / 失败时谁回滚补偿
3. 只改了一个方法、上下游没跟着改 → 这本身就是最高优先级的缺陷,必须报
4. 只评本次改动新增/修改的行;未改动的代码只用于取证,不得建议改动它
```

⚠️ 只要有一条关键的上下游关系没读到,就算「未确证」,不提。

### 机械兜底:没有推理过程的意见会被丢掉

标准里要求「每条意见写清取证过程」,但要求不等于做到 —— 所以解析报告时有一道**纯本地、零 token** 的校验:

```text
逐条意见检查:
  ① 问题描述(content)非空
  ② 推理(thinking)去掉空白后 ≥ 80 字符     ← 一段真正的调用链取证不可能只有一句话
两条都满足才保留;否则丢弃,并计入本次运行的「丢弃意见」条数
```

被丢掉的条数会**写进运行记录并在详情页显示**(示例:`丢弃 3 条(缺取证推理)`),不静默吞掉 —— 否则「这版标准更严了」和「评审没跑完」在界面上长得一模一样。

> 安全阀:若一轮报告里**所有**意见都没有推理(≥2 条且全部被丢),判定为「引擎这一版不填该字段」而不是「全都在乱提」,此时不过滤、只记标记。宁可放过,也不因字段缺失把意见误杀成「没问题」。

### 业务背景:告诉评审「代码里看不出来」的规则

标准是**所有仓库共用**的,团队自己的业务约定另走**业务背景**——两级,可各自填,上限都是 **20000 字**:

| 级别 | 在哪填 | 典型内容 |
|---|---|---|
| 全局 | 设置页 → 代码评审 → 「业务背景」 | 团队级约定:「所有资金变动都走 X 通道」「退款必须先冻结再扣减」 |
| 本仓库 | 仓库编辑器 → 「业务背景」 | 这个服务的口径:租户隔离字段、幂等键怎么取、状态机有哪些合法流转 |

注入时按 **全局 → 空行 → 本仓库** 的顺序拼成一份 Markdown,用 `--background-file` 交给引擎(落盘在工作区 `inputs/` 下、文件名带内容 hash,陈旧文件 1 小时后自动清理;不写进仓库副本,免得污染 git 工作树)。

- 写「代码里读不出来的规则」:为什么这么算、谁必须调谁、失败时怎么补偿
- ❌ 别写:通用编码规范(那是标准的事,重复一遍只是浪费 prompt)、密钥/令牌、个人隐私信息
- 留空 = 这一段背景不注入,评审仍按标准跑
- ⚠️ 业务背景**不算进标准版本号** —— `standard_version` 只跟标准正文有关。改了背景不会让版本号变,想比对两次运行的口径差异时,记得背景也是变量

### 探索深度(`--effort`)

| 档位 | 含义 | 什么时候用 |
|---|---|---|
| `low` | 少量工具轮次,快而浅 | 只想扫一眼明显问题 |
| `medium` | 引擎默认 | — |
| **`high`(本系统默认)** | 允许更多轮次的读文件/检索,支持沿调用链取证 | 默认就用它 |

标准要求「每条意见写出上下游证据」,**取证是要花轮次的** —— 轮次不够时模型只能凭直觉猜,那正是标准要消灭的东西。所以本系统默认 `high`。代价是**更慢更贵**:实测单次评审到过 1,876,001 token / 7 分 49 秒的量级,所以「单次 token 预算」的默认值也一并提到了 8,000,000(见下节)。

### 哪些文件会被送审(实测)

送审范围由**引擎**决定,不是我们配的。用零成本的 `ocr review --preview`(只选文件、不跑模型)实测的结果:

| 情况 | 内容 |
|---|---|
| 送审 | `*.java` `*.kt` `*.kts` `*.go` `*.py` `*.pyi` `*.ipynb` `*.ts` `*.tsx` `*.js` `*.jsx` `*.mjs` `*.cjs` `*.vue` `*.rs` `*.c` `*.cc` `*.cpp` `*.cxx` `*.h` `*.hpp` `*.hxx` `*.cs` `*.php` `*.rb` `*.swift` `*.scala` `*.dart` `*.lua` `*.ex` `*.exs` `*.erl` `*.hs` `*.ml` `*.fs` `*.vb` `*.pl` `*.jl` `*.m` `*.R` `*.sql` `*.yml` `*.yaml` `*.json` `*.xml` `*.properties` `*.toml` `*.ini` `*.env`(仅 `x.env` 这种带前缀文件名的;`.env` 本体见「密级排除」行) `*.sh` `*.bash` `*.gradle` `*.html` `*.css` `*.scss` `*.less` `*.svelte` `*.astro` `*.ets` `*.ftl` `*.ftlh` `*.hbs` `*.mustache` `*.pug` `*.nix` `*.bicep` `*.tf` `*.tfvars` `*.hcl` `*.proto` `*.gql` `*.graphql` `*.prisma` `*.po` `*.pot` `*.nim` `*.nimble` |

- ⚠️ 后缀**大小写不敏感**:`Foo.JAVA` 与 `Foo.java` 等价、`App.VUE` 与 `App.vue` 等价 —— 送审与「命中哪一段」两边都看不出差别(实测)
- ⚠️ 送审 ≠ 有意见:兜底段对 `.md` 这类文件本来就不评措辞,引擎层又先按后缀挡了一层 —— 所以**文档类文件根本不会进评审**,不用担心它给你提排版意见
- ⚠️ 需要额外屏蔽的文件(生成物、fixtures)用高级参数里的「**排除路径**」,与引擎自身的名单是**合并**关系

### 版本号怎么用

标准编译产物做 sha256,取前 12 位十六进制 —— 形如 `v4246b9e1a629`。它出现在**四处**:管理面板运行详情、成员页「我的用量」运行详情、导出报告(`standard:` 一行)、通知邮件(`评审标准:v…` 一行)。**运行列表里不显示**(避免每行都挂一长串噪声)—— 要比对两次运行的口径,点进详情看。设置页的标准卡片上还能看到完整 64 位指纹。

```text
两版标准之间意见条数的变化,只有同版本号才可直接比较
—— 换版本前后,「意见变少了」既可能是代码变干净了,也可能是标准收紧了
```

**怎么改标准**:改 `lib/review-standard/` 下的段正文(或 `manifest.json` 的段映射)→ 跑一遍代码评审的测试 → 发版重启 → 设置页点标准卡片上的「**重新载入**」,版本号与正文即刻更新。界面**不提供编辑**——这是刻意的取舍:标准能评审、能回滚,改动留在版本历史里。

⚠️ 标准坏掉时(段文件被删空、兜底规则不在最后一条),设置页标准卡片会标红并摊开具体错误,而**这期间发起的评审会直接失败并写明原因**,不会退回「没有标准」凑合评 —— 「用了哪版标准」这件事不允许含糊。

## 预算与守卫

| 参数(高级参数里) | 默认 | 范围 | 作用 |
|---|---|---|---|
| 当日 token 预算 | `50000000` | 0 ~ 20 亿(0 = 不限) | **所有仓库合计**,按北京时间当日 00:00 起算。**只闸自动/定时触发**,手动、CI、MCP 触发照常受理 |
| 单仓库磁盘上限(MB) | `2048` | 64 ~ 102400 | 工作区里该仓库目录超限 → 拒绝入队并推送通知 |
| 单次 token 预算 | `8000000` | 0 ~ 2 亿 | 单次评审交给 OCR 的预算参数。`high` 档 + 沿调用链取证的量级实测到过 1,876,001。**撞到它是「部分完成」而不是「失败」** —— 见[单次预算撞顶:部分完成](#单次预算撞顶部分完成);撞顶后网关会**自动续评**,见[撞顶后自动续评](#撞顶后自动续评默认开) |
| 自动续评轮数 | `2` | 0 ~ 10(0 = 关闭) | 撞顶后最多再用**同一会话**续几轮。单次运行的最坏 token 上限 = `(1 + 该值) × 单次 token 预算` |
| 单请求超时(秒) | `0` | 0 ~ 3600(0 = 不下发) | 下发给引擎的 `OCR_LLM_TIMEOUT`,**管单次 LLM 请求**(引擎默认 300 秒)。和「单任务超时(分钟)」不是一回事:后者管整个任务的分钟预算,调它治不了单次请求超时 |
| 探索深度(effort) | `high` | low / medium / high | 见[统一评审标准](#统一评审标准);调低会更快更省,但取证轮次变少 |
| 冷启动回溯提交数 | `10` | 1 ~ 500 | 一条分支**第一次**评审(或游标失效)时往前回溯多少步作为起点;可在仓库编辑器里按仓库覆盖(留空 = 跟随全局)。填 `1` = 只评最新一个提交,合并内容要一起评需 ≥2 —— 见[评审范围](#评审范围增量口径) |
| 记录保留天数 | `90` | 1 ~ 3650 | 超过的运行记录被自动清理 |
| 每仓库保留运行数 | `50` | 1 ~ 1000 | 每仓库只留最新 N 条(与天数取「或」,谁先命中删谁) |
| 全局并发任务 | `2` | 1 ~ 4 | 同时在跑的评审数上限 |
| 单任务超时(分钟) | `30` | 2 ~ 240 | 超时判 `超时`,游标不推进 |
| 结果推送 | 每次推送 | 每次 / 仅失败 / 不推送 | 走「通知设置」里已配好的渠道。⚠️「**部分完成**」按**失败**类推(选了「仅失败时」也会推) |

预算用尽的两种表现:

```text
手动 / API / MCP 触发 → 仍然受理,但落一条状态为「已跳过」的记录(说明为什么没跑)
定时扫描            → 静默跳过,不写记录(否则 60 秒一条会把表刷爆),每天只在日志里提示一次
```

### 单次预算撞顶:部分完成

「单次 token 预算」管的是**一次运行**。OCR 引擎在**每一轮 LLM 请求之前**检查:已用量 + 下一组的预估用量超过预算,它就**停止派发后续分组**,把已经评完的部分照常输出,**退出码仍然是 0**。网关把这种结局记成独立的终态 **「部分完成」**(引擎原话:`Review partially complete: N finding(s); X of Y selected item(s) failed.`)。

它不是失败 —— 已经评出来的意见一条不少,只是**没评完**:

```text
选取 39 个文件 → 评了 10 个 → 29 个没评(原因:超出单次 token 预算)
引擎那句「为什么」自带算式(实测原样透出):
  used 2056288 tokens + group estimate 99304 = projected 2155592 exceeds budget 2000000

结论不再写「未发现问题」,而是:
  增量评审只完成了一部分:选取 39 个文件,评了 10 个,29 个未评审(超出单次 token 预算);已评的 10 个未发现问题
  ↑ 未评原因只有一种时直接给中文名;多种原因时写成 (24 个超出单次 token 预算 / 5 个<其它分类>) —— 认不出的分类原样透出,不吞
```

### 撞顶后自动续评(默认开)

撞顶不再是终点:网关会用**同一个引擎会话**再跑一轮,只补评没评到的部分。

```text
第 1 轮:选取 39 个文件 → 评了 10 个 → 撞单次预算,停止派发(会话 9bd30e2b-…)
        └ 网关从报告顶层读出 session_id,把已评完的 10 个记为「复用」
第 2 轮:--resume 9bd30e2b-…,只对剩下 29 个重新分组、继续评(同一会话)
        └ 已评的 10 个不再付费重评(引擎事件 review_item_reused)

单次运行最多 = (1 + 自动续评轮数) 轮,每轮各有一份「单次 token 预算」
```

**参数**(设置页 → 代码评审 → 高级参数):

| 参数 | 默认 | 范围 | 作用 |
|---|---|---|---|
| 自动续评轮数 | `2` | 0 ~ 10(0 = 关闭) | 撞顶后最多再续几轮。单次运行的最坏 token 上限 = `(1 + 该值) × 单次 token 预算` |
| 单请求超时(秒) | `0` | 0 ~ 3600(0 = 不下发) | 下发给引擎的 `OCR_LLM_TIMEOUT`。**管单次 LLM 请求**(引擎默认 300 秒)——大 diff 常见整组以 `LLM request timeout` 失败,而调「单任务超时(分钟)」治不了它 |

**什么时候停**(四道刹车,任一命中即停,原因写进结论):

```text
① 评完了(coverage 里没有未评项)→ 正常收尾
② 已到轮数上限(1 + 自动续评轮数)
③ 续评没有新增进展:非预算原因失败(超时等)且这一轮一个文件都没多评 → 立刻停,不空转
④ 当日 token 预算已用尽 → 停(续评也逃不过这道闸)
```

**结论里会写明**,例如:

```text
增量评审完成:选取 39 个文件,提出 12 条意见;自动续评 1 轮(复用 10 项已评结果)
增量评审只完成了一部分:选取 39 个文件,评了 30 个,9 个未评审(超出单次 token 预算);已评的 30 个提出 12 条意见;自动续评 2 轮(复用 10 项已评结果,已达续评轮数上限)
```

**每次运行都会留下「这次带没带续评」的证据**(三处,启动一行、真续评一行、详情一行):

```text
日志(起跑,每次都有):  [代码评审] run#9 自动续评最多 2 轮(0=关闭),单请求超时 0 秒
日志(真去续评):        [代码评审] run#9 第 1 轮未评完(未评 29 项),自动续评(session 9bd30e2b-…)
详情事实表(没评全时):  自动续评  已续评 1 轮（复用 10 项已评结果）
```

⚠️ 这三处的用途是**免除猜测**:看到「部分完成」却没有任何续评字样时,起跑那行会直接告诉你这次运行的计划是几轮 —— 若计划是 2 轮而详情写「未触发（已配置上限 2 轮）」,说明**跑这次评审的还不是带续评的版本**(部署后没重启进程),而不是「续评没生效」。

要点:

- **续评只补未评部分**:已评完的部分被引擎复用,不重复付费 —— 比手工「按范围补评」省,后者会把已评过的文件再评一遍。
- **token 按轮累加**记在**同一条**运行记录里。当日预算是所有运行记录 token 的**求和**,只记最后一轮会让那道安全闸漏算。
- **覆盖率与意见是累计的**:续评报告会把被复用条目的意见一起带回来,所以最终那条记录本身就是全部结论。
- 续评**只发生在同一次运行内部**(会话 id 取自本轮报告);运行期间标准身份不会变,所以不会出现「续到一个标准已经换掉的会话」。引擎拒绝续评时(会话丢了等),网关保留已经评出的那一轮并写明原因,不会把已花的 token 一起丢掉。
- ⚠️ **填 0 关掉它时,行为与从前一字不差**:一轮就收,结论里也不会多出续评字样。

### 六个展示面

| 位置 | 显示什么 |
|---|---|
| 运行列表行 | 状态标**部分完成**(深橙),文件列写成 `10/39`;没有覆盖率数据的老记录,行上标一个「覆盖不全,详见详情」 |
| 详情弹层 | 事实表多一行**覆盖率**(`10/39 个文件(超出单次 token 预算)`),外加一条醒目提示与**未评文件清单**、引擎那句算式与引擎版本;**绿框「未发现问题」不再出现**,换成灰底「未评完,结论不完整」;紧接着还有一行**自动续评**(见下) |
| 成员页「我的用量」 | 同一套口径:列表行 `X/Y`、详情副标题给覆盖率、0 意见时不再给绿字结论(见[我的用量页](my-usage.md#代码评审)) |
| 报告 / 通知邮件 | 元信息写成「选取 39 / 完成 10」,页脚「已评审文件」只列**真评过**的那 10 个(从前那个 `reviewed files (39)` 对没评完的运行是假话) |
| 服务日志 | 起跑时先写一行本次的续评计划:`[代码评审] run#9 自动续评最多 2 轮(0=关闭),单请求超时 0 秒`;**真去续评**时再写 `[代码评审] run#9 第 1 轮未评完(未评 29 项),自动续评(session 9bd30e2b-…)`;收尾写 `[代码评审] run#9 charging-pile: partial, 0 条意见, 2323293 token, 覆盖 10/39(29 未评审: budget) 覆盖不全`。⚠️ 排查「为什么没续评」先看这三行:起跑那行说明**这次运行到底带没带续评** |
| 结果推送 | 「部分完成」按**失败**类推给管理员 —— 「结果推送」选「仅失败时」也会推。成员渠道仍是「有意见才通知」,不变 |
| 结论那句话 | 续评过就在结尾补一句:`;自动续评 2 轮(复用 10 项已评结果,已达续评轮数上限)`,一眼看出这次是补过的、以及为什么停在半路(未续评 / 撞轮数上限 / 无新增进展 / 续评输出不可用 / 当日预算已尽) |
| 详情里的「自动续评」行 | 只在**没评全**时出现,回答「网关自己补过没有、为什么停下」。四种取值:`已续评 1 轮（复用 10 项已评结果）` / `已续评 3 轮（复用 10 项已评结果），已达续评轮数上限` / `已关闭（轮数 0），未评项不会自动补` / `未触发（已配置上限 2 轮）`。⚠️ **最后一种不该出现**:配置了轮数、又确实有未评项时,引擎一定会被再拉起一次 —— 若它出现,说明这次运行用的网关还不是带续评的版本 |

⚠️ **残留的未评项不会自动补评**:自动续评会在同一次运行里尽量补完,但触到轮数上限 / 当日预算 / 空转时仍会留下未评项。`partial` 属于**推进游标**的一类(见[游标什么时候推进](#游标什么时候推进)),下次评审从本次的 to 往后走。这是刻意的 —— 预算没变的话,不推进就变成死循环(每次重评都卡在同一处,照样烧满整份预算)。补救是**手动两步**:

```text
1. 把「单次 token 预算」或「自动续评轮数」调高(设置页 → 代码评审 → 高级参数;全局设置,影响所有仓库)
   或者把「探索深度」降到 medium / low(取证轮次变少,token 也少)
2. 用触发卡片下方的「按范围补评」把没评到的那段重评一次(补评不推进游标)
```

⚠️ **别把「部分完成」当成「连续失败」**:它不算失败,仓库的「连续失败次数」会被清零。想知道某个仓库是不是一直在撞预算,看运行列表的状态与 `X/Y`,别只看失败计数。

⚠️ **历史记录也看得到**:库里已经产生的「完成(有错误)」老记录(状态词表里没有 `partial` 的那个年代写下的),详情弹层会**按需读一次原始报告**把覆盖率现算出来并显示为「部分完成」;原始报告已被清理时退化为「覆盖不全(详情缺失)」,不报错、不改库。

## 维护与清空

设置页「代码评审」最下面的「维护」卡片:

| 操作 | 做什么 | 安全性 |
|---|---|---|
| 立即清理 | 按上面的保留设置删历史运行与报告文件,**不动游标** | 安全,随时可点;默认每天也会自动跑一次 |
| 删除单条运行 | 面板评审列表每行的「**删除**」按钮:删掉那一条运行记录,**连同它的全部意见与报告文件** | 破坏性且不可撤销:不要求二次密码,但会写审计日志;运行中的记录会拒绝删除(先在行上点「取消」) |
| 清空数据 | 统计 + 意见 + 游标全清,报告文件删除,**保留仓库定义与引擎配置** | 破坏性:需要**管理员密码**,且会自动先备份 `config.json` 与数据库 |
| 连工作区一起删 | 在「清空数据」基础上再删 `code-review-workspaces/`(拉下来的代码副本) | 同上;删掉只是下次评审要重新 clone |

⚠️ **删除单条运行会退还当日 token 预算**。当日用量是对运行表的**实时求和**,不是一个独立计数器 —— 删掉记录,今天就少算这些 token。这不是删除功能引入的新行为(「立即清理」一直如此),只是单条删除让它更容易被踩到,所以「删除」的确认对话框里直接写了这一条。

⚠️ **删除后仓库状态会退回上一条记录**:上次状态 / 上次时间 / 连续失败次数都按剩下的记录重算;若该仓库只剩这一条,卡片回到「未评审」。**游标不动** —— 删记录不等于要重评那段代码。

⚠️ 但有个连带效应要留意:失败记录本来就**没推进游标**,所以删掉「最新那条失败记录」之后,该仓库看起来就是「最近这段还没评过」。若它配了定时,下一轮到点会**真的重新评审**那段代码(不是空跑,会照常消耗额度)。

⚠️ **成员侧看不到失败记录**(见[我的用量](my-usage.md#代码评审))之后,「跑不起来」只剩两个信号:**管理员渠道的结果推送**、以及**本面板**。如果「通知设置」里 `notifier` 没启用,或「结果推送」选了「不推送」,**失败就只在本面板里躺着** —— 成员看不到、也不会有人来报修。评审连续挂几天却没人发现,通常就是这个组合造成的。

## 自检

设置页「运行自检」一次列出「为什么跑不起来」,逐项给结论与处理建议:

`OCR 引擎` · `git 版本` · `评审方案` · `方案真实 Key` · `模型` · `端点回环` · `方案已钉住` · `模型可用` · `评审账号` · `工作区可写` · `统一评审标准`(标准能否加载、当前版本号) · 每个仓库一条(上次运行时间、状态、定时期、是否已拉取、在线触发开关、连续失败次数)

只探测不修改配置。任一必填项不通过时整体结果为「未通过」,条目里的 `hint` 就是要做的事(例如方案没有真实 Key → 评审会 403)。

## 结果怎么看

面板顶部是**引擎状态条**(绿灯 + OCR / git 版本 + 工作区占用),下面是**触发卡片**:选仓库(可再选分支)→ 点「开始评审」,卡片下方还有一个「**按范围补评**」折叠块(见下文)。触发卡片下方一行小字讲清了增量口径:**每条分支各记一份游标**,首次评这条分支会回溯最近 N 个提交(默认 10,设置页可调),之后按「上次评到 → 现在 HEAD」的增量,不会整个仓库重跑;**合并带进来的多个提交属于同一段增量,会一起评**。

工作区列表每行是一条评审记录,左侧色条按状态着色:**绿**=成功、**墨绿(高亮)**=进行中(排队/同步/评审/解析)、**橙**=完成有警告/完成有错误、**深橙**=部分完成、**红**=失败/超时、灰=已跳过。行内含 `时间 | 范围(来源标签 + 短 SHA) | 状态 | 文件数 | 意见数 | token | 耗时`,覆盖到多个提交时还会带一段 `· 提交 N`;非手动的触发方式(schedule/api)会额外标一个小标签。被机械兜底丢掉过意见的运行会多一段 `· 丢弃 N 条(缺取证推理)`(见[统一评审标准](#统一评审标准),这类运行不该被误读成「这次代码很干净」)。**没评完的运行**文件列写成 `10/39`(已评/选取),并在后面跟一个「覆盖不全,详见详情」;老记录(库里只有状态、没有覆盖率数)也会靠引擎警告里的「预算」字样标出同样的「覆盖不全,详见详情」标记。

每行下面还有三样「证明它真干了活」的信息:一句**结论**(人话,见下)、**被评文件**的文件名(超过 3 个显示 `+N`)、以及失败时的错误摘要。运行列表上方有**搜索**(仓库名/结论/错误)与**状态过滤**,记录一页 15 条、可翻页。

点「**详情**」以**弹层**打开(不再堆在列表下面,信息再多也不用来回滚页面),弹层内含:

- 顶部一行摘要:范围(来源标签 + 短 SHA,如 `冷启动回溯 a1b2c3d4→e5f6a7b8`)、提交人、意见数、文件数、token、耗时;右上角「导出报告」
- **事实表**:结论、评审范围、**覆盖率**(只有没评完才出现,如 `10/39 个文件(29 个超出单次 token 预算)`)、**自动续评**(紧跟在覆盖率后面,同属「没评完」才显示,见[撞顶后自动续评](#撞顶后自动续评默认开))、**范围来源**(为什么是这一段的人话说明)、**覆盖提交**(本次区间内的提交总数)、提交人、模型、**评审标准**(这次用的标准版本,如 `v4246b9e1a629`;早于统一标准的旧记录显示「—(此记录早于统一标准)」)、**丢弃意见**(机械兜底丢掉的条数,只有 >0 才显示)、引擎动作(读了多少文件/检索多少次)、两个 token 口径、耗时
- **没评完时**:事实表下方多一条醒目提示(选了几个、评了几个、几个没评、为什么),带**未评文件清单**、引擎那句自带算式的原话与引擎版本;无意见时**不再给绿框**,换成灰底「未评完,结论不完整 —— 已评部分没有提出意见,这不等于『没有问题』」
- **引擎警告**:引擎在运行中记下的警告逐条列出(从前只在邮件里出现,面板上看不到)—— 撞预算就写在这里
- **本次覆盖的提交清单**(提交号 / 标题 / 作者 / 提交时间):默认展开到 12 条以内,更多则折叠。清单本身最多留最近 200 条,超出时标题会注明「清单只留最近 N 条」,而**总数仍是真实值** —— 合并带进来的提交在这里一眼可数
- **本次选取的文件清单**(0 意见也列出)—— ⚠️ 这是引擎**选中**要评的文件,不等于真评过的;哪些真评过看上面那条覆盖率
- **评审意见列表:带搜索(文件路径/问题内容)与分页,每页 20 条** —— 意见几百条时只渲染当前页,不卡;**本次一条意见都没有时,这块列表与搜索栏一起收起**,上面的事实表照常显示(0 意见的结论由事实表里的结论行给出)
- ⚠️ 事实表与意见列表是**两块独立的区域**:事实表(结论 / 覆盖率 / 警告 / 提交与文件清单)永远显示;从前两者挤在同一个容器里,意见列表一渲染就把事实表覆盖掉,0 意见的运行点开只剩一句「没有内容」—— 看着像「详情没有数据」
- 弹层支持点遮罩空白处或按 Esc 关闭

「我的用量」页的代码评审详情是同一套弹层(成员视角,无导出按钮),运行记录同样有搜索。

### 结论那句话怎么来的

`note` 由**网关**按已知事实生成(不是直接透出引擎的英文 message),所以「已跳过」一定会说清是哪种跳过:

| 情况 | 结论文案 |
|---|---|
| 增量评审有改动 | `增量评审完成:选取 N 个文件,提出 M 条意见`(M=0 时写作「未发现问题」) |
| 单提交评审 | `单提交评审完成:选取 N 个文件,…` |
| 按范围补评 | `补评完成:选取 N 个文件,…` |
| **没评完**(撞单次预算) | `增量评审只完成了一部分:选取 N 个文件,评了 M 个,K 个未评审(超出单次 token 预算);已评的 M 个未发现问题` —— ⚠️ **「未发现问题」只在已评范围内成立**,且绝不会单独出现 |
| 范围为空(游标已在 HEAD) | `自上次评审以来没有新提交(范围为空),本次无需评审` |
| 引擎没选中任何条目 | `没有可评审的改动(引擎未选中任何条目)` |
| 超出当日预算 | `超出当日 token 预算` |

⚠️ 「未发现问题」这句话的分量有个前提:**它只对已评过的文件有效**。运行没评完时(单次预算撞顶),结论会明写「已评的 M 个未发现问题」并把未评数写在前面;详情里的绿框也会让位给灰底提示 —— 一条没说「评了几个」的「未发现问题」是不可信的。

「冷启动回溯 / 游标失效回溯」也走增量口径,所以结论同样写作 `增量评审完成…` —— **为什么是这一段**看「范围来源」那一行的人话,例如:

- `这条分支首次评审:回溯最近 10 个提交`
- `上次评到的提交(1a2b3c4d)已不在当前历史里（历史被改写）,回退为最近 10 个提交`
- `手动按范围补评 1a2b3c4d→5e6f7a8b（不推进游标）`;若填的 from 不是 to 的祖先,还会补一句实际取净差异用的共同祖先

⚠️ **「已跳过」最常见的意思是「没有新提交」**,不是出错:评审是增量的,游标已停在 HEAD 时再点一次,范围就是空的 —— 此时引擎不会调用模型(实测 0 请求、0 token),只是记一条「无新提交」。想让它评点东西,先 push 新提交。

### 被评文件 / 引擎动作是什么

- **被评文件**来自引擎的 `groups`(它实际入选评审的文件路径),落库在 `files_json`,报告与详情都会列出。**即使 0 条意见也会列出**——这就是「它到底看了哪些文件」的直接证据。⚠️ 它列的是**选中**要评的文件;真评过的有几个,看[单次预算撞顶](#单次预算撞顶部分完成)
- **引擎动作**来自 `tool_calls`(读文件 / 代码检索的调用次数与失败数),落库在 `tool_calls_json`。它和「意见 0 条」合起来才能说明「读了、看了、没挑出问题」,而不是「啥也没干」

状态含义:`完成`(可能零意见)、`完成(有警告)`、`完成(有错误)`、**`部分完成`**(引擎撞到单次 token 预算,只评了一部分 —— 见[单次预算撞顶](#单次预算撞顶部分完成))、`失败`、`超时`、`已取消`、`已跳过`(无新提交 / 超当日预算 / 引擎未选中条目,看结论那句话)。

详情页右上角的「导出报告」会下载一份**自包含单文件 HTML**(`code-review-run-<id>.html`):内容全部转义、不引用任何外部资源,可以直接发群或存档。报告里同时标注本次运行的范围(**含来源标签**,如抬头那行 `main 冷启动回溯 1a2b3c4d5e → 6f7a8b9c0d · 2026-10-08 14:30:00 北京时间`)、分支/提交,以及元信息里的 `range`(非增量时才有)、**`standard:`(本次用的统一评审标准版本)**、`commits: N 个`、`covered commits (N)` 提交清单(逐条列提交号/标题/作者/北京时间)、两个 token 口径、警告列表与全部意见;有意见被机械兜底丢掉时会另起一行写明「另有 N 条」。非增量运行还会注明「不推进游标」。

⚠️ **没评完的运行,报告也不说假话**:元信息里的文件数写成「**选取 N 个 / 完成 M 个**」(从前写的是 `files : N reviewed`,而 N 是**选中**数 —— 对没评完的运行是假的),页脚「已评审文件」只列**真评过**的那 M 个,并另行写明「另有 K 个未评审(原因),下面的结论只覆盖已评部分」。通知邮件(评审发现问题的邮件)首部同样带一行 `评审标准:v…`,正文同一份 HTML;若这条运行没评完,邮件主题里也会带上「另有 K 个文件未评审」—— 收到意见的人必须知道这些意见只覆盖了一部分。

**token 归因有两个口径**,详情页与报告都同时给出:OCR 自报的 token(`summary`),以及**网关侧实证** —— 评审 Key 在 `users` 表的请求数与 token 在本次运行前后的差值。两者可能有偏差(OCR 一次评审会发多次 LLM 请求,无法一一对应到单次运行),以网关侧为准来对账。

## CI / MCP 触发接口

管理员之外,成员可以拿**自己的虚拟 Key** 触发评审 —— 这是个**写操作**,会消耗你所在方案的配额。

```bash
# 触发单个仓库(仓库名或 8 位 id 都可以)
curl -X POST http://<网关>/api/code-review/trigger \
  -H "Authorization: Bearer jx-xxxx" -H "Content-Type: application/json" \
  -d '{"repo":"主仓库"}'

# 不带 repo = 触发**你名下**的全部可触发仓库(不是所有仓库)
curl -X POST http://<网关>/api/code-review/trigger -H "Authorization: Bearer jx-xxxx" -d '{}'
```

| 状态码 | 含义 |
|---|---|
| `202` | 已受理,返回 `runId`(评审在后台跑,客户端不必等) |
| `200` | 已受理但没真跑:与进行中任务合并(`deduped`)、超当日预算(`skipped`)、或一次触发多个仓库(返回 `results` 数组) |
| `401` | Key 无效 |
| `403` | 你不在**这个仓库的成员名单**里,或该仓库没开「允许在线触发」/已停用(错误文案会点名是哪个仓库、卡在哪一条) |
| `404` | 仓库不在白名单里 |
| `429` | 触发过于频繁 —— **每个 Key 60 秒只能触发一次**(管理员豁免成员名单,但不豁免限频) |

⚠️ **被拒的请求不消耗限频窗口**:403/404 之后改正再试是立刻可用的,不用等 60 秒。

MCP 侧两个工具(只对获授权的 Key 可见):

| 工具 | 参数 | 返回 |
|---|---|---|
| `code_review_list` | `limit`(最近多少次运行,默认 10) | **你名下的**仓库 + 各自上次状态/上次提交/连续失败次数 + 它们的运行记录(看不到别人负责的仓库) |
| `code_review_trigger` | `repo`(可选,缺省 = 你名下全部) | 同上面的接口,结果按工具结果返回 |

⚠️ 评审的是**已提交**的代码,不是工作区未提交的改动 —— CI 里请先 push 再触发。


## 面板上按次选分支

管理面板的触发卡片里有**仓库**和**分支**两个下拉:选中仓库后会拉出它的分支列表(默认分支排首位并自动选中),点「开始评审」就用这条分支。

- **只对本次生效**:不改仓库配置、不写回 `config.json` —— 仓库的默认分支还是设置页里那个
- 评审记录里会记下这次用的分支,详情与报告都能看到
- ⚠️ **游标是按「仓库 + 分支」各记一份的**:按次评了 `feature` 用 `feature` 自己的游标(第一次评它就是冷启动回溯),不会动 `main` 的游标,也不会继承 `main` 的
- 分支列表来自 `git ls-remote --heads`(local 仓库走 `for-each-ref`),所以私有仓库要凭据能通才拉得到;拉不到时会退回显示「默认分支(未取到分支列表)」并提示原因,不会把触发卡死
- 设置页的仓库编辑器里也有「拉取分支」按钮:填完地址就能先看看有哪些分支,再决定默认评哪条

## 按范围补评(补历史)

「开头那一次漏评的合并,现在想补上」—— 触发卡片下方的「**按范围补评**」折叠块填两个提交号(起点 / 终点,7~40 位十六进制)即可。

- 走的是**显式范围**:起点终点原样交给引擎(等价 `git merge-base(起点,终点)..终点` 的净差异),**不看游标、也不推进游标** —— 补一段历史不该把高水位线往回拉,下次常规评审仍从原来的位置继续
- 也**不改写**该分支的「上次运行时刻」与连续失败次数,所以定时扫描的节奏不会被这次人工操作带偏
- 两个输入框**要么都填、要么都不填**:只填一个、或填的不是十六进制提交号,直接 400 拒绝,不会静默降级成一次普通评审
- 起止填成同一个提交 = 只评这一个提交(引擎收到长度为 0 的区间会得出空 diff、报「已跳过」,所以此时自动改走单提交口径)
- 详情里的「范围来源」会写明 `手动按范围补评 1a2b3c4d→5e6f7a8b（不推进游标）`;若填的起点不是终点的祖先,还会补一句实际取净差异用的是哪个共同祖先
- ⚠️ **只能补「当前 clone 里有的提交」**:工作区只拉取该仓库配置的那条分支(或面板本次选的分支)。提交不在里面时运行会**明确失败**并提示「请先把该仓库分支改成包含它的分支,再按范围补评」—— 不会偷偷去评别的区间
- 补评同样受当日 token 预算与磁盘上限约束
- 这个入口**只有管理员面板有**,对外接口(`/api/code-review/trigger`)不开放指定范围 —— 成员 CI 触发走的永远是常规增量

## 来源与拉取行为

| 来源 | 怎么填 | 评审前做什么 | 凭据 |
|---|---|---|---|
| **remote** | 线上仓库地址(`https://` / `ssh://` / `git@`) | 每次评审前 `git fetch` 该地址并 reset 到目标分支最新 | 公开仓库选「无凭据」;私有仓库填 HTTPS Token 或 SSH 私钥路径 |
| **local** | 服务器上仓库的**绝对路径**(如 `/Users/xxx/Project/my-app`) | 首次评审时从该路径 clone 一份到工作区;之后每次评审前从该路径 `fetch` 最新提交 | 不需要凭据(本机路径) |

- **填入只是登记白名单,不会立即拉取** —— 第一次触发评审(手动/定时/CI)时才 clone,之后每次评审前自动同步到目标分支最新
- ⚠️ 评审基于**已提交**的内容:本地仓库里未 commit 的工作区改动不会被评审 —— 想评什么就先 commit
- 本地路径要求:是一个 git 仓库(有 `.git`)且至少有一个提交;克隆进工作区后你的原仓库不会被改动(评审在独立副本上进行)

### 先测连接再保存

编辑器里填好地址/分支/凭据后,不必先保存 —— 底部「**测试连接**」按钮直接拿**当前表单里的值**去验(remote 发一次 `git ls-remote`,local 检查路径存在且是 git 仓库),结果就地显示,填错能当场改。

- 测试用的凭据就是你此刻填的;**凭据留空**时会沿用该仓库已保存的原值(界面回显的是掩码)
- 已保存的仓库,表格行里也有「测试」按钮,结果以顶部浮层(toast)提示
- ⚠️ 容器部署时,`local` 路径填的是**容器内**路径 —— 测试报「路径不存在」多半是宿主机路径没挂进容器

## 评审范围(增量口径)

系统给**每个「仓库 + 分支」各记一份游标**(上次评到哪个提交),存在数据库 `code_review_repo_state`,不写 config。每次评审都用「起点 → 终点」两段式,引擎按这两个端点取**净差异**(等价 `git merge-base(起点,终点)..终点`),区间内的提交会**一起**被评审。

```text
终点 to:  分支当前 HEAD(面板按次选了分支,就是那条分支的 HEAD)
起点 from 按下面四条依次判定 —— 运行详情里的「范围来源」写的就是命中的那一条:

cursor    上次评到的提交仍是 to 的祖先   → from = 上次评到的提交
          (最常见:只评「上次评到 → 现在」之间的新增内容)
cold      这条分支还没有游标(第一次评它)  → from = to~N     ← 冷启动回溯
rewritten 有游标,但它已不是 to 的祖先
          (force push / rebase 改写了历史) → from = to~N     ← 游标失效回溯
manual    管理员在面板里显式填了范围       → from/to 原样用(补评;不推进游标)

N = 冷启动回溯提交数:全局默认 10,可在仓库编辑器里按仓库覆盖,钳位 [1,500]
```

### 回溯 N 步到底覆盖了哪些提交

`to~N` 走的是**第一父链**(即 `git log --first-parent` 那条线),而 N 是**步数**、不是「提交个数」:

| N | 起点落在 | 覆盖到 |
|---|---|---|
| `1` | `to~1`(上一个提交) | 只有 `to` 自己 —— 等价于老版本的「只评最新一个提交」 |
| `2` | `to~2` | `to~1` 与 `to` 两个提交 |
| `10`(默认) | `to~10` | 第一父链上最近 10 步之内的全部提交,含这些合并**带进来**的旁支提交 |

⚠️ **这就是「合并进来 5 个提交却只评了最后一个」的成因**。设主分支刚做过一次合并 `M`,合并后又落了一个提交 `X`(现在 `HEAD=X`):

```text
git log --first-parent --oneline
X   收尾提交        ← HEAD(= to)
M   Merge branch 'topic'
c1  合并前的主分支尖
    ├─ t5 ... t1    ← topic 分支的 5 个提交(被 M 带进来)

N=1: from = X~1 = M   区间 M..X      = {X}                → 只评 1 个提交,5 个并入提交全在区间外
N=2: from = X~2 = c1  区间 c1..X     = {t1..t5, M, X}     → 7 个提交,并入内容全在
```

所以**要让合并带进来的内容被评到,N 至少要比「HEAD 到那次合并的距离 + 1」大**。

数字代入(实测真实仓库的一次合并提交 `a62a0900`,看引擎拿到多少文件):`~1` 命中 **1** 个文件、`~2` 命中 **12** 个(被并入的模块全在里面)、`~5` 命中 **38** 个。

⚠️ 回溯步数超过分支历史长度时会**夹到根提交**,不报错(小仓库第一次评审因此等于「评全部历史」)。根提交本身不会出现在区间里。

⚠️ 默认 10 意味着**首次评审一条分支的评审量明显比以前大**(老版本只评 1 个提交)。仓库大或套餐紧张,就在仓库编辑器里把这条分支的「冷启动回溯提交数」调小(填 `1` = 只评最新一个提交);全局值在设置页「高级参数」里,仓库上留空即跟随全局。代价由 `单次 token 预算`(默认 800 万)兜底。

### 游标什么时候推进

```text
推进:  success / completed_with_warnings / completed_with_errors / partial / skipped
       → last_commit = 本次的 to,失败计数清零
       ⚠️ partial(部分完成)也推进 —— 预算没调高的话,不推进就会每次重评同一段、
          照样烧满整份预算(死循环)。没评到的文件靠「按范围补评」手动补
不推进: failed / timeout / canceled
       → last_commit 保持原值(下次仍从上次成功处开始),失败计数 +1
补评(manual): 一律不推进 —— 补一段历史不该把高水位线往回拉;
       也**不改写**「上次运行时刻」与失败计数,免得定时扫描被人工操作带偏
```

⚠️ **每条分支的游标互相独立**:仓库配置里默认评 `main`,面板上按次选了 `feature`,那一次用的是 `feature` 自己的游标 —— 既不继承也不覆盖 `main` 的。把仓库的默认分支从 A 改成 B 等于换了一条线:B 没有游标,下一次是**冷启动回溯**。

想核对「这次到底评了哪一段」,有三个地方:运行列表每行的 `范围` 标签(增量 / 冷启动回溯 / 游标失效回溯 / 手动补评)+ 短 SHA、详情弹层的「范围来源」与「本次覆盖的 N 个提交」清单、HTML 报告里的 `range` 与 `covered commits` 两段。

## ⚠️ 注意与边界

- **代码片段会入库**:评审意见里的原代码与建议代码默认写入 SQLite(`storeComments: true`)。这是本系统第一次把源码内容落库;可在设置里关掉(只存统计),也可用「清空评审数据」整体清除。
- **磁盘占用**:每个仓库一份完整检出 + 评审产物(`code-review-workspaces/`,已在 `.gitignore` 里)。`perRepoDiskLimitMB`(默认 2048MB)是**每仓库**上限,超限拒绝入队并通知;可在设置页查看占用与清理。
- **工作区不是只读仓库**:系统会 `git reset --hard FETCH_HEAD` 强制同步到目标分支,**不要**把手工改动放在这里。
- **凭据**:HTTPS Token / 私钥路径存在 `config.json`(与方案真实 Key 同一信任级别),只经子进程环境变量传给 git,**不进命令行参数、不进日志**;界面与接口只回掩码。HTTPS Token 走一个临时 askpass 脚本喂给 git,用户名默认 `oauth2`(GitHub / GitLab / Gitea 等对 HTTPS Token 认证的用户名不敏感,只要非空即可)。
- **子进程环境是白名单重建的**:`ANTHROPIC_API_KEY` / `OPENAI_API_KEY` / `*_TOKEN` 等一律不传给 OCR —— 否则它可能绕开指定的 provider 直连上游,导致计费与审计双失守。
- **被拒绝的用法**:非 `https/ssh/git@` 的仓库地址(含 `file://`、`ext::`)、以 `-` 开头的地址或分支、非十六进制的提交号、把端点配成非回环地址 —— 都会被拒绝。
- 定时任务按 **间隔** 或 **每天某时刻 + 星期** 判定(见上文「定时评审怎么算到期」);同一仓库同时只会有一个任务(串行),避免 git 工作树被并发写坏。
- **触发是写操作**:成员用虚拟 Key 触发一次评审就会真的消耗套餐额度,且评审结果入库 —— 只把确实需要的人加进仓库成员名单。
- **标准与业务背景都是每次评审的固定 prompt 成本**:标准按文件类型注入,单份文件拿到的是「通用段 + 该技术栈段」(约 6~8 KB);业务背景每级上限 20000 字,两级都填就一起发。背景别写成第二份编码规范 —— 只写代码里读不出来的业务规则,重复的内容既费 token 又容易与标准冲突。
- **换标准前后意见数不可直接比**:标准版本号变了,口径就变了。要比对,先确认两次运行的「评审标准」是同一个版本,业务背景与探索深度也没动过。
