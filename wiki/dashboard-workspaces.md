# 管理面板：工作区

左栏菜单里的十三个工作区(「数据总览」之外的菜单项,各自数据懒加载)。协议三段开关对数据总览生效,其它工作区不受它影响。

## 1. 用户用量

团队成员表格，每行一位成员：

- 请求数、输入 / 输出 / 缓存写 / 缓存命中 / 合计 Token、今日用量、最后活跃时间
- **在线状态 LED**：绿灯表示近期有请求
- **配额列**：成员只用一个方案时显示单个配额进度；多方案时自动**展开为每方案一列**（百分比 + 进度条，悬停可看已用/上限/配额来源/倍率/临时加量）
- **「只看配额」**按钮：折叠 Token 统计列，只留配额信息（偏好存在浏览器本地）

## 1.1 点数余额

逐成员列出当前周期的点数预算：启用状态、周期（日/周/月）、预算点数、本期已用、剩余、使用率、周期起止与首选方案。数据来自管理端「点数预算」同一份配置与 `usage_daily` 聚合；未启用的成员显示「未启用」，不是余额为 0。

> 系统同时按人记录 day / week / month 三档点数用量（`point_usage`），供后续统计；当前卡片只展示本期预算与用量。查询接口见[配额与计费机制](mechanism-quota.md#用量留存)。

## 2. 上游额度

把各平台**官方**的套餐用量窗口与账户余额拉成一张张卡片（**只读对账用**，与本站在扣的额度池是两套账）：

- 顶部**四格概览**：`需要关注`（额度告警 + 查询失败）/ `查询正常` / `未配置` / `已关闭`（后两格为 0 时不留空位），最后一格是这份快照的更新时间（北京时间）
- **数字是主角**：余额类一张卡片一个大号金额（`¥1,234.56`）＋口径与赠金/充值明细；套餐类一个窗口一行——左边窗口名、右边**大号已用百分比**、下面是进度条与 `剩 6.00M / 300.00M tokens · 3 天后重置（10-17 11:45）`
- **条目多的卡横着铺开，并且排在后面**：一行达到 **5 项**以上（典型是阿里云百炼：月额度 + 7 项 Harness 权益）时，这张卡占满整行、卡内条目按列自动分栏（宽屏 2–3 列），不再是一张特别长的卡把整段行高撑歪；条目少的卡照旧按 236px 起排
  - **单列卡优先在上/在前**：同一分区里，占满整行的宽卡一律排到单列卡**之后**（宽卡上的数字照样看得到，但短卡先占满前几行，视线从短的、正常的卡开始扫）。例外是**告警 / 查询失败**的宽卡——那张会被钉在分区最上面（最要紧，红卡不该被压到底下）
  - **卡片按各自高度往下排（瀑布列）**：不再是一行等高的格子。卡片按「下一张进当前最矮的那列」贪心分列，再补一轮「把某张卡挪到别的列、只要最高的列能变矮就保留」的微调——所以同一行里两张卡通常不等高，但**列与列之间尽量齐平**，矮卡下面不会留一大块空白（实测余额分区两列高度差 325px → 60px）。一行放几张随窗口宽度走：每张至少 236px、间隔 10px，窗口缩放会自动重排
  - 面板如果是在**后台标签页**里渲染的（当时量不到宽度），会等到你切回来、真正有宽度的那一刻再分列，不会留下「一列到底」的样子
  - **代金券单独成小卡片**：条目带 `voucher` 标记时（目前只有硅基流动会这么标）不会被当成余额条目 —— 卡片主体下面另起一块虚线小区，抬头是「代金券 N 张 · 可直接抵扣消费」，每张券一张小卡显示**券名 + 剩余金额 + 面额 / 已用 / 有效期至**，一眼分得清哪个数字是余额、哪个是券；券的金额照样计入上面那条「可用余额」合计
- **套餐额度单独圈一块**：一张卡里**所有带进度条的额度窗口**（智谱的 5 小时 / 每周窗口、火山方舟的三个窗口、阶跃星辰 Step Plan 的套餐 Credit、阿里云百炼 Coding Plan 的三个窗口、百炼 Token Plan 的套餐月额度…）都画进一块**虚线框**里，抬头是「套餐额度」；MCP / Harness **权益**额度（智谱的「MCP 每月额度」、百炼的 7 项权益）留在框外，一眼分得清哪个百分比是**套餐**用量、哪个是权益额度。框、进度条和数字按健康度上色：**低于 80% 蓝色**、**80% 及以上红色**（虚线框一起变红）—— 这里的 80% 是固定分界，与顶部「告警阈值」无关
- **卡片宽度**：每张卡至少 **330px**（放得下「智谱 GLM / GLM Coding Plan」这种长名字，名称不再被省略号截断、也不折行）；窗口不够宽时 Plan / 余额两个分区**竖着叠**（每个分区整行铺开），而不是把卡片压窄
- **套餐信息行**：上游接口若给得出套餐本身的信息（规格 / 状态 / 到期 / 剩余天数），卡片标题下方会多一行小字，例如 `Standard · 生效中 · 到期 2027-01-15（剩 92 天）`。**拿不到这一行就不显示** —— 目前有两处给得出：阿里云百炼个人版的控制台订阅接口（规格 / 状态 / 到期 / 剩余天数），以及阶跃星辰 Step Plan 的 `GetStepPlanStatus`（只有套餐名，如 `Plus`）；其它套餐平台（智谱 GLM、火山方舟…）只给窗口重置时间，没有套餐字段，所以那张卡上没有这一行，不是漏显示
- **没有数字的平台**压成一行小字，带「启用 / 配置 / 控制台」链接，不占卡片位置（还能查的「仅控制台」直接摆出来；已关闭 / 未配置的收进分区末尾的「其余 N 个（未配置 / 已关闭）」折叠块，展开状态浏览器会记住）；分区内按「告警 → 查询失败 → 正常」排序，要紧的排前面
- 卡片右上角：徽章（正常 / 额度告警 / 查询失败 / 未配置 / 已关闭 / 仅控制台；失败但留有上次数据时**额外**挂「旧数据」黄标）、`↻`（只重查这一个平台，就地替换该卡、不重排整面板）、`ⓘ`（悬停看该平台的官方口径说明）
- 进度条一律表示**已用比例**：套餐用上游给的百分比，余额用 `1 − 剩余 ÷ 总额` 反推；拿不到就不画（不会拿 0% 冒充）
- 分区只有两个：**Plan**（订阅套餐 / 套餐窗口 / 只能在控制台看的套餐）与**余额**（充值余额 / 账户余额 / 中转站钱包）；宽屏时左右并排、一屏看完（窗口窄了自动上下堆叠）。标题栏右侧摘要 `1 个需要关注 · 共 20 个平台 · 更新于 11:45`（需要关注时前面带一颗红点；「共 N 个」= 20 个内置平台 + 你自己加的中转站点），「**刷新全部**」强制重查所有已开平台
- 两个分区**左右并排、底部对齐**：段内最后那两行（「仅控制台」小字行、`其余 N 个（未配置 / 已关闭）`折叠块）钉在各自分区底部，所以左右两列一定是齐的；窗口窄了自动上下堆叠
- 点卡片页脚、小字行里的「**控制台**」，以及设置页那一行的「打开控制台」，都在**新标签页**打开对方官网（不做内嵌：16 个入口里 8 个明确拒绝被嵌，能嵌的也要重新登录，详见[上游额度 / 账户余额](upstream-quota.md)的「控制台入口」一节）
- 查询行为在设置页 → 上游额度里配：默认**缓存 5 分钟、不自动轮询上游**（只在打开面板或手动刷新时查），告警阈值 90%，超时 10 秒
- 平台清单、每种凭据怎么配、各家接口的性质（官方接口 / 私有接口 / 仅控制台）见[上游额度 / 账户余额](upstream-quota.md)

## 3. 客户端用量

按识别到的调用方客户端（claude-cli / codex_cli_rs / zcode / unknown…）统计请求数与 Token，用来回答「团队都在用什么工具跑」。

## 4. 明细记录

按**日 / 周 / 月 / 年**分组的周期明细：

- 关键字搜索、时间范围筛选
- 按时间 / Token / 请求数排序，分页
- 点击某个周期可展开看该周期的成员明细
- **点击成员用户名**可展开该成员在该时段的 **24 小时请求分布**（半小时粒度，双轴：柱=请求数、线=总 Token，与「24 小时趋势」口径一致）——数据在点击时才向后端拉取（`/api/user-hours`），不随面板数据预载；再次点击收起
- 小时明细数据仅保留 **7 天**：时段完全超出保留期时会提示「超出小时明细保留期」而非空图
- 「重置」一键清空筛选条件（并收起所有展开）

## 5. 方案中心

各方案一张行：入口 URL、上游地址、今日请求、今日用量、**使用状态**、状态徽章（**限流中 / 熔断中 / 默认组头**等）。按协议分节展示。排查「某个方案现在能不能用」先看这里。

**使用状态**（使用中 / 休眠中）回答「这个方案现在有没有人在用」：

- 判定规则（后端计算，默认值）：该方案**当前有进行中的请求**，或**最近 5 分钟内有过完成记账的请求** → 绿灯「使用中」；否则灰灯「休眠中」
- 有并发请求时显示数量：如「使用中 · 3」表示 3 个请求正经该方案转发（含 failover 尝试中的候选方案）
- 休眠中的行**悬停**可看「最后活跃：x 分钟前」；从未使用过的方案显示「从未」
- ⚠️ 注意两点：①「最近 5 分钟」按**请求完成记账**时刻计，失败未记账的请求不推进窗口（进行中的请求由并发计数覆盖，两者合起来无死角）；② 数据随面板 30 秒轮询刷新，非实时推送——刚结束的请求最多延迟 30 秒才反映
- 服务器重启后并发计数清零，但「最近 5 分钟」窗口来自数据库、不受影响

### 方案用量报告导出

每行末尾的「**导出**」按钮可以把该方案**指定时间段**的完整用量报告导出成两个文件：一份**HTML 报告**（设计工整、自带样式，可直接发群或用浏览器打开打印）＋一份 **Excel 明细**（5 个工作表，信息最全）。

#### 怎么用

1. 方案中心 → 点某行的「导出」，弹窗里**方案名**已自动填好；
2. 选**报告周期**（月度 / 周度，二选一），再从下拉里挑具体时段——
   - **月度** = 自然月（如 `2026-09 → 2026-09-01 ~ 2026-09-30`）；**周度** = **周一到周日**（北京时间），如 `09-07 ~ 09-13`，列表里任意一天点周度都会落到它所在的那个周一开头的周；
3. 点「开始导出」——任务进**后台队列**，页面不卡；弹窗提示已开始，完成后在「数据总览」顶部工具栏的「**文件管理**」里查看并下载。

「文件管理」弹窗里每条任务一行：状态徽章（**排队中 / 生成中 / 完成 / 失败**）、方案名、周期、创建与完成时间、文件名与字节数；完成后可「**下载**」（HTML / Excel 两个链接），HTML 额外有「**查看**」在浏览器里直接预览；失败的任务会显示失败原因。打开期间每 2.5 秒自动刷新一次任务列表。有进行中任务时「文件管理」按钮上亮橙色小圆点，任务完成/失败时弹一次提示——中途刷新页面也会接管继续提醒。任务列表里的时间按**浏览器本地时区**显示；报告内部的生成时间统一写北京时间（UTC+8）。

导出记录多了以后，弹窗顶部有**筛选栏**、底部有**分页**，找历史任务不用一直滚：

| 项 | 默认值 | 说明 |
|---|---|---|
| 筛选 · 方案 | 全部方案 | 下拉列出**出现过导出记录**的方案（新方案导出过一次就自动可筛） |
| 筛选 · 状态 | 全部状态 | 排队中 / 生成中 / 完成 / 失败 |
| 筛选 · 类型 | 全部类型 | 月度 / 周度 |
| 分页 | 每页 **10** 条（上限 100） | 按**创建时间新 → 旧**排列；底部显示「第 x / y 页 · 共 N 条」，越界请求自动夹回有效页 |

三个筛选条件可叠加（如「G计划 + 完成 + 月度」），任一条件变化都回到第 1 页。⚠️ 注意两点：① 小圆点与完成/失败 toast **不受筛选和翻页影响**——即使你正看着别的方案那页、或关着弹窗，任何任务的完成提醒都照常弹；② 任务记录本身**不会自动清理**（含失败记录），文件太多时可在服务端 `exportFile/` 目录手动删除旧文件——对应记录的下载链接会提示「文件不存在或已被删除」，筛选列表不受影响。

#### 可选的周期范围

下拉列表按**新 → 旧**排列，只列出**该方案真实有数据的时段**，并设上限：

| 参数 | 默认值 | 说明 |
|---|---|---|
| 月度回溯上限 | **60 个月** | 从当月往前数最多 60 个自然月 |
| 周度回溯上限 | **104 周** | 从本周一往前数最多 104 个周一 |
| 列表下界 | 该方案 `usage_daily` **最早有数据的日期** | 之前（含没有数据）的月份/周不会出现在下拉里 |

边界情况：方案当天刚开通、还没有任何数据时，下拉里只剩**当月（本周）**一项——导出来是一份「该周期无数据」的空报告，不会报错。

#### 报告里有什么（HTML 与 Excel 内容一致，Excel 更细）

- **汇总卡片**：请求次数、输入 / 输出 / 缓存写入 / 缓存读取 Token、总 Token（含缓存）、计权 Token（配额口径）、活跃用户、有数据天数。总 Token 的计算逻辑：

  ```
  总 Token = 输入 + 输出 + 缓存写入 + 缓存读取
  ```

  数字代入示例：输入 3,500 + 输出 700 + 缓存写入 160 + 缓存读取 110 = **总 Token 4,470**；同一周期计权 Token = 4,800、请求 10 次、活跃用户 2、有数据天数 2。两套口径的区别见[先搞清两套 Token 口径](metrics-reference.md#先搞清两套-token-口径)。
- **每日用量表**：每天一行（输入/输出/缓存/总/计权/请求），HTML 里带条形图，末行合计。
- **用户汇总**：每位成员一行——Token 明细、请求数、活跃天数、最近活跃日期，按计权 Token 降序。姓名取自「用户用量」的成员名；该用户从未被登记过名字时显示 **user_key 前 12 位 + `****`**（HTML 与 Excel 一致，均做打码）。
- **每日 × 用户矩阵**：行=成员、列=日期（如 `09-10`），一眼看出谁在哪天用得多。
- **模型使用（计费归因）**：每个模型一行，回答「**这个方案的配额到底被哪个模型吃掉了**」——除了请求数与 Token，还给每个模型算三个归因指标：

  | 指标 | 公式 | 读法 |
  |---|---|---|
  | **计费占比** | 该模型计权 ÷ 方案总计权 | 这个模型吃掉了多少**配额**（核心数字） |
  | **累计占比** | 按占比降序逐行累加 | 前几名模型合计占多少；看前两行就知道大头在哪 |
  | **实际倍率** | 该模型计权 ÷ 该模型原始 Token | 这个模型「记账时乘了几」；= 1 说明没放大，> 1 说明倍率贵 |

  数字代入示例（接上面 4,800 计权的例子）：model-b 计权 2,600 → 计费占比 2,600÷4,800 = **54.2%**、实际倍率 2,600÷2,400 ≈ **×1.08**；model-a 计权 1,500 → 占比 31.3%、倍率 1,500÷1,200 = **×1.25**。一眼结论：配额大头是 model-b（54.2%），但**单价最贵**的是 model-a（×1.25）。表格按计费占比**降序**排列（占比并列时按模型名排序，结果稳定）。
- **模型计费归因摘要**（HTML 报告模型表上方的一行结论）：「计费占比最高的是 **model-b**，占该周期配额消耗的 54.2%（实际倍率 ×1.08）· 前两名合计 85.4%」。周期内出现模型明细缺口（见下方 ⚠️）时，摘要尾部追加橙色提示「⚠️ 模型明细仅覆盖 xx% 的计权消耗（超出 400 天保留期部分无法归因）」。

#### Excel 的 5 个工作表

| Sheet | 内容 |
|---|---|
| 汇总 | 周期、方案、协议、上游、各项 Token 合计、**计费归因**（top 模型+占比，覆盖不足 100% 时多一行 ⚠️）、生成时间、口径说明 |
| 每日用量 | 每天 8 列 + 合计行 |
| 每日×用户 | 用户 × 日期矩阵 + 当日合计行 |
| 用户汇总 | 11 列（含活跃天数、最近活跃） |
| 模型使用 | 每模型请求数、Token、**计费占比(%) / 累计占比(%) / 实际倍率** |

表头**冻结首行**、数字**千分位**，打开即可筛选排序。

#### ⚠️ 注意

- **模型明细只保留 400 天**：早于 400 天的周期，「模型使用」sheet 会是空的（其余内容不受影响——日汇总主表永久保留，见[数据保留期总表](metrics-reference.md#数据保留期总表)）。模型明细**不含缓存 Token**（存储表没有缓存列），所以模型表的 Token = 输入 + 输出，与汇总卡片的「总 Token（含缓存）」口径不同——两个口径并存是有意设计，对账时别混用。**计费归因同理**：归因只统计 400 天内的模型明细，跨出 400 天的周期里「各模型占比合计不足 100%」（归因摘要会标 ⚠️），但「计费占比」的**分母仍是全周期的计权 Token**——所以占比数值是保守的（不会虚高），缺口只影响覆盖度
- **实际倍率是「平均」值**：落表时按请求发生那一刻的时段（峰/谷）× 当时的模型倍率折算（`计权 = (输入−缓存写入×0 + 缓存读取×缓存倍率 + 输出) × 倍率`，写入即冻结、永不追溯）。一个周期内跑过峰谷两档、或中途改过价的模型，实际倍率会落在两档之间（如峰 ×1.25、谷 ×1.0 各一半 → ≈×1.13）；要逐日核对请配合「每日用量表」和[配额模型倍率](#6-配额模型倍率)页的「实收 ×N」标注
- **报告是「记账口径」**：只统计**成功记账**的请求，失败请求不进报告（失败的去「错误记录」看）
- 导出是**后台串行队列**：一次跑一个任务，多个任务依次排队；**服务重启**会打断进行中/排队中的任务并标记为失败（「服务重启,任务中断,请重新导出」），重新导一次即可——已完成任务的文件不受影响
- 产物存放在服务端 `exportFile/` 目录（HTML/XLSX + 任务索引 `index.json`），属运行时数据；在文件管理里删除入口不可用，需要清理时直接删目录下的文件即可（下载链接会相应报「文件不存在或已被删除」）

### 方案模型计费归因分析

方案中心每行的「**分析**」按钮（在「导出」旁）打开一个实时弹窗，回答「**这个方案的配额消耗被哪个模型吃掉了**」。与导出报告的区别：报告是**选定周期**的完整文件，这里是**快捷窗口**（近 7 天 / 近 30 天 / 本月，默认近 30 天）的实时数字，30 秒内即可切换。

#### 怎么用

1. 方案中心 → 点某行的「分析」，弹窗顶部显示方案名；
2. 顶部三个窗口按钮切换时间段：**近 7 天 / 近 30 天 / 本月**（本月=北京时间的自然月 1 号起）；
3. 弹窗内容从上到下：
   - **归因摘要**一行结论：如「计费占比最高的是 **glm-4.6**，占近 30 天配额消耗的 **55.6%**（实际倍率 ×1.50）· 前两名合计 86.9%」；明细覆盖不足时尾部有橙色 ⚠️ 提示；
   - **四张卡片**：计权用量（配额口径）、实际 Token、请求次数、活跃用户；
   - **模型表**（按计费占比降序）：模型、计权 Token、计费占比（含条形）、累计占比、实际倍率、请求、实际 Token；
   - 底部**口径注解**。

#### 指标口径（与导出报告的归因表完全一致）

| 指标 | 公式 | 读法 |
|---|---|---|
| 计费占比 | 该模型计权 ÷ 方案总计权 | 配额被哪个模型消耗（核心数字） |
| 累计占比 | 降序逐行累加，上限 100% | 前几名合计，快速判断「大头集中在哪」 |
| 实际倍率 | 该模型计权 ÷ 该模型原始 Token | 该模型记账时平均乘了几；≈1 表示按原价，>1 表示倍率放大 |

数字代入示例：某方案近 30 天计权 810 K。`expensive-model` 计权 450 K / 原始 300 K → 占比 450÷810 = **55.6%**、倍率 450÷300 = **×1.50**，排第一；`cheap-model` 计权 360 K / 原始 1.2 M → 占比 **44.4%**、倍率 360÷1200 = **×0.30**，排第二。结论：配额大头在 expensive-model，但原始 Token 大头其实在 cheap-model（1.2 M）——只看 Token 量会得出完全相反的结论，这正是要看计费占比的原因。

**为什么历史占比准确**：计权 Token 在**请求落表那一刻**就按「当时的峰谷时段 × 当时的模型倍率」折算冻结（写入后永不追溯，中途改价不影响历史数字），所以任意窗口内直接对模型明细求和就是精确的计费归因，不用回放价格。

#### ⚠️ 注意

- **模型明细只保留 400 天**：窗口完全落在 400 天外时弹窗提示「没有模型明细可归因（有计权用量但明细已超出 400 天保留期）」；窗口**跨**出 400 天时各模型占比合计不足 100%，摘要尾部会标「⚠️ 模型明细仅覆盖 xx%」（占比分母仍是全窗口计权，数值不虚高）。近 7 天 / 近 30 天 / 本月三个快捷窗口天然落在保留期内，日常使用碰不到这个边界
- **实际倍率是平均值**：窗口内跑过峰谷两档、或期间调整过倍率时，实际倍率落在两档之间（如峰 ×1.25、谷 ×1.0 各半 → ≈×1.13）；要逐日拆解用「导出」报告的每日用量表
- 数据**实时读取**数据库（打开弹窗与切换窗口时各拉一次），不随面板 30 秒轮询自动刷新；弹窗开着时想看最新数字，重切一次窗口即可
- 该弹窗是**只读分析**，不消耗配额、不影响方案的运行状态

## 6. 配额模型倍率

按协议分成 **Anthropic（Claude Code）** 与 **OpenAI（Responses）** 两张列表，**一行一个方案**；方案的「模型倍率」列把每个模型逐行列出：

- 每个模型一行：`峰 ×A / 谷 ×B / 当前 ×C`，当前时段那一档加粗
- 模型后标别名（如 `jx-opus`）；按**真实上游模型名**匹配单独定价
- 单独定价的模型带「单独定价」徽章
- 列尾显示该方案今日请求数；表头汇总当前时段、方案数与模型配置数

## 6.1 方案模型倍率

和「配额模型倍率」同一套列表布局，但展示的是**点数倍率**：`pointPeakRate` / `pointOffPeakRate` / `pointModelRates`，以及方案级「方案系数」。点数倍率与额度池倍率完全独立，留空显示「未配置」，当前值按 1.00 计算；方案系数只影响点数扣减。

## 7. 错误记录

最近的代理错误（429 / 403 / 503 等），可一键清除。**配额超限、并发超限、限流产生的 429 都会进这里**——成员喊「用不了」先来这里对时间点。429 的具体含义见 [FAQ](faq.md)。

> 注意：错误表只保留**最近 200 条且 7 天**，清空前的历史无法追查。

## 8. 产出质量

团队的产出分析工作台：

- **指标**：净产出、文件数、失败率、重写率、验证密度、Token 效率等——**每个指标的精确公式与着色阈值**见[指标口径参考](metrics-reference.md#产出质量指标公式)
- **时间筛选**：今日 / 近 7 天 / 近 30 天
- **导出报告**：生成自包含 HTML 报告，可直接发群里
- **指标口径说明**：弹层解释每个指标怎么算
- **告警列表**：系统自动扫出的异常（空转消耗 / 错误循环 / 编辑失败爆发，阈值见[指标口径参考](metrics-reference.md#产出告警的精确阈值)），可全部标记已读
- **项目分布**：按项目统计产出；会话跨多项目时整段记给主导项目

隐私边界：只记行数、文件路径、命令分类，**不存代码内容**；文件路径记录可在设置里关闭。

## 9. 会话使用情况

团队维度的会话面板：

- 每个会话一行：可读标题、客户端、项目、Token、缓存率、净产出。**项目列写「无代码产出」只表示该会话没有可归属的代码项目**（没改过文件），不代表没有工具调用——工具/文件/净产出三列照实显示，所以「无代码产出 + 300 次工具调用」是可能的，也是真实的
- **「合计 N 个会话」不是 N 次对话**。面板顶部把这行拆开写：`真人 X + 自动化 Y，真人碎片 Z`。三个数相加能对回总数——这正是最早被误读、也最被怀疑「数据对不对」的地方
  - **碎片** = 会话轮数 ≤ 2（上限见[指标口径参考](metrics-reference.md#会话统计)），常见于机器任务、上下文被切碎后的残留、或问了就走
  - **自动化** = 代码评审机器人账号产生的会话：一次评审落一条会话，所以它们的会话数会排到最前，却几乎没有代码产出
- 自动化账号在成员表里**默认折叠**成一行「自动化账号 N 个（代码评审机器人）· … 点击展开」，不占真人排名；真人 Key 偶尔跑一次评审的**混合账号不折叠**，但它的那些会话行会贴「自动化」标
- 支持**下钻**（点成员下钻到他的会话流水，可清除下钻）
- 今日 / 7 天 / 30 天筛选
- 会话标题的来源、自动化的三条判定线索、缓存率的协议修正算法见[指标口径参考](metrics-reference.md#会话统计)

## 10. 等值成本

把 Token 按参考牌价折算成 USD（牌价在设置页维护，支持峰谷分时价）：

- 按成员、按方案两个维度统计
- 今日 / 7 天 / 30 天筛选
- **改牌价后全部历史立即按新价重算**（查询时现算）——它是参考工具，不是账单存档
- 计价公式、默认牌价表与峰谷规则见[指标口径参考](metrics-reference.md#等值成本计算)

## 11. 代码评审

把登记过的仓库拉到本地用 OCR 做行级评审。列表每行:时间 / 仓库 / 触发方式 / 范围(来源标签 + 短 SHA,如 `冷启动回溯 1a2b3c4d→5e6f7a8b`,覆盖多个提交时带 `· 提交 N`) / 状态 / 文件数 / 意见数 / token / 耗时;点「详情」按文件分组展开每条意见(定位行号、问题描述、原代码、建议改法、推理),并列出**本次覆盖的提交清单**(提交号/标题/作者/时间),右上角「导出报告」下载自包含单文件 HTML。顶部可选择仓库与分支并手动触发,触发卡片下方还有「**按范围补评**」:填两个提交号补评一段历史(不推进游标)。

行上的动作随状态变化:**进行中**给「取消」,**终态**给「删除」——删除会连带清掉这条运行的全部意见与报告文件,不可撤销(细节与连带效应见[维护与清空](code-review.md#维护与清空))。

- 状态:完成 / 完成(有警告) / 完成(有错误) / **部分完成**(撞单次 token 预算,只评了一部分,深橙色) / 失败 / 超时 / 已取消 / 已跳过(超当日预算 / 无新提交)
- **没评完的运行会被标出来**:文件列写成 `10/39`(已评/选取),后面跟「覆盖不全,详见详情」;详情事实表里多一行「**覆盖率**」(如 `10/39 个文件(超出单次 token 预算)`),并列出未评文件、引擎那句自带算式的原话;**这种情况下不显示「未发现问题」的绿框**,改成灰底「未评完,结论不完整」。撞顶后网关会**自动续评**(同一会话只补未评部分,默认最多 2 轮),所以看到「部分完成」= 续评也补不完;结论结尾会写「自动续评 N 轮(复用 X 项已评结果…)」。紧跟覆盖率还有一行「**自动续评**」写明这次是**关了**(`已关闭（轮数 0）`)、**真补过**(`已续评 2 轮（复用 10 项已评结果），已达续评轮数上限`)还是**根本没触发**(`未触发（已配置上限 2 轮）`)—— 最后一种意味着跑这次评审的还不是带续评的版本。六个展示面与补救步骤见[单次预算撞顶:部分完成](code-review.md#单次预算撞顶部分完成)
- 详情事实表里有「**评审标准**」一行(这次用的是哪一版统一评审标准,如 `v4246b9e1a629`;早于统一标准的旧记录显示「—(此记录早于统一标准)」),意见被机械兜底丢掉时还有「**丢弃意见**」一行(缺取证推理的条数)。两次评审意见数不同时先看这两项 —— 口径不同不能直接比,详见[统一评审标准](code-review.md#统一评审标准)
- **评审范围是增量的**:每条「仓库 + 分支」各记一份游标;首次评这条分支会回溯最近 N 个提交(默认 10,设置页可调),之后只评「上次评到 → 现在 HEAD」之间的新增内容 —— 合并带进来的多个提交会一起评。详见[评审范围](code-review.md#评审范围增量口径)
- 触发方式除了手动,还有定时(设置页给仓库配)、CI(`POST /api/code-review/trigger`)、MCP(`code_review_trigger`)
- 未启用时显示引导;未安装 OCR 或 git 版本过低时显示安装/升级命令(不自动安装)
- 详情页同时给出两个 token 口径:OCR 自报与网关侧计数差值

详见[代码评审](code-review.md)。
