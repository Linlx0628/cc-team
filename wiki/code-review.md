# 代码评审

系统把登记过的仓库拉到服务器本地,用 [open-code-review](https://open-codereview.ai)(阿里开源的 OCR CLI)做**行级代码评审**,结果进管理面板「代码评审」工作区,并可推送通知。评审消耗走本网关的**评审专用 Key** —— 也就是计入用量与配额,和日常使用同一套账。

> ⚠️ **这是本系统唯一会执行外部命令的功能**(`git` 与 `ocr`),因此**默认关闭**,只有管理员能配置,成员无法提交任意仓库地址。

## 前置依赖(装在哪台机器上)

| 依赖 | 要求 | 安装 |
|---|---|---|
| `git` | ≥ 2.41 | `apt install git` / `apk add git` |
| `@alibaba-group/open-code-review`(`ocr`) | 能跑 `ocr version` | `npm i -g @alibaba-group/open-code-review` |
| `openssh-client` | 仅 SSH 拉私有仓库时需要 | `apk add openssh-client` |

网关**不会自动安装** OCR:未检测到时会显示「未安装」与安装命令,由管理员自行处理。设置页左栏「代码评审」的「引擎」卡片顶部会显示探测结果(OCR 版本与 git 版本),下面的「运行自检」会连方案、账号、工作区、每个仓库一起体检。

## 三步启用(不需要填任何 API 信息)

系统本身就是 AI API 网关,评审只是「另一个经网关的调用方」—— 所以只需要选方案,不用配 Key/端点/协议:

1. **选方案**:设置页 → 左栏「代码评审」→「评审用哪个方案」下拉选一个已有方案(端点与协议由系统按该方案自动推导)
2. **一键创建评审账号**:点「创建评审账号」即可。系统生成 `jx-review-…` 专用账号并设为超级用户,运行期向所选方案**借用已有的真实 Key**(不需要你填);用量记在「代码评审」名下,便于对账
3. **加仓库白名单**:「＋添加仓库」填名称、来源(`remote` 填 `https://`/`ssh://`/`git@` 地址,`local` 填服务器上已有仓库的绝对路径)、分支(**可点「拉取分支」从仓库列出来选**);可选凭据/定时/在线触发
4. **给仓库指定成员**:在同一个编辑器里勾「负责这个仓库的成员」—— 列在里面的人才能触发它、并在自己的「我的用量」页看到它的结果

引擎参数(并发、超时、token 预算等)收在「高级参数」折叠区,默认值一般不用动。

**评审端点会钉住你选的方案**:系统按该方案推导出 `http://127.0.0.1:<端口>/<方案后缀>/v1` —— 带后缀才能确保评审**就跑在这个方案上**。不带后缀的 `/v1` 会被当成「默认入口」交给**方案组**去 failover,结果评审可能跑在你没选的方案上(实测踩过:设置里选「阶跃星辰」,实际跑在「火山引擎」→「DeepSeek」),而真实 Key 也是从胜出方案借的 —— 用量会记错人。自检里有「方案已钉住」与「模型可用」两项专门盯这件事:方案没有独立后缀、或所选模型不属于该方案时都会报红。

## 四种触发方式

| 方式 | 怎么用 | 说明 |
|---|---|---|
| 手动 | 管理面板 → 代码评审 → 选**仓库**与**分支** → 开始评审 | 分支可当场从列表里选(见下);同仓库已有任务在跑时返回同一个 runId(去重) |
| 定时 | 设置页给仓库配「固定间隔 / 每天定时」 | 每 60 秒扫描一次;按**北京时间**判定;到点且该仓库无进行中任务才入队 |
| CI | `curl -X POST /api/code-review/trigger` + 虚拟 Key | 该 Key 必须在**这个仓库的成员名单**里,且仓库开了「允许在线触发」 |
| MCP | agent 调用 `code_review_trigger` / `code_review_list` | 同上;不在任何仓库名单里的 Key,工具列表里**看不到**这两个工具 |

**「谁能触发哪个仓库」是按仓库给的**:每个仓库有自己的成员名单(设置页里点该仓库的「编辑」勾选)。不是每个人负责同一个仓库,所以没有「一次授权、全仓库通行」的全局名单。不带仓库名触发时,只会触发**该成员名下的**那些仓库。

## 定时评审怎么算到期

每 60 秒扫一遍所有**启用**的仓库,按**北京时间**判定(时区固定 UTC+8,不跟随服务器本地时区):

```text
关闭          : 永不自动触发
固定间隔      : 上次运行距今 ≥ 间隔小时数 → 触发(从未跑过 = 立即触发)
每天定时 + 星期: 若填了星期,今天不在其中 → 不触发
                现在时刻 < 设定时刻              → 不触发
                今天已经跑过(手动也算)          → 不触发
                否则 → 触发
```

| 参数 | 默认 | 取值范围 | 说明 |
|---|---|---|---|
| 定时评审 | 关闭 | 关闭 / 固定间隔 / 每天定时 | 每仓库独立设置 |
| 间隔(小时) | 6 | 1 ~ 168 | 只看「距上次运行」,不挑时段 |
| 每天时刻 | `03:00` | `HH:MM` | 北京时间;格式非法时按 `03:00` 处理 |
| 只在星期几 | 空 | `1`~`7`(1=周一)逗号分隔 | 留空 = 每天;仅「每天定时」生效 |

⚠️ 注意:

- **「上次运行」包含手动与 API 触发** —— 手动跑过一次,当天的定时就不会再跑;间隔模式也会因此顺延
- **失败也会写「上次运行」**,不会每 60 秒重试失败任务;要看失败原因请用「结果推送」或运行列表
- **同一仓库永远串行**:排队中或运行中的仓库会被跳过,等它结束后的下一次扫描再判
- 清空评审数据会连游标与「上次运行」一起抹掉 → 定时仓库会立刻重新到期(相当于重新开始)

## 评出问题后通知谁

评审**发现了意见**时(0 条意见不打扰人),有两条独立的去向:

| 去向 | 发给谁 | 需要什么 |
|---|---|---|
| **提交人** | 被评提交的 **git 作者邮箱**(`git log -1 --format=%ae`)—— 可能是写代码的人,哪怕他不是网关成员 | 管理员在「通知设置」里配好 SMTP |
| **仓库成员** | 该仓库成员名单里的人,走**他们各自**在「我的用量 → 通知设置」里配的渠道(飞书/钉钉/企微/Server酱/Bark/邮箱) | 成员自己配渠道;邮箱还需管理员配 SMTP |

通知正文含:仓库、分支、提交短 SHA 与作者、**前 5 条意见的摘要**(文件:行 + 一句话),以及「完整结果去我的用量页看,或直接问 MCP」。

两个开关(高级参数里,默认都开):`notifyCommitAuthor` 控制是否发提交人,`notifyMembers` 控制是否发仓库成员。
它们与「结果推送」(`notifyOn`)是**两回事**:`notifyOn` 管的是**管理员自己**那几个渠道(飞书/钉钉/…),按「每次/仅失败/不推送」推系统事件。

⚠️ 被评提交的作者取自**评审时那次 git log**;如果仓库是浅克隆或作者信息缺失,取不到就只发成员、不发提交人,不会因此让评审失败。

## 预算与守卫

| 参数(高级参数里) | 默认 | 范围 | 作用 |
|---|---|---|---|
| 当日 token 预算 | `0`(不限) | 0 ~ 20 亿 | **所有仓库合计**,按北京时间当日 00:00 起算 |
| 单仓库磁盘上限(MB) | `2048` | 64 ~ 102400 | 工作区里该仓库目录超限 → 拒绝入队并推送通知 |
| 单次 token 预算 | `2000000` | 0 ~ 2 亿 | 单次评审交给 OCR 的预算参数 |
| 记录保留天数 | `90` | 1 ~ 3650 | 超过的运行记录被自动清理 |
| 每仓库保留运行数 | `50` | 1 ~ 1000 | 每仓库只留最新 N 条(与天数取「或」,谁先命中删谁) |
| 全局并发任务 | `2` | 1 ~ 4 | 同时在跑的评审数上限 |
| 单任务超时(分钟) | `30` | 2 ~ 240 | 超时判 `超时`,游标不推进 |
| 结果推送 | 每次推送 | 每次 / 仅失败 / 不推送 | 走「通知设置」里已配好的渠道 |

预算用尽的两种表现:

```text
手动 / API / MCP 触发 → 仍然受理,但落一条状态为「已跳过」的记录(说明为什么没跑)
定时扫描            → 静默跳过,不写记录(否则 60 秒一条会把表刷爆),每天只在日志里提示一次
```

## 维护与清空

设置页「代码评审」最下面的「维护」卡片:

| 操作 | 做什么 | 安全性 |
|---|---|---|
| 立即清理 | 按上面的保留设置删历史运行与报告文件,**不动游标** | 安全,随时可点;默认每天也会自动跑一次 |
| 清空数据 | 统计 + 意见 + 游标全清,报告文件删除,**保留仓库定义与引擎配置** | 破坏性:需要**管理员密码**,且会自动先备份 `config.json` 与数据库 |
| 连工作区一起删 | 在「清空数据」基础上再删 `code-review-workspaces/`(拉下来的代码副本) | 同上;删掉只是下次评审要重新 clone |

## 自检

设置页「运行自检」一次列出「为什么跑不起来」,逐项给结论与处理建议:

`OCR 引擎` · `git 版本` · `评审方案` · `方案真实 Key` · `模型` · `端点回环` · `方案已钉住` · `模型可用` · `评审账号` · `工作区可写` · 每个仓库一条(上次运行时间、状态、定时期、是否已拉取、在线触发开关、连续失败次数)

只探测不修改配置。任一必填项不通过时整体结果为「未通过」,条目里的 `hint` 就是要做的事(例如方案没有真实 Key → 评审会 403)。

## 结果怎么看

面板顶部是**引擎状态条**(绿灯 + OCR / git 版本 + 工作区占用),下面是**触发卡片**:选仓库 → 点「开始评审」。触发卡片下方一行小字讲清了增量口径:首次只评最新一个 commit,之后按「上次评到 → 现在 HEAD」的增量,不会整个仓库重跑。

工作区列表每行是一条评审记录,左侧色条按状态着色:**绿**=成功、**墨绿(高亮)**=进行中(排队/同步/评审/解析)、**橙**=完成有警告、**红**=失败/超时、灰=已跳过。行内含 `时间 | 范围(短 SHA) | 状态 | 文件数 | 意见数 | token | 耗时`;非手动的触发方式(schedule/api)会额外标一个小标签。

每行下面还有三样「证明它真干了活」的信息:一句**结论**(人话,见下)、**被评文件**的文件名(超过 3 个显示 `+N`)、以及失败时的错误摘要。运行列表上方有**搜索**(仓库名/结论/错误)与**状态过滤**,记录一页 15 条、可翻页。

点「**详情**」以**弹层**打开(不再堆在列表下面,信息再多也不用来回滚页面),弹层内含:

- 顶部一行摘要:范围(单提交/增量 + 短 SHA)、提交人、意见数、文件数、token、耗时;右上角「导出报告」
- **事实表**:结论、评审范围、提交人、模型、引擎动作(读了多少文件/检索多少次)、两个 token 口径、耗时
- **本次选取的文件清单**(0 意见也列出)
- **评审意见列表:带搜索(文件路径/问题内容)与分页,每页 20 条** —— 意见几百条时只渲染当前页,不卡
- 弹层支持点遮罩空白处或按 Esc 关闭

「我的用量」页的代码评审详情是同一套弹层(成员视角,无导出按钮),运行记录同样有搜索。

### 结论那句话怎么来的

`note` 由**网关**按已知事实生成(不是直接透出引擎的英文 message),所以「已跳过」一定会说清是哪种跳过:

| 情况 | 结论文案 |
|---|---|
| 增量评审有改动 | `增量评审完成:选取 N 个文件,提出 M 条意见`(M=0 时写作「未发现问题」) |
| 单提交评审 | `单提交评审完成:选取 N 个文件,…` |
| 范围为空(游标已在 HEAD) | `自上次评审以来没有新提交(范围为空),本次无需评审` |
| 引擎没选中任何条目 | `没有可评审的改动(引擎未选中任何条目)` |
| 超出当日预算 | `超出当日 token 预算` |

⚠️ **「已跳过」最常见的意思是「没有新提交」**,不是出错:评审是增量的,游标已停在 HEAD 时再点一次,范围就是空的 —— 此时引擎不会调用模型(实测 0 请求、0 token),只是记一条「无新提交」。想让它评点东西,先 push 新提交。

### 被评文件 / 引擎动作是什么

- **被评文件**来自引擎的 `groups`(它实际入选评审的文件路径),落库在 `files_json`,报告与详情都会列出。**即使 0 条意见也会列出**——这就是「它到底看了哪些文件」的直接证据
- **引擎动作**来自 `tool_calls`(读文件 / 代码检索的调用次数与失败数),落库在 `tool_calls_json`。它和「意见 0 条」合起来才能说明「读了、看了、没挑出问题」,而不是「啥也没干」

状态含义:`完成`(可能零意见)、`完成(有警告)`、`完成(有错误)`、`失败`、`超时`、`已取消`、`已跳过`(无新提交 / 超预算 / 引擎未选中条目,看结论那句话)。

详情页右上角的「导出报告」会下载一份**自包含单文件 HTML**(`code-review-run-<id>.html`):内容全部转义、不引用任何外部资源,可以直接发群或存档。报告里同时标注本次运行的范围、分支/提交、两个 token 口径、警告列表与全部意见。

**token 归因有两个口径**,详情页与报告都同时给出:OCR 自报的 token(`summary`),以及**网关侧实证** —— 评审 Key 在 `users` 表的请求数与 token 在本次运行前后的差值。两者可能有偏差(OCR 一次评审会发多次 LLM 请求,无法一一对应到单次运行),以网关侧为准来对账。

## CI / MCP 触发接口

管理员之外,成员可以拿**自己的虚拟 Key** 触发评审 —— 这是个**写操作**,会消耗你所在方案的配额。

```bash
# 触发单个仓库(仓库名或 8 位 id 都可以)
curl -X POST http://<网关>/api/code-review/trigger \
  -H "Authorization: Bearer jx-xxxx" -H "Content-Type: application/json" \
  -d '{"repo":"主仓库"}'

# 不带 repo = 触发**你名下**的全部可触发仓库(不是所有仓库)
curl -X POST http://<网关>/api/code-review/trigger -H "Authorization: Bearer jx-xxxx" -d '{}'
```

| 状态码 | 含义 |
|---|---|
| `202` | 已受理,返回 `runId`(评审在后台跑,客户端不必等) |
| `200` | 已受理但没真跑:与进行中任务合并(`deduped`)、超当日预算(`skipped`)、或一次触发多个仓库(返回 `results` 数组) |
| `401` | Key 无效 |
| `403` | 你不在**这个仓库的成员名单**里,或该仓库没开「允许在线触发」/已停用(错误文案会点名是哪个仓库、卡在哪一条) |
| `404` | 仓库不在白名单里 |
| `429` | 触发过于频繁 —— **每个 Key 60 秒只能触发一次**(管理员豁免成员名单,但不豁免限频) |

⚠️ **被拒的请求不消耗限频窗口**:403/404 之后改正再试是立刻可用的,不用等 60 秒。

MCP 侧两个工具(只对获授权的 Key 可见):

| 工具 | 参数 | 返回 |
|---|---|---|
| `code_review_list` | `limit`(最近多少次运行,默认 10) | **你名下的**仓库 + 各自上次状态/上次提交/连续失败次数 + 它们的运行记录(看不到别人负责的仓库) |
| `code_review_trigger` | `repo`(可选,缺省 = 你名下全部) | 同上面的接口,结果按工具结果返回 |

⚠️ 评审的是**已提交**的代码,不是工作区未提交的改动 —— CI 里请先 push 再触发。


## 面板上按次选分支

管理面板的触发卡片里有**仓库**和**分支**两个下拉:选中仓库后会拉出它的分支列表(默认分支排首位并自动选中),点「开始评审」就用这条分支。

- **只对本次生效**:不改仓库配置、不写回 `config.json` —— 仓库的默认分支还是设置页里那个
- 评审记录里会记下这次用的分支,详情与报告都能看到
- 分支列表来自 `git ls-remote --heads`(local 仓库走 `for-each-ref`),所以私有仓库要凭据能通才拉得到;拉不到时会退回显示「默认分支(未取到分支列表)」并提示原因,不会把触发卡死
- 设置页的仓库编辑器里也有「拉取分支」按钮:填完地址就能先看看有哪些分支,再决定默认评哪条

## 来源与拉取行为

| 来源 | 怎么填 | 评审前做什么 | 凭据 |
|---|---|---|---|
| **remote** | 线上仓库地址(`https://` / `ssh://` / `git@`) | 每次评审前 `git fetch` 该地址并 reset 到目标分支最新 | 公开仓库选「无凭据」;私有仓库填 HTTPS Token 或 SSH 私钥路径 |
| **local** | 服务器上仓库的**绝对路径**(如 `/Users/xxx/Project/my-app`) | 首次评审时从该路径 clone 一份到工作区;之后每次评审前从该路径 `fetch` 最新提交 | 不需要凭据(本机路径) |

- **填入只是登记白名单,不会立即拉取** —— 第一次触发评审(手动/定时/CI)时才 clone,之后每次评审前自动同步到目标分支最新
- ⚠️ 评审基于**已提交**的内容:本地仓库里未 commit 的工作区改动不会被评审 —— 想评什么就先 commit
- 本地路径要求:是一个 git 仓库(有 `.git`)且至少有一个提交;克隆进工作区后你的原仓库不会被改动(评审在独立副本上进行)

### 先测连接再保存

编辑器里填好地址/分支/凭据后,不必先保存 —— 底部「**测试连接**」按钮直接拿**当前表单里的值**去验(remote 发一次 `git ls-remote`,local 检查路径存在且是 git 仓库),结果就地显示,填错能当场改。

- 测试用的凭据就是你此刻填的;**凭据留空**时会沿用该仓库已保存的原值(界面回显的是掩码)
- 已保存的仓库,表格行里也有「测试」按钮,结果以顶部浮层(toast)提示
- ⚠️ 容器部署时,`local` 路径填的是**容器内**路径 —— 测试报「路径不存在」多半是宿主机路径没挂进容器

## 评审范围(增量口径)

```text
首次评审:  --commit HEAD                       只评最新一个提交(避免大仓库首评烧穿套餐)
之后每次:  --from <上次评审到的提交> --to <HEAD>  等价 git merge-base(from,to)..to 的增量
历史被改写(上次的提交已不是 HEAD 祖先):自动回退为单提交评审,并在运行详情标注
游标推进:  success / completed_with_warnings / completed_with_errors / skipped 都推进;
          failed / timeout / canceled 不推进 —— 下次仍从上次成功处开始
```

游标存在数据库(`code_review_repo_state.last_commit`),不写 config。

## ⚠️ 注意与边界

- **代码片段会入库**:评审意见里的原代码与建议代码默认写入 SQLite(`storeComments: true`)。这是本系统第一次把源码内容落库;可在设置里关掉(只存统计),也可用「清空评审数据」整体清除。
- **磁盘占用**:每个仓库一份完整检出 + 评审产物(`code-review-workspaces/`,已在 `.gitignore` 里)。`perRepoDiskLimitMB`(默认 2048MB)是**每仓库**上限,超限拒绝入队并通知;可在设置页查看占用与清理。
- **工作区不是只读仓库**:系统会 `git reset --hard FETCH_HEAD` 强制同步到目标分支,**不要**把手工改动放在这里。
- **凭据**:HTTPS Token / 私钥路径存在 `config.json`(与方案真实 Key 同一信任级别),只经子进程环境变量传给 git,**不进命令行参数、不进日志**;界面与接口只回掩码。HTTPS Token 走一个临时 askpass 脚本喂给 git,用户名默认 `oauth2`(GitHub / GitLab / Gitea 等对 HTTPS Token 认证的用户名不敏感,只要非空即可)。
- **子进程环境是白名单重建的**:`ANTHROPIC_API_KEY` / `OPENAI_API_KEY` / `*_TOKEN` 等一律不传给 OCR —— 否则它可能绕开指定的 provider 直连上游,导致计费与审计双失守。
- **被拒绝的用法**:非 `https/ssh/git@` 的仓库地址(含 `file://`、`ext::`)、以 `-` 开头的地址或分支、非十六进制的提交号、把端点配成非回环地址 —— 都会被拒绝。
- 定时任务按 **间隔** 或 **每天某时刻 + 星期** 判定(见上文「定时评审怎么算到期」);同一仓库同时只会有一个任务(串行),避免 git 工作树被并发写坏。
- **触发是写操作**:成员用虚拟 Key 触发一次评审就会真的消耗套餐额度,且评审结果入库 —— 只把确实需要的人加进仓库成员名单。
