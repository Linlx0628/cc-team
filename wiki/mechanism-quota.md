# 配额与计费机制

本页解释系统**怎么算、怎么扣**每一笔用量。阅读前提：先看[核心概念](concepts.md)里的「方案 / 额度池 / 配额倍率」。

## 一个请求进来，经过哪些检查

请求（以协议默认入口 `/v1` 或 `/v1/responses` 进来）按顺序通过以下关卡，任何一道不过就返回错误：

| 顺序 | 检查 | 超限行为 |
|---|---|---|
| 1 | 入口识别、虚拟 Key 有效性 | 404 / 403 |
| 2 | 组成员直连限制（开启「限制直连」后，组内方案禁止 `/后缀` 直连） | 403 |
| 3 | IP 限流（**120 次/分钟/IP**，硬编码，60 秒滚动窗口） | 429，Retry-After: 60 |
| 4 | 用户归属校验（Key 是否分配给该方案） | 403 |
| 5 | 每用户频率（`rateLimitPerMinute`，默认 **60 次/分钟**，滚动窗口） | 429，Retry-After: 60 |
| 6 | 每用户并发（`maxConcurrentPerUser`，默认 **5**） | 429，Retry-After: 1 |
| 7 | **用户周期点数预算**（仅对该成员启用时；只判一次，与候选方案无关） | 429 `points_exceeded`，**不进入 failover** |
| 8 | **逐候选方案**依次检查：模型白名单 → 熔断器 → **配额** | 见下 |

第 7 步是核心：系统按生效方案组的顺序逐个方案尝试，每个候选都要过三道门，任何一道不过就**跳到下一个候选**（failover），最后一个候选也不过才把错误返回给你。

> ⚠️ **配额是逐方案检查的**：同一个用户的配额会在每个候选方案上各判一次——因为不同方案的倍率、额度池可能不同。429 文案里显示的是「实际会记账的那个模型」的倍率，不是方案默认。

## 额度池：配额的唯一载体

**配额存在「额度池」上，不直接存在方案或用户身上**（方案级每日限额是旧版设计，已迁移进池）。运行时判定：

```text
baseLimit = 用户在该池设置的个人配额（>0 时）
          否则 = 池级每日配额
limit     = baseLimit + 当日临时加量(bonus)
used      = 当日计权用量(weighted_tokens 求和) − 当日重置基线
允许请求 ⇔ used < limit
```

- 两者都没设（≤0）→ **不限制**，签到/加量等临时操作会提示「无需加量」
- 同一池内多个方案**共享**同一份额度：从方案 A 用掉的，从方案 B 的入口看也一样少
- 一个用户可以访问多个池（多个方案分属不同池时），各池独立计账、独立签到/加量

## weighted_tokens：配额货币的完整公式

每次响应完成后记账，公式：

```text
rate = 当前倍率（峰谷判定 + 模型单独定价，见下节）

# 两种协议同一公式 —— 存储口径已对齐（2026-09-18 起）
# 落库的 input_tokens 一律 = 新鲜输入（Responses 上游折叠在 input 里的缓存
# 命中在 recordUsage 落库前剥掉，缓存只进 cache_read 列；历史数据一次性迁移）
billableInput = input_tokens + round(cache_read × cacheReadQuotaRate)   # 仅 Responses 方案 cache_read 参与
weighted      = round((billableInput + output_tokens) × rate)
```

各 token 类型的处理：

| 类型 | 计入配额基数？ | 说明 |
|---|---|---|
| input_tokens | ✅ 全额 | **各协议均为新鲜输入**（Responses 的缓存命中已剥出，见上） |
| output_tokens | ✅ 全额 | |
| **cache_creation（缓存写入）** | ❌ **不计入** | 只落库存档、进报表，不参与计权 |
| cache_read（Anthropic） | ❌ **不计入** | 上游单独报字段，天然在配额基数之外 |
| cache_read（Responses/OpenAI） | 默认不计 | 存储对齐后已不在 input 里；`cacheReadQuotaRate` 决定按多少比例计回 |

`cacheReadQuotaRate`（仅 Responses 协议方案有意义）：**默认 0 = 缓存命中完全免费**；0~1 部分计入；1 = 全额计费（旧口径）。守卫：仅当 `0 < cache_read ≤ 上游原始 input` 时才剥离——上游返回的缓存读大于 input（说明已排除过缓存）时视为口径已对齐，不再处理。

### 数字示例

**Anthropic 方案**，低谷倍率 ×0.5，某次响应：input 10,000 / output 4,000 / 缓存写 50,000 / 缓存读 80,000：

```text
weighted = round((10000 + 4000) × 0.5) = 7000
```

本次扣配额 **7000**——缓存写、缓存读都不进公式；但报表和图表显示全部真实 token。

**Responses（Codex）方案**，倍率 ×1.0，`cacheReadQuotaRate = 0.1`，某次响应：上游报 input 100,000（其中缓存命中 90,000 折叠在内）/ output 2,000：

```text
落库 input = 100000 − 90000 = 10000（新鲜输入）
billableInput = 10000 + round(90000 × 0.1) = 19000
weighted      = round((19000 + 2000) × 1.0) = 21000
```

若 `cacheReadQuotaRate` 为默认 0，则 weighted = 12,000——这就是 Codex 重放式对话（每轮重发全对话、缓存命中率极高）在默认配置下几乎不扣配额的原因。

> ⚠️ **记账时刻是响应完成时刻**：跨峰谷边界的长请求按「结束时刻」的倍率定价。倍率**写时冻结、永不追溯**——事后改倍率只影响之后的请求，历史不重算。

## 点数预算模式（可选）

> 默认关闭。开启后，该成员从「按额度池的每日配额」切换为「按人的周期点数预算」。两种模式**互斥**：启用了点数的成员，个人日配额不再生效（池级日限额仍可作为团队护栏）。

### 配置在哪里

设置页左栏「**点数预算**」可以逐人启用、填预算、选周期、批量设置。底层配置在 `config.json`：

```json
"pointSettings": {
  "defaultPeriod": "month",
  "allowSelfSelect": true
},
"pointBudgets": {
  "jx-完整虚拟Key": {
    "enabled": true,
    "budgetPoints": 5000,
    "period": "month",
    "startsAt": "2026-10-01",
    "note": "",
    "billingFactor": 1
  }
}
```

| 字段 | 默认 | 规则 |
|---|---|---|
| `enabled` | 未配置=`false`；条目已存在但省略=`true` | 关闭 = 该成员继续走旧的池配额；管理端保存时总会写布尔值 |
| `budgetPoints` | `0` | 整数，范围 **0 ~ 10,000,000**；`0` 且启用 = 该成员所有请求都被拒绝 |
| `period` | 跟随 `pointSettings.defaultPeriod`（默认 `month`） | `day` / `week` / `month` |
| `startsAt` | 管理端保存时=当天；手写配置省略=周期起点 | `YYYY-MM-DD`，不能晚于今天；中途启用只从这一天起算 |
| `note` | 空 | 最多 200 字，仅管理端备注 |
| `billingFactor` | `1` | **用户计费系数**，0.10 ~ 10.00；只乘点数，不乘额度池 |

- 预算按**完整虚拟 Key** 键控；换 Key = 新成员，需要重新设置预算。
- `pointSettings.allowSelfSelect=false` 时成员页隐藏「请求方案」选择器，成员写接口返回 403。

### 判定公式

```text
periodStart   = 北京自然日 / 周一 / 自然月 1 日的 00:00 起点
windowStart   = max(periodStart, startsAt || periodStart)
billableBase  = 新鲜输入 + 缓存读×0.1 + 缓存写×0.01 + 输出
pointRate     = pointModelRates[实际模型]（有覆盖）
                否则 pointPeakRate / pointOffPeakRate（留空 = 1.00）
factor        = 用户 billingFactor × 方案 pointsBillingFactor
                （单级 0.10~10.00，乘积封顶 100）
billingWeighted = round(billableBase × pointRate × factor)
usedWeighted  = SUM(point_usage.billing_weighted_tokens)
                WHERE user_key = 该成员 AND granularity='day'
                  AND bucket_start BETWEEN windowStart AND 今天
limitWeighted = budgetPoints × 10,000
允许请求 ⇔ usedWeighted < limitWeighted

usedPoints    = round(usedWeighted / 10,000)   // 只用于展示
```

- **1 点 = 10,000 计费计权 token**。点数是**另一套价目**：`weighted_tokens` 继续按额度池倍率算、供池配额使用；`billing_weighted_tokens` 按点数倍率 × 用户系数 × 方案系数算，只供点数使用。两者都在响应完成时冻结。
- 点数倍率与额度池倍率**完全独立**：额度池高峰 0.5、点数高峰 3.0 可以同时存在。点数倍率留空按 **1.00**，不沿用额度池倍率。
- 历史行没有 `billing_weighted_tokens` 时回退到 `weighted_tokens`，不重算历史；上线前的用量按点数倍率 1.00 计。
- 判定用 `usedWeighted` 的精确值；页面上的「已用 X 点」是四舍五入后的展示值，可能差 1 点。
- 点数是**用户级、跨方案**的：同一个成员从哪个方案入口用，扣的都是同一份预算。
- 成员总预算在候选方案循环**之前只做一次**；耗尽直接 `429 points_exceeded`，不会因为换一个方案就绕过。方案级上限在候选循环里逐方案判，见下节。
- 改预算立即生效；改点数倍率/系数只影响之后的请求，已经落库的 `billing_weighted_tokens` 不变。
- 管理员还可以发**临时点数**（带到期日，计入本期预算）或**重置本期已用**（记基线，不删历史）；见下节。

### 周期与重置

| `period` | 起点 | 下一次重置 |
|---|---|---|
| `day` | 当天 00:00（北京） | 次日 00:00 |
| `week` | 周一 00:00（北京） | 下周一 00:00 |
| `month` | 自然月 1 日 00:00（北京） | 下月 1 日 00:00 |

- 没有定时清零任务：日期窗口一变，旧周期自然不再被统计。
- **未用完的点数不结转**（一期明确不做 carryover）。
- 中途启用：从 `startsAt` 起算，之前的历史用量不扣。
- 中途把预算改到低于已用：**立即生效**，下一次请求就会被拒；页面会显示「已超出 X 点」。
- 建议在周期边界调整周期类型；中途从「月」改「周」会立刻按新周期重算展示，历史用量本身不重算。

### 用量留存

每个成功请求会对**启用点数预算**的成员同时写入 `point_usage` 的 day / week / month 三行，金额是响应完成时冻结的 `billing_weighted_tokens`（已含点数倍率、用户系数、方案系数）：

| 字段 | 含义 |
|---|---|
| `user_key` | 完整虚拟 Key |
| `granularity` | `day` / `week` / `month` |
| `bucket_start` | 日=当天；周=周一；月=自然月 1 日（均为北京日期串） |
| `billing_weighted_tokens` | 累计点数计权，读取时 ÷10,000 得到点数 |
| `requests` | 累计请求数 |

- 只为启用点数的成员写入；未启用时不写，避免把额度池计权误当点数。
- 从启用后开始累计，**不回溯**启用前的历史；停用后已有行保留，便于回看。
- 查询：`GET /api/point-usage?granularity=day|week|month&key=<完整Key>&from=YYYY-MM-DD&to=YYYY-MM-DD&limit=400`（管理员鉴权；不传 `key` 返回全部成员）。返回 `points` 已按 10,000 折算。
- 这张表同时服务统计与**点数预算判定**：`checkPointBudget` 只聚合 `point_usage` 的 day 桶，避免把“非点数用户 billing=weighted”的历史额度池用量算进点数。`usage_daily` 仍只负责额度池判定。
- 另有一张逐请求凭证表 `point_requests`：每个成功请求一条，字段只含方案、模型、输入/输出/缓存、额度池计权、点数计权、点数倍率和完成时间，不含 prompt/响应正文。它只用于成员核对“这次扣了多少点”，不参与预算判定；按 `id` 自增游标分页，90 天自动清理，单条写入与 `point_usage` 在同一个事务里完成，崩溃不会出现“汇总加了、明细没加”的半条账。

### 方案级点数上限（可选）

除了成员的总点数预算，还可以在**方案设置**里给单个方案加两层上限，防止某个人或所有人把某个方案吃光：

| 配置 | 位置 | 作用 |
|---|---|---|
| 本方案总上限 | 方案表单 →「方案点数上限」 | 所有成员在该方案上的点数合计上限 |
| 每成员上限 | 同一张表的人名行 | 某个成员在该方案上的点数上限 |

```text
profileUsed  = SUM(usage_daily.billing_weighted_tokens)
               WHERE profile = 方案 suffix
                 AND user_key = 成员（总上限时省略）
                 AND date BETWEEN max(periodStart, startsAt) AND 今天
允许 ⇔ profileUsed < limitPoints × 10,000
```

- 只对**启用点数预算**的成员生效；旧额度池成员完全不看这个配置。
- 与总预算**叠加**：用某方案时同时扣总预算和该方案上限，任一耗尽都不能再用该方案。
- 自动路由：某方案上限耗尽 → **跳过**该方案，继续试下一个候选；全部候选都满 → 429。
- 手动首选/`/后缀` 直连：硬选择，上限耗尽直接 429 `profile_points_exceeded`，不拿别的方案顶替。
- 周期独立（日/周/月），`startsAt` 默认保存当天；中途加限制不会被当月历史用量立刻拦住。
- 方案上限只统计 `billing_weighted_tokens`，不会把额度池历史算进来。
- 临时点数只加成员总预算，不自动加方案上限；重置本期已用也不自动重置方案上限。
- 方案上限的 429 文案会写明是「总上限」还是「你在这个方案的上限」，并带周期与恢复时间。

### 临时点数与重置已用

管理员在「点数预算」表格的操作列有两个按钮：

| 操作 | 写入 | 判定方式 | 注意 |
|---|---|---|---|
| **临时点数** | `point_grants(user_key, points, starts_at, expires_at, note, revoked_at)` | 当天在 `[starts_at, expires_at]` 内的未撤销记录求和，加到本期预算 | 到期后自然失效，不需要定时任务；可撤销；不修改基础预算，也不结转 |
| **重置已用** | `point_period_ops(user_key, period_start, reset_baseline_weighted, reset_at)` | `used = max(0, point_usage 本期累计 − reset_baseline_weighted)` | 只改判定基线，不删除 `point_usage` / `point_requests`；同一周期再次重置会写当前累计量，已用重新归零 |

- 临时点数和签到一样是**本期加量**，不会写回 `config.pointBudgets`；周期结束后自动不再计入。
- 临时点数默认 `starts_at = 今天`，`expires_at` 必须 ≥ 今天且按北京日期、含当天；例：`expires_at = 2026-10-31` 在 10-31 23:59 前有效。
- 重置只影响「本期已用」和剩余/429 判定；成员请求明细仍保留重置前的记录，管理员审计也会记录基线。
- 重置与临时点数都只对**已启用点数预算**的成员生效；对旧额度池成员无效。
- 生产分析 SQL 见仓库 `docs/point-budget-analysis.sql`；它只读 `point_usage` / `point_grants` / `point_period_ops`，不会改数据。

### 点数倍率与计费系数

方案设置页的「**点数倍率**」区只影响点数，和上面的「配额倍率」互不影响：

| 配置 | 字段 | 默认 | 说明 |
|---|---|---|---|
| 方案点数高峰倍率 | `pointPeakRate` | 留空 = 1.00 | 高峰时段按它乘 |
| 方案点数低谷倍率 | `pointOffPeakRate` | 留空 = 1.00 | 低谷时段按它乘 |
| 按模型点数倍率 | `pointModelRates` | 空 | 键是**实际模型名**；留空档位 = 1.00 |
| 方案计费系数 | `pointsBillingFactor` | 1.00 | 0.10~10.00，只乘点数 |

成员级再乘一个「用户计费系数」：`pointBudgets[完整Key].billingFactor`，默认 1.00。最终：

```text
点数计费输入 = 新鲜输入 + 缓存读 × 0.1 + 缓存写 × 0.01
点数计权 = round((点数计费输入 + 输出) × 点数倍率 × 用户系数 × 方案系数)
```

缓存系数全平台统一为读 0.1、写 0.01，不可按方案单独配置；它再跟随当前点数倍率：点数倍率 1.00 时缓存读按 0.10、缓存写按 0.01；倍率 2.00 时读 0.20、写 0.02。只影响点数，不改变额度池的 `weighted_tokens`。

- 单级系数范围 0.10~10.00，用户×方案乘积封顶 100。
- 点数倍率/系数**只对启用点数预算的成员生效**；旧额度池成员完全不看这些字段。
- 成员页只展示点数倍率与最终扣点，不展示用户/方案系数；管理员在「点数预算」表格与方案表单里配置。
- 改点数倍率/系数只影响之后的请求；已落库的 `billing_weighted_tokens` 不重算。

### 逐方案「支持点数计费」准入

方案表单里的「支持点数计费」是**方案级**开关（`config.profiles.<name>.pointsEligible`，缺省 `true`）。它只约束**启用点数预算的成员**：

| 入口 | 未开放点数计费的方案 |
|---|---|
| 默认入口自动路由 | 不进入候选（`getAvailableDefaultProfiles` / `getAvailableResponsesProfiles` 都过滤） |
| `/后缀` 直连 | 403 `points_profile_not_allowed`（在候选循环前拦截） |
| 成员手动首选方案 | 保存时 403；不可用方案在概览中红色且不可选；已设置过的旧首选变为不可用时，请求直接失败并提示原因，不会自动切换 |
| `/v1/models` 探测 | 不返回该方案；显式后缀 403 |
| 旧额度池模式成员 | 完全不受影响 |

> ⚠️ 关闭开关**不会**删除方案、不会改上游或模型别名，也不会影响已有历史用量；只是让点数成员“看不到、进不去”。

### 和额度池的关系

| 场景 | 判定 |
|---|---|
| 成员启用点数，池级日限额为空/0 | 只受点数预算约束 |
| 成员启用点数，池级日限额 > 0 | 先过点数，再过池级日限额（团队护栏） |
| 成员未启用点数 | 完全走旧的「个人日配额优先 / 否则池日配额」 |

- 点数模式下，该成员在池里的**个人日配额被忽略**；池级 `dailyTokenLimit` 仍生效。
- 点数成员的「签到」改为发点数（直接加到本期预算）；「申请加量」仍返回 409，提示改用「点数预算」调整。池级护栏仍会看到旧的池签到/加量。

### 超限 429

```json
{
  "type": "error",
  "error": {
    "type": "points_exceeded",
    "message": "本月点数预算已用尽：已用 5000 点 / 预算 5000 点……",
    "points": { "usedPoints": 5000, "limitPoints": 5000, "period": "month", "periodStart": "2026-10-01", "periodEnd": "2026-10-31" },
    "usageUrl": "http://<host>/usage/<key>"
  }
}
```

响应头带 `Retry-After`（到下一周期起点的秒数）与 `X-CC-Points-Reset`（重置时刻 ISO）。与旧的 `quota_exceeded` 是两个不同错误类型：前者是个人周期预算，后者是池日配额/团队护栏。

### 成员自选「请求方案」

- 成员可在「我的用量 → 概览」的「请求方案」卡片里，对 Anthropic / Responses 两条协议各选一个**首选方案**；选择存在 `member_profile_preference` 表，按完整虚拟 Key 键控。
- 首选是**手动覆盖**：只要该方案仍分配给成员、协议匹配、且勾选了「支持点数计费」，就会被插到候选列表第一位，**不要求它当前在自动调度组里**；默认自动仍按方案组调度。首选被限流/熔断/额度耗尽/未分配 Key 时，请求直接 429/503 并提示原因，**不会 failover 到后续候选**；成员需改选方案或等待恢复。
- 首选优先于粘性会话；首选不是组头时，粘性绑定的「基准头」也跟着变，避免每轮都被误判为 failover 而清掉缓存亲和。
- 改首选会清掉该成员该协议的粘性绑定，从下一个**新会话**开始生效；已在跑的长会话可能还会走旧绑定。
- 这不是「任选模型」：模型仍由方案的模型别名决定；首选只决定请求先落到哪个方案。

### 数字示例

预算 `5000 点 / 月`，`startsAt=2026-10-01`，10-20 时已用 `32,000,000` 计费计权 token：

```text
limitWeighted = 5000 × 10000 = 50,000,000
usedPoints    = 32,000,000 / 10000 = 3200
remaining     = 5000 − 3200 = 1800 点（18,000,000 计费计权）
```

同一天再用一次 `1,000,000` 原始 token、点数倍率 `3.0`、用户系数 `2`、方案系数 `1.5` 的模型：

```text
billingWeighted = 1,000,000 × 3.0 × 2 × 1.5 = 9,000,000
扣点            = 900 点
```

额度池那边仍按额度池倍率（例如 1.0）记 `1,000,000 weighted_tokens`，两边互不影响。

> ⚠️ **预算是请求前判定的**：单次请求可能把余额用超（例如剩 10 点、这次要 30 点，仍会放行）；**下一次**请求才会被拒。并发请求也可能同时越过边界，这是有意的「不因预算而中断正在跑的任务」。
>
> ⚠️ **点数不是钱**：`coding_plan` 方案下它只是内部稀缺容量单位；`on_demand` 方案下才近似成本。不要把它当账单/充值余额。
>
> ⚠️ **预算为 0 且启用 = 全拒**。想「暂停点数、回到旧配额」应把 `enabled` 关掉，而不是把预算填 0。
>
> ⚠️ **不结转**会让部分成员在周期末突击消耗；如果这是问题，下一期再加「结转上限」或「提前预警」，不要靠改小预算硬压。

## 峰谷倍率怎么选

```text
inPeak  = 当前时刻(北京时间)落在方案的 peakHours 内
rate    = 有该模型的单独定价 → inPeak ? 定价.peak : 定价.offPeak
        否则                 → inPeak ? 方案峰倍率 : 方案谷倍率
```

- **模型单独定价按「真实上游模型名」匹配**（不是别名），精确匹配优先，其次大小写不敏感比对
- 高峰时段支持跨午夜（如 22:00–02:00：`分钟 ≥ 22:00` 或 `分钟 < 02:00` 命中）
- **peakHours 不配置 = 全天按低谷倍率**（设置页会警告）
- 倍率范围 [0, 10]，两位小数；**锚定约定：×1.0 = 高峰时段一个 token 按方案默认价**
- 配额倍率工作区/价目表里的「×N 后转入低谷」提示，取的是**下一个会翻转峰谷状态**的时刻

## 临时加量 / 重置 / 撤销：到底改了什么

三个操作都写在「当日操作表」里，键 =（池, 用户, 北京日期）——**日期一变旧行查不到，自然失效**，无需回滚任务：

| 操作 | 精确语义 |
|---|---|
| **加量** | **设置/覆盖**当日 bonus 值（不是累加！再加 1 万是「改成 1 万」不是「+1 万」）。生效：`limit = baseLimit + bonus` |
| **重置** | 记录当日已用计权量为**基线**，此后 `used = 当日用量 − 基线`，即配额回满。统计行不删，报表照常显示真实用量 |
| **撤销** | 删除当日该用户的全部手工痕迹（加量和基线一起清），回到系统自然状态 |

**累加的例外**：签到奖励和「加量申请发放」是**累加**到 bonus 上的（`bonus = 原bonus + 奖励`），与手工加量共存。

> ⚠️ 手工加量作用于**整个池**：给方案 A 加量，同池的方案 B 也一起生效（否则用户换条路由照样被挡）。

## 签到与加量申请的精确规则

**每日签到**：

```text
amount = min + floor(random() × (max − min + 1))   # [min, max] 均匀整数
```

- 默认区间 [10,000, 100,000]；随机数**只抽一次**，用户可访问的**每个池各加同一份**（不是每池独立抽）
- 每天一次（北京日期键）；连续天数（streak）纯展示，无奖励加成；未签时从昨天起算（「今天还能保住的连续」）

**加量申请**：

- 提交：每北京日 1 次；**提交不占每周次数**——只有管理员处理过（通过/拒绝）的申请才计数
- 每周上限默认 **3**（可配 0–1000），周窗口 = 本周一 00:00（北京时间）
- 池不限量时拒绝申请（「无需申请加量」）
- 管理员「发放加量」= 发当日临时加量（累加）并自动标记已处理

## 自动配额调整（AUTO）完整算法

> ⚠️ 三个隐藏约束，配置前必须知道：
> 1. 只评估**默认方案所属的额度池**，其他池不受影响
> 2. 只评估**设置了个人配额**的用户（只吃池公共配额的用户永远不会被自动上调）
> 3. **没有定时器**——每天第一次有请求进来时惰性评估一次（每北京日一次）

参数（设置页 → 全局配置 → 自动配额调整）：

| UI 名称 | 字段 | 默认 | 范围 |
|---|---|---|---|
| 启用自动调整 | `autoQuotaAdjust.enabled` | 关 | — |
| 评估周期（天） | `evaluationPeriodDays` | 5 | 3–30 |
| 命中阈值 | `hitThreshold` | 0.9 | 0.5–1 |
| 触发命中率 | `triggerRate` | 0.9 | 0.3–1 |
| 增长率 | `increaseFactor` | 1.15（+15%） | +5%~+100% |
| 安全系数 | `safetyFactor` | 1.3 | 100%–200% |
| 单次最大增幅 | `maxIncreaseFactor` | 2.0 | ≥1.1 |
| 配额上限 | `maxAutoQuota` | 10,000,000 | ≥0 |
| 冷却天数 | `cooldownDays` | 3 | ≥1 |

算法（对池内每个用户）：

```text
dates    = 昨天往前 P 个北京日期（不含今天）
dayUsage[d] = 该用户当日按池全部成员方案聚合的计权用量(weighted_tokens)

命中日   = dayUsage[d] > 0 且 dayUsage[d] ≥ userQuota × hitThreshold 的天数
命中率   = 命中日数 ÷ P          ← 分母是周期总天数！
命中率 < triggerRate → 不调整

avgDaily = 总用量 ÷ 有用量的天数   ← 这里的分母才是有用量天数
methodA  = userQuota × increaseFactor        # 稳健路线：现有额度 × 增长率
methodB  = avgDaily × safetyFactor           # 激进路线：真实日均 × 安全系数
newQuota = min( max(methodA, methodB),
               userQuota × maxIncreaseFactor,
               maxAutoQuota )
newQuota ≤ userQuota → 放弃
生效: 永久改写该用户在池内的 dailyTokenLimit（直到下次调整）
```

### 数字示例

个人配额 1,000,000，默认参数（P=5, hit=0.9, trigger=0.9, growth=1.15, safety=1.3, maxInc=2.0）：

- 近 5 天计权用量：900k、950k、880k、920k、0（周三没来）
- 命中日 = 4 天（≥900k）；命中率 = 4÷5 = 0.8 < 0.9 → **不调整**（尽管几乎天天顶满，因为没用的那天也占分母）
- 若命中率达标：methodA = 1,000,000×1.15 = 1,150,000；methodB = (900k+950k+880k+920k)÷4 ×1.3 = 1,191,750 → 取大者 1,191,750，未超 2,000,000 上限 → 新配额 **1,191,750**

> ⚠️ 评估一律用**计权**列：若用真实 token，×0.5 的低谷折扣会被复利放大。调整写 `quota_adjust_history`（只留最近 100 条）+ 系统审计，与临时加量互不干扰。

## 超限 429 长什么样

所有候选都因配额失败时，返回 429：

```json
{
  "error": "今日配额已用尽：7400/8000（计权）…",
  "type": "quota_exceeded",
  "quota": {
    "used": 7400, "limit": 8000, "remaining": 0,
    "source": "个人配额", "rawUsed": 14800, "discounted": 7400, "rate": 0.5
  },
  "usageUrl": "http://服务器地址/usage/你的虚拟Key"
}
```

（`rawUsed` 与 `used` 的差额是倍率/缓存抵扣的展示口径，按当日真实与计权比例折算。）

响应头 `Retry-After` = 距**下一个北京时间零点**的秒数。错误消息逐行包含：

1. 计权用量与限额（池共享时注明「额度池『xx』，N 个方案共用」）
2. 真实 token 与抵扣差额（`实际 token 14800，已抵扣 7400`）
3. 当前时段倍率（`高峰 ×1.5` / 模型单独定价标注 / `· 20:00 后转入低谷 ×0.5`）
4. 固定尾行：`额度将于北京时间次日凌晨重置。查看用量详情: {usageUrl}`

每日零点重置不是定时清零，而是**日期键不再匹配**——今天的用量行存的是今天的北京日期，零点后查的是新日期，自然从零开始。

## 上游官方额度（与本地配额无关）

本站的配额是**自己扣的账**（额度池）；上游平台还有一本**服务商扣的账**（套餐窗口、账户余额）。两本账互不影响：

- 上游额度归零**不会**让本站拦截请求——本站只看额度池；反过来池子里配额充裕，也可能因为上游套餐用完而吃到上游 429
- 上游那本账在管理面板「**上游额度**」工作区查看（套餐窗口 + 账户余额），配置在设置页左栏底部的同名入口，细节见[上游额度 / 账户余额](upstream-quota.md)
- 上游没有额度接口的平台（腾讯云 TokenHub Coding Plan、腾讯 CodeBuddy）只能看控制台，或从报错反推（阿里云百炼 Coding Plan 2026-10-15 起走控制台网关能查到三个窗口）

上游没有额度接口时，「额度还剩多少」只能从 429 反推。几种 429 的区分：

| 现象 | 来源 | 后续 |
|---|---|---|
| `type: quota_exceeded`，正文含「今日配额已用尽」「额度池『xx』」 | **本站**额度池 | 加量 / 重置 / 等北京时间次日零点，与上游无关 |
| 腾讯云 `20097 hour\|week\|month allocated quota exceeded` | **上游**套餐 | 等对应窗口重置（5 小时滑动 / 每周一 00:00 / 订阅月到期时刻）；本站按套餐耗尽处理 |
| 阿里云百炼 `usage allocated quota exceeded`（含 hour / week / month） | **上游**套餐 | 同上 |
| 阿里云百炼 Token Plan 个人版 `429 insufficient_quota: Your token-plan quota has been exhausted.` | **上游** Token Plan 月额度 | 等订阅月重置（重置时刻看「上游额度」页那张卡的「重置」），或让账号买用量包 / 升档；本站按套餐耗尽处理 |
| 上游 `tpm rate limit exceeded`、智谱业务码 `1302` / `1305` | **上游**频率限流 | 瞬时突发，**不算**套餐耗尽，不触发方案暂停 |

> ⚠️ 上游额度的查询结果**只用于展示与告警**，不参与路由决策——不会因为「某个上游余额为 0」就自动跳过某个候选方案。
