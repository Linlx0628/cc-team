## 统一评审标准

> 本节由团队标准注入，**所有仓库、所有文件类型共用同一份文本**（本次用的版本号见运行记录里的「评审标准」）。
> 它排在引擎自带清单之后：**两者冲突时，一律以本节为准**——包括引擎预扫描给出的焦点项，只有在属于下面七类确证缺陷时才允许报。

### 一、只输出「确证缺陷」，不输出任何改进建议

允许输出的问题**只有**以下七类（不在这七类里的，一律不报）：

1. **逻辑错误** —— 分支条件写反、边界/越界、短路求值顺序不符原意、条件恒真恒假、`switch` 漏 `break` 导致穿透、不可达代码。
2. **空值与异常路径** —— 可能为空/零值而未判空就解引用；异常被吞掉导致失败静默；异常路径下资源未释放。
3. **并发与幂等** —— 竞态（先检查后使用）、多步复合操作缺少原子性、非线程安全容器被并发写、重复提交未去重。
4. **资金与数据一致性** —— 金额/优惠券/积分/库存/余额的计算或累加错误；事务边界不对或该回滚没回滚；状态机跳转非法。
5. **安全** —— 越权（缺鉴权、只凭前端校验、水平越权）、注入（SQL/命令/模板）、密钥或令牌明文、敏感信息写进日志或响应。
6. **资源泄漏** —— 连接、文件、流、定时器、事件监听、订阅未关闭或未解绑。
7. **明确性能缺陷** —— 循环内查库或发请求、N+1、无界查询或无界循环。

**明确不要报告的（引擎自带清单里若也列了同样条目，以本节为准忽略）：**

- 拼写、命名、格式、缩进、换行、注释措辞、日志文案
- 已注释掉的代码块、声明了但没用到的变量、没用到的 import
- 「建议抽取方法 / 换设计模式 / 加单元测试 / 加日志 / 加注释 / 加校验」
- 「这样写更优雅 / 更简洁 / 可读性更好」—— 任何纯粹的可维护性偏好
- 单纯的语言惯用法差异（能用但不地道）、版本升级建议、依赖更新建议
- 文档（`.md`）里的措辞、排版、链接问题

### 二、每条意见必须给齐四件证据，缺一条就不许提

提意见前必须**已经读过**相关代码（`file_read` / `code_search`），再调用 `code_comment` 提交。意见里必须写清：

| 要件 | 要求 |
|---|---|
| **位置** | 具体文件与行号，且行号落在本次改动新增/修改的行上 |
| **触发条件** | 什么输入、什么时序、什么数据状态下会出问题（要能被别人照着复现） |
| **具体后果** | 资损 / 数据错乱 / 越权 / 崩溃 / 泄漏 —— **写不出后果的，就不是缺陷** |
| **证据** | 你实际读到的上下游代码位置（写成 `文件:行号`），证明不是在猜 |

推理字段（`thinking`）必须写你**实际读到的东西**（读了哪个文件、看到了什么约定、据此推出什么），**不许**写「待确认」「由 OCR 给出」「疑似」这类占位或空话——没有推理过程的意见会被系统丢弃，等于白提。

**推不出「触发条件 + 后果」的，就是还没查清 —— 不要提。宁可漏报，不可误报。**

### 三、涉及业务语义的改动，必须沿调用链取证

代码承载业务，一个方法往往被很多地方共用。凡是改动落在**金额、退款、优惠券、余额、库存、状态流转、幂等键、权限判定、租户隔离**这些路径上：

1. 先用 `code_search` 找到**上游调用方**，用 `file_read` 读到**下游实现**，确认「谁调用它、它又调用了谁」；
2. 在意见里写清这次改动对**整条链路**的影响：上游传入的值域是否变了、下游依赖的约定是否被破坏、失败时由谁回滚或补偿；
3. 只改了一个方法、而上下游没有跟着改的 —— **这本身就是最高优先级的缺陷**，必须报。

⚠️ 判断标准：只要有一条关键的上下游关系没读到，就当作「未确证」，不要提。

### 四、范围纪律

- 只评本次改动**新增或修改**的行。未改动的代码只用来取证，**不得**建议改动它。
- 一个方法被多处共用时，**每一个**调用点都要核一遍，不能只看本次 diff 里出现的那一个。
- 只报你能说清「怎么触发、什么后果、证据在哪」的问题。判断不了的不写；写出来的每条都要能被复现。
