# 代理与调度机制

本页解释请求转发层**怎么重试、怎么限流、怎么熔断、怎么调度**。配套阅读：[配额与计费机制](mechanism-quota.md)。

## 超时与重试

参数（设置页 → 全局配置 → 超时 & 重试）：

| UI 名称 | config 字段 | 默认值 | 保存范围 | 作用 |
|---|---|---|---|---|
| JSON 请求超时 | `proxy.timeout` | 180,000ms（3 分钟） | 10s–10min | 非流式上游超时 |
| 流式请求超时 | `proxy.streamTimeout` | 600,000ms（10 分钟） | 1min–30min | 流式 socket 级兜底超时 |
| 最大重试次数 | `proxy.maxRetries` | 3 | 0–10 | 非流式**同一上游**重试次数 |
| 重试基础延迟 | `proxy.retryDelay` | 1000ms | 100ms–30s | 指数退避基数 |
| 可重试状态码 | `proxy.retryableStatusCodes` | 429, 502, 503, 504 | 数字列表，非法项丢弃 | 命中才同上游重试 |
| 流式空闲超时 | `proxy.streamIdleTimeout` | 120,000ms | ⚠️ **无 UI** | 流内多久没数据判死，0 = 关闭 |
| 粘性会话 TTL | `proxy.stickySessionTtlSeconds` | 300s | ⚠️ **无 UI** | 0 = 关闭 |
| 限流回退秒数 | `proxy.rateLimitFallbackSeconds` | 120 | ⚠️ **无 UI** | 上游 429 无恢复信息时的兜底窗口 |

> ⚠️ 三个「无 UI」字段设置页没有输入框，**必须手改 config.json 并重启**才能生效（启动时快照）；其余有 UI 的字段保存即热更新。

进程级：服务自身超时 = max(流式, JSON) + 60 秒；请求体上限 50MB。

### 重试算法（仅非流式）

```text
attempt = 0 .. maxRetries:
  延迟 = retryDelay × 2^attempt（封顶 10s）± 25% 随机抖动
```

什么情况才走「同上游重试」（判定顺序）：

1. 上游 429 且正文命中**套餐耗尽**特征 → 抛给 failover **换方案**，不原地重试
2. 上游 429 且命中**频率限速**特征（如「速率限制」「too many requests」）→ 突发限速，走重试路径**原地重试**
3. 状态码 ∈ 可重试列表 → 退避重试
4. 网络异常/超时 → 记熔断失败 + 退避重试

重试全部耗尽：超时 → 504，其余 → 502。重试过的响应带 `x-proxy-retry: <次数>` 响应头。

> ⚠️ **流式请求没有网络错误重试**——单次尝试，失败直接抛给 failover 换下一个方案（流已经开始就没法安全重放）。唯一的例外是「工具调用自愈重发」，最多 1 次且不占重试额度。

### 流式请求的三层防护

1. **HTTP 429**：先缓冲完整错误体、**不给客户端写任何字节**；判定为套餐限 → 无缝切下一候选方案（客户端无感）；判定为突发限速 → 原样透传 429
2. **HTTP 200 但流内报错**（SSE 首帧是 `response.failed` / `error`）：响应头发出前最多缓冲 64KB 预备区；对失败帧做同样的 429 分类，命中则切方案
3. **空闲看门狗**：每个上游数据块到达都会重置计时器，`streamIdleTimeout`（默认 2 分钟）内无数据即断开上游；响应头已发出的场景直接截断 SSE

## 流量控制

| 限制 | 默认值 | 实现 | 超限 |
|---|---|---|---|
| 每用户并发 | 5（1–50） | **每用户全局计数，不分方案**；请求结束（含客户端提前断开）即释放 | 429 `concurrency_exceeded`，Retry-After: 1 |
| 每用户频率 | 60 次/分钟（1–600） | 60 秒**滚动窗口**（保留最近 60s 的时间戳） | 429 `rate_limit_exceeded`，Retry-After: 60 |
| IP 限流 | 120 次/分钟（**硬编码**，不可配） | 同上滚动窗口 | 429，Retry-After: 60 |
| 登录尝试 | 5 次失败锁 15 分钟 | 针对后台登录接口 | 锁定期拒绝 |

## 熔断器状态机

每个方案一个熔断器（参数在设置页「流量控制」里）：

| 参数 | 默认 | 范围 |
|---|---|---|
| 熔断失败阈值 `circuitBreakerFailures` | 连续失败 **5** 次 → 熔断 | 1–50 |
| 熔断冷却时间 `circuitBreakerCooldown` | 30 秒 | 1s–5min |

```text
CLOSED（正常）─ 连续失败 ≥ 阈值 → OPEN（熔断）
OPEN ─ 冷却到期后放探测 → HALF_OPEN（半开）
HALF_OPEN ─ 探测成功（并发上限 2 次）→ CLOSED
HALF_OPEN ─ 探测失败 → 冷却翻倍后继续 OPEN
```

- **指数退避公式**：`冷却 = min(30s × 2^连续探测失败次数, 5 分钟)`——即 ×2 递增、封顶 8 倍 / 5 分钟；探测成功清零
- 熔断中的方案**自动退出 failover 候选**，恢复后**自动回到候选列表**——全程无需手工重置
- 设置页/方案中心显示熔断状态与「距下次探测秒数」
- 注意：状态码 <500 一律记为成功（4xx 不算上游故障）；≥500 才累计失败

## 上游套餐限流记忆（429 ≠ 熔断）

上游 429 被判定为**套餐耗尽**时（见 [FAQ 决策表](faq.md#收到-429-了到底是什么限制)），方案被标记限流并**记住恢复时刻**：

```text
恢复时刻优先级：
1. 正文里的重置时刻（中文「限额将在 2026-09-16 20:00 重置」或英文 "reset at ..."，
   英文报文缺时区时默认按北京时间解析）
2. Retry-After 响应头（钳制到 15 秒–600 秒——5 小时级套餐窗口下分钟级估值不可信）
3. 兜底：120 秒（rateLimitFallbackSeconds）
```

- 限流状态**持久化到数据库，重启不清除**；到期**惰性恢复**（检查时发现过期即删，无定时器），写一条「自动恢复参与 failover」审计
- 与熔断互相独立：限流有已知恢复时刻，熔断靠探测恢复
- 全组方案都限流时，客户端收到 429：`所有可用方案均已限额，最早 {时刻} 恢复。`
- 设置页「数据管理 → 清除限流状态」可手动解除

## failover 与组头回切

候选列表 = 生效组成员的定义顺序，经过滤后逐个尝试：

```text
过滤掉：限流标记中的 / 熔断中的 / 用户无权的 / 无 runtime 的
      → 粘性会话把绑定的方案重排到队首（见下节）
      → 逐个尝试；最后一个候选失败才把它的错误返回给客户端
```

**组头回切**的完整语义：

- 组头不可用（限流/熔断）→ 流量由组内下一位**代答**，记一条「failover 切换」（附原因）
- 组头恢复 → 流量**自动切回**组头，记一条「组头恢复接管」
- 一次持续故障只产生一对「切换 + 恢复」记录（状态对比去重，不是每请求一行）
- 全部候选不可用时的兜底：回退到默认入口的基础组头——**宁可服务也不轻易 429**

## 粘性会话（缓存亲和）

两协议都是「无状态重放」：每轮把全部对话重发一遍。如果同一个会话的请求被打到不同方案，上游的 prompt 缓存全部冷启动、全额重付。粘性会话就是让**同一会话粘在同一个方案上**。

| 项 | 值 |
|---|---|
| TTL | 300 秒（每轮成功服务即刷新；0 = 关闭）|
| 存储 | 进程内存，上限 1000 条（LRU），**重启即失**；设置页可手动清除 |
| 范围 | 只对协议默认入口（`/v1`、`/v1/responses`）生效；`/后缀` 直连不参与 |

**会话怎么识别**（三级优先）：

1. 请求头 `session-id`（Codex 实际发的是这个连字符形式）/ `session_id` / `x-session-id` / `x-claude-code-session-id`
2. 请求体 `prompt_cache_key` 字段
3. 首轮消息摘要：取（system/instructions + 第一条消息）做 sha256 前 16 位（键名排序后序列化，客户端键序不同不影响）——重放式协议首条消息跨轮不变，所以稳定

**绑定与回切**：

- 会话由**生效组头**服务 → 刷新绑定（保持亲和）
- 会话由 failover 备选代答 → **删除绑定**——组头一旦恢复，对话自然回到组头，不会钉死在备选上
- 可用性永远优先于亲和：绑定的方案限流/熔断时，正常走 failover

## 方案组调度求值

**没有定时器**——每个请求进来实时求值一次「此刻该用哪个组」，跨时间边界无需任何 reload。

```text
1) 手动指定（override）存在且未到期 → 生效
2) 否则：按数组顺序找第一条命中的时间规则（星期 × 时段匹配）→ 组非空才生效
   ⚠️ 组为空则继续找下一条规则，而不是跳回基础组
3) 兜底：基础组 @base
```

**规则匹配细则**：

- 星期按北京时间判定；**跨午夜窗口归开始日**——「周六 22:00–周日 02:00」在周日 01:00 命中（属周六的规则），周五 01:00 不命中
- `start:end` 配置缺一端、两端相同、时间非法 → **整条规则丢弃**（绝不静默变全天）
- 星期一个都没选 → 规则判非法，同样丢弃
- 规则表为空时功能完全惰性，恒为基础组

**手动指定的到期时刻** = 下一个会**改变生效组**的时间边界（比较的是组名，两条规则同组不算切换）；没有任何翻转边界时退到下一个北京时间零点——**绝不永不过期**。到期收回不是定时器，而是每请求求值时发现过期自然失效。

**下次切换时刻**的算法：扫描未来 8 天内所有规则的起止分钟 + 每天零点，取最早的「生效组名真正改变」的时刻——这就是调度视图里「下次切换时刻」和手动指定到期时间的来源。

## WebSocket 通道（Codex remote compact）

remote compact（会话压缩）是 Codex 的私有服务端压缩协议：客户端对 `wire_api="responses"` 的通道先探测 **WS upgrade**（GET + `Upgrade: websocket`），404 则回落 HTTPS POST+SSE——所以 WS 与 HTTP 并存，互不影响。网关在 `/v1/responses`（含方案后缀路径）上接住 upgrade：

- **鉴权在握手时**：`Authorization: Bearer` / `x-api-key`（也支持 `?key=` 查询参数，给设不了自定义头的 WS 客户端），拒绝时向 socket 写普通 HTTP 401/403 后断开
- **一帧一请求**：连接建立后等客户端发一帧 `response.create` JSON（帧体 = 标准 Responses 请求），合成一次**普通 POST** 走完整代理链路——鉴权、配额、failover、用量记账全部复用；一条连接同时只跑一帧（忙则回 `connection_busy` 错误帧）
- **事件回传**：上游 SSE 的每个 `data:` 事件 JSON 作为 WS 文本帧逐个回传（`event:` 行/空行/`[DONE]` 不传）；错误统一归一化为 `{type:"error",error:{…}}` 帧
- **断开即取消**：WS 客户端断开而请求未完成时，代理的客户端中断路径（markClientAborted）会销毁上游请求
- **帧格式（经 codex CLI 0.145 真机抓帧验证）**：客户端帧为顶层 `{"type":"response.create","model":…,"input":…,"tools":…}`——**平铺**的 Responses 请求体加一个 `type` 标记（非嵌套 `response:{}`）；网关剥掉 `type` 后按普通请求转发。服务端回帧 = 每个 SSE `data:` 事件的 JSON 原文
- **连接复用**：codex 在同一 WS 连接上用 `previous_response_id` 续会话多轮；打开连接时会先发一个 `input:[]` 的 warmup 空请求
- **通道选择**：provider 声明 `supports_websockets = false` 时 codex 全程走 HTTP（含 compact）；声明 `true`（或内置通道未声明）时对话与 compact 都走 WS。本网关生成的 ccteam provider 模板保持 `false`（主对话走 HTTP 更成熟），WS 通道服务内置通道的 compact
- compact 的**响应语义由上游负责**：网关只做传输与标准 Responses 转发；上游若不支持 Codex 的压缩响应约定，compact 结果可能被 codex 判为无效而重试
- 传输层是手写的最小 RFC6455 实现（`lib/ws-server.mjs`，纯 text 帧、无压缩），零新依赖；握手已被真实 codex 客户端验证（sec-websocket-accept 计算正确）
